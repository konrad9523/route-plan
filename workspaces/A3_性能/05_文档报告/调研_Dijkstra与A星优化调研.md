### 2.3 数据侧的关键事实（影响设计决策）

读图数据（`osm_loader` 的输出）得到三条必须尊重的性质：

| 性质 | 说明 | 对设计的影响 |
|---|---|---|
| **有向图，且混有单向边** | 部分节点对只有一个方向可达 | 反向搜索必须建**反向邻接表**，不能用正向表代替（§3.4） |
| **存在平行边** | 同一对节点之间可能有多条边（不同 edge id） | 路径重建必须按 **edge id** 取权，不能按"节点对"反查第一条边（§7.2） |
| **边权为浮点米数** | `length_m` 是浮点 | 不能直接整数化去套 radix heap 等整数专用结构（§9.2） |

### 3.1 GraphHopper

**为什么优先看它**：GraphHopper 的 `AStar.java` / `Dijkstra.java` 是少数把
"启发式可插拔"与"路径重建与搜索分层"写得非常清晰的实现，且都是小文件，
适合精读。

#### 3.1.1 启发式可插拔（`WeightApproximator`）

`AStar.java` 通过 `WeightApproximator` 接口取启发值，而不是把距离公式写死在循环里。

```java
// GraphHopper AStar.java（结构示意）
double h = weightApproximator.approximate(adjNode);
double f = g + h;
```

**可迁移点**：启发式应当作为参数注入。收益是双重的——
① 便于公平消融（`h=0`、Haversine、平面投影、ALT 可以跑同一套基准）；
② 便于后续加 ALT 等强启发式而不改搜索主体。

**已落地为**：本项目改进实现里 `astar(..., heuristic=...)`、`dijkstra(..., heuristic=...)`。

#### 3.1.2 A\* 等价于重加权图上的 Dijkstra

`AStar.java` 的注释明确指出：A\* 可以看作在重加权图
`l_r(v,w) = l(v,w) + h(w) − h(v)` 上跑 Dijkstra。

**可迁移点**：这一条让"重加权 Dijkstra"与"A\*"在代码结构上可以统一，
也提供了一个**交叉验证手段**：两个实现应当给出完全相同的展开数
（因为数学上等价），据此可以发现任一实现里的簿记错误。

**依据出处**：该重加权形式亦见于 Eppstein 的讲义与 ALT 论文的推导（§4.2）。

#### 3.1.3 `SPTEntry`：路径重建只依赖边端点

`SPTEntry.java` 的字段是：

```java
class SPTEntry {
    int edge;        // 进入本节点的边
    int adjNode;     // 本节点
    double weight;   // g 值
    SPTEntry parent; // 父 entry
    boolean deleted; // 惰性删除标记
}
```

**可迁移点**：搜索树节点只需保存"进入边 + 父节点"，**不需要同时维护
`prev[]` 和 `prev_edge[]` 两张表**。回溯时从边取端点即可。

**注意（本项目踩过的坑）**：如果按"节点对"反查边来取权，在有**平行边**的图上会取错。
GraphHopper 之所以能这样做，是因为它存的是**边的内部索引**，而不是靠节点对反查。
本项目因此改为父链同时存 **edge id**（§7.2）。

#### 3.1.4 惰性删除（tombstone）与 `isDeleted()`

`Dijkstra.java` 在更新节点距离时，把旧 entry 标记 `deleted`，
弹出时检查 `isDeleted()` 直接跳过，而不是维护"decrease-key"。

**可迁移点**：这正是 Python `heapq` 章节里常说的"lazy deletion"。
它对 Python 格外重要——`heapq` 本身**不提供 decrease-key**。

**不采纳的部分**：GraphHopper 显式维护 `deleted` 标记并做对象池化，
这与 Java 的对象分配模型有关；Python 里用"比较当前 g 与堆项 g"即可达到同样效果，
额外维护标记反而增加开销。

### 3.2 Organic-Maps

**为什么看它**：`astar_algorithm.hpp`（819 行）包含一份完整的、面向移动端的
双向 A\* 实现，注释详细。

#### 3.2.1 双向搜索的启发式方向必须相反

`astar_algorithm.hpp` 里正向搜索用"到终点的估计"，反向搜索用"到起点的估计"。

**可迁移点（易错点）**：反向搜索**不能**也用 `h(v, goal)`。若两侧都用同一个目标，
反向搜索的启发值方向就与它的扩展方向相反，一致性立刻失效。

**已落地为**：`hb(node) = heuristic(start, node)`。

#### 3.2.2 相遇候选与 settled 的关系

Organic-Maps 在松弛邻边后检查对侧标签，并用 `AreWavesConnectible` 确认两条父链能组成
真实路径；它并非简单地要求“两个方向都 settled 才可更新候选”。暂定 `g` 标签只要各自
对应真实父链，其和就是可行路径的上界，不会低于最优距离。真正的风险是父链尚未同步、
使用了过期标签，或把不可连接的两侧父链拼起来。

**可迁移点**：不能把“相遇必须在 settled 后”当成普遍规则；要验证候选确实对应可行路径，
并让停止界与队列排序的距离度量一致。

#### 3.2.3 Organic-Maps 的终止式：比较的是重加权距离

源码第 606 行的 `TopDistance()` 返回的是队列状态对应的**重加权距离**，而比较对象是
`bestPathReducedLength`，不是原始长度上的两个任意 `g` 或未配平 `f`。前面 `ConsistentHeuristic`
为正反两侧构造相反的平衡势，扩展时用 `weight + pW - pV` 计算重加权边；相遇候选也在
同一 reduced 度量下合并，并检查两侧父链是否可连接。因此“两个 top 来自不同节点集合”
本身并不能推翻这个下界。源码还保留了对启发式一致性的 TODO/负重加权检查，说明其前提
仍须沿调用链核验。

**本地结论**：该实现提供的是“共享可行势 + 同一重加权度量上的队列界”，不是可以脱离上下文
照抄的裸公式。本项目据此实现 `p(v)=(h(v,t)-h(s,v))/2`，每条展开边验证重加权代价非负，
并以 `best + p(t)-p(s)` 还原停止界；不复用它的路线拼装/特定图接口。

**此前报告的更正**：我们曾把旧原型的失败误归因于“两侧前沿属于不同节点集合”，并称该式在
有向图不成立。该理论解释不正确；旧原型反例只证明其当时的堆键、候选更新或度量组合不正确，
后续应按具体实现条件复核，不能作为否定平衡双向 A* 的证据。

### 3.3 NetworkX

**为什么看它**：同语言（Python），`heapq` 用法、lazy deletion 的写法可逐一对照。

#### 3.3.1 `enqueued[nxt] = (g, h)` 的单字典技巧

`networkx/algorithms/shortest_paths/astar.py` 把"当前最好的 g"与"首次算出的 h"
**放在同一个字典的值里**，一次查表同时取到两者：

```python
if nxt in enqueued:
    old_g, h = enqueued[nxt]      # 一次查表拿到 g 和 h
    if old_g <= new_g:
        continue
else:
    h = heuristic(nxt, goal)       # 首次发现才计算 h
```

**可迁移点**：这比"`g_score[v]` 与 `h_cache[v]` 两个字典分别查"少一次字典查找。
在高频松弛循环里，Python 的字典查找开销不可忽略。

#### 3.3.2 官方文档的重要提醒

NetworkX 的 `astar_path` 文档明确指出：**启发式会被缓存，因此必须保证
可采纳（admissible）**。这与 §4.1 的理论要求一致。

#### 3.3.3 Dijkstra 的目标提前终止

`weighted.py` 的 Dijkstra 在目标节点被弹出时即可终止（不进 `seen` 的继续循环），
而 `astar.py` 也采用同样的"弹出即判定"。两者都**不需要**等到队列空。

### 3.4 OSRM Backend / Valhalla

**为什么看它们**：架构层面的启发，而不是算法细节。

- **OSRM**：提供 CH 与 MLD 两条离线准备流程，README 推荐多数场景用 MLD。
- **Valhalla**：同样以预处理 + 层级图为核心。

**核心认识（对判断"改进空间在哪里"很关键）**：

> 成熟引擎相对朴素 Dijkstra 的巨大速度优势，**主要来自层次化预处理与捷径边**，
> 而不是基础 Dijkstra/A\* 的微优化。

**对本案的处置**：本轮**不实现** CH/MLD。理由是它带来预处理、存储、
路径解压与正确性边界的一整套新问题，属于另一个工程档次（作业 2 的范畴）。
但它解释了一个常见误解：不要期望通过"把 Dijkstra 循环写得更省"
去逼近成熟引擎的查询速度。

#### 3.4.1 反向搜索必须建反向图（本项目的一条硬约束）

虽然这条主要来自有向图算法的通识，但对照引擎实现后可以确认其必要性：
反向搜索要回答"谁通向终点"。若直接扫正向邻接表，得到的
`g_b[v] = g_b[u] + w` 语义是"v 经 u 到终点"，只有在边为 `v→u` 时才成立。
在混有单向边的图上这会**造出图中不存在的路径**，得到比真最优还小的荒谬结果。

**落地方式**：预处理阶段建立 `radj[v] = [(u, w, eid), ...]`，把每条 `u→v` 收进 `radj[v]`。

### 4.1 A\* 的理论基础（最核心的一篇）

**Hart, Nilsson & Raphael (1968), _A Formal Basis for the Heuristic Determination of Minimum Cost Paths_**
IEEE Trans. Systems Science and Cybernetics.
[论文 PDF](https://ai.stanford.edu/~nilsson/OnlinePubs-Nils/PublishedPapers/astar.pdf) ·
[DOI](https://doi.org/10.1109/TSSC.1968.300136)

**解决什么问题**：首次把"用启发信息引导最短路搜索"形式化，定义 A\* 并证明其最优性条件。

**两个必须区分的概念**（本文最重要的收获）：

| 概念 | 定义 | 保证什么 |
|---|---|---|
| **可采纳（admissible）** | `h(v) ≤ d(v, goal)`：启发值不超过真实剩余代价 | A\* **最终**返回最优解 |
| **一致（consistent / monotone）** | `h(u) ≤ w(u,v) + h(v)`（等价于 `l_r = w + h(v) − h(u) ≥ 0`） | 节点**首次被弹出时其 g 已最优**（settled = optimal） |

**为什么这个区分对本案是关键**：

- 可采纳但不一致的启发式可能要求重新打开获得更优 `g` 的节点；不能把首次弹出的普通节点永久封闭。目标终止条件还需结合重开策略、非负边权与 `h(goal)=0` 判断，不能仅以“弹出目标”为由判错。参见 [NetworkX A* 文档](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.shortest_paths.astar.astar_path.html)。
- 一致性还带来一个实用的副产品：`l_r ≥ 0`，于是 A\* 的重加权形式可以直接复用
  Dijkstra 的循环结构（对应 GraphHopper 的设计，§3.1.2）。

**可迁移结论**：
1. 必须明确自己的启发式满足哪一条，不能含糊。
2. 一致性是一个**可离线执行的数据属性检查**：对每个节点、每条边验证
   `w + h(v) − h(u) ≥ 0`。这比"在每次松弛里顺便检查"便宜得多（见 §5.4）。

**不可迁移部分**：论文的图模型是通用加权图，不涉及转向限制、
道路等级等路网特有约束；那属于后续扩展。

### 4.2 强启发式：ALT

**Goldberg & Harrelson (SODA 2005), _Computing the Shortest Path: A\* Search Meets Graph Theory_**
[Microsoft Research 页面与 PDF](https://www.microsoft.com/en-us/research/publication/computing-the-shortest-path-a-search-meets-graph-theory/)

**解决什么问题**：纯几何启发式（欧氏/大圆距离）在路网上往往偏弱
（因为路网距离可能远大于直线距离）。ALT 用少量**地标（landmark）**的
预处理最短距离，通过三角不等式构造强得多的下界。

**方法（有向图版）**：对地标 `L`，保存 `d(L,x)` 与 `d(x,L)`，则

```
h_L(v,t) = max( 0,  d(L,t) − d(L,v),  d(v,L) − d(t,L) )
```

两项分别来自有向三角不等式：

```
d(L,t) ≤ d(L,v) + d(v,t)   ⟹   d(v,t) ≥ d(L,t) − d(L,v)
d(v,L) ≤ d(v,t) + d(t,L)   ⟹   d(v,t) ≥ d(v,L) − d(t,L)
```

**多个地标取 max 仍是下界**，因此可以叠加。

**可迁移结论**：
1. 这是文献中**与本任务最贴合、且能保持精确最短路、又不引入庞大工程**的强启发式方向。
2. 必须与几何启发式取 `max`（仍可采纳），因为两者在不同点对上的强弱不同。
3. **记账要求**：ALT 有预处理成本（每个地标一次全图搜索）与内存成本
   （每个地标两张距离表），必须与查询耗时**分开报告**，否则收益会被误判。
4. 对不连通点对要处理"距离为无穷"的情况（跳过该项）。

**不可迁移部分**：论文报告的加速比依赖其路网规模与实现，不能直接作为本项目的预期值。

**解决什么问题**：专门研究 GIS 来源道路网上的一对一最短路，用真实路网做经验比较。

## 5. 启发函数设计

> 用户明确要求重点调研启发函数设计。本节把理论（§4.1、§4.2）、
> 数据事实（§2.3）与引擎做法（§3.1.1）合成一份可直接执行的设计方案。

### 5.1 候选方案总表

记 `d_geo(u,v)` 为两端经纬度间距离，`w(u,v)` 为边代价（米）。

| h 方案 | 形式 | 可采纳条件 | 一致性条件 | 代价 | 建议 |
|---|---|---|---|---|---|
| `h = 0` | 0 | 任意非负权图 | 天然满足 | 无 | **保留为消融对照**（等价 Dijkstra） |
| Haversine | 球面大圆距离 | 每段道路代价 ≥ 端点大圆距离 | 球面三角不等式 | 较高（多次超越函数） | 保留为对照基线 |
| **平面投影** | 见 §5.2 | 不能由局部近似直接保证，须验证 | 对固定图、权重、目标逐边验证 | 较低 | 保留为实验对照，非自动安全默认 |
| 时间启发 | `d_geo(v,t) / v_max` | 边权为秒，`v_max` 为所有可用边的安全上界 | 同上 | 低 | 仅当引入"最快路径"模式时 |
| ALT（有向） | 见 §4.2 | 静态非负边代价 + 地标预处理 | 三角不等式 | 查询低、预处理高 | **首选的强启发式实验** |
| `max(几何, ALT)` | 两者取大 | 两者各自可采纳 ⟹ 取大仍可采纳 | 需分别验证 | 叠加 | 与 ALT 同批验证 |

### 5.2 推荐默认：平面投影（`DistancePlaneProjection`）

```
h(v, t) = R · sqrt( Δlat² + ( cos(midLat) · Δlon )² )
其中  midLat = (lat_v + lat_t) / 2 ,  Δ 为弧度差,  R = 6371000 m
```

来源：GraphHopper `util/DistancePlaneProjection.java`。

**为什么它更快**：Haversine 需要 `sin`、`cos`、`atan2`、两次 `sqrt` 等约 8 次
超越函数调用；平面投影只需 4 次基础运算（两次减、两次乘、一次平方和、一次开方，
外加一次 `cos`）。

**可采纳性不能由 `midLat` 自动推出**：该公式是局部平面近似，不存在本文旧稿所称的普遍“大圆距离下界”保证。武汉复测在 50 个目标的逐边检查中发现 1,627 次负重加权代价，因此不能直接用于标签确定式重加权 Dijkstra。平面 A* 的 0/50 对拍结果只是样本证据，不是全图所有查询的证明。

**可迁移结论**：先验证代价单位、几何条件、目标与启发式；ALT-only 与平面组合版本分别作为实验候选，不从局部计算成本直接推导默认选型。

### 5.3 一致性验证方案（离线，必须做）

一致性定义（§4.1）：对每个节点 `u`、每条边 `u→v`：

```
l_r(u,v) = w(u,v) + h(v) − h(u)  ≥  0
```

**执行方式**：
- 目标节点需固定（`h` 依赖目标），因此抽样多个目标节点，对全图所有边检查一遍。
- 数据侧还需检查一个必要前提：**每条边的 `w` 不小于两端点的大圆距离**
  （否则几何启发式在原理上就不可能可采纳）。
- 项目已有 `path_planning.check_heuristic_consistency()` 承担这一职责。

**为什么必须离线做**：见 §5.4。

### 5.4 一个重要的"不要做什么"

**不要在热循环里做一致性检查。**

逐边检查会给每次松弛增加一次浮点比较与一个分支。在纯 Python 里，
这种"看起来无害"的检查会显著抬高单次查询耗时，甚至抵消几何启发式带来的全部收益。

**正确的分工**：
- **离线**（数据加载时或测试中）：验证一致性一次即可。图、权重、目标与启发式都不变时才可复用结论；仅抽样目标通过不能推广到所有目标。
- **在线**（每次查询）：只做启发值计算与缓存，不做合法性检查。

这一条与 §3.1.1 的"启发式可插拔"配合使用：
调试时可临时打开检查，生产路径上关闭。

### 5.5 启发值缓存

同一节点在一次查询中会被**多次松弛**（每次找到更短的 `g`）。
启发值只依赖"节点 + 固定目标"，因此**每个节点只需算一次**。

**实现方式**（对照 NetworkX，§3.3.1）：
把"当前最好 `g`"与"已算出的 `h`"放在**同一个字典**里，
一次查表同时拿到两者；只有首次发现该节点时才计算 `h`。

**为什么要强调**：在平面投影这类"已经很便宜"的启发式下，
**重复计算的相对浪费更大**——因为分母变小了。
这也是"换个更便宜的启发式"必须与"缓存启发值"配套做的原因。

### 5.6 启发函数设计的检查清单

设计或更换启发式时，逐项确认：

- [ ] `h(goal) = 0`
- [ ] `h(v) ≥ 0` 对所有 v
- [ ] **可采纳性**：`h(v) ≤ d(v, goal)`——对具体数据抽样验证，不能只靠推理
- [ ] **一致性**：`w(u,v) + h(v) − h(u) ≥ 0` 对所有边成立（离线全图检查）
- [ ] `h` 只依赖"节点 + 目标"，与"当前已走代价"无关（否则不能缓存）
- [ ] 若权重单位改变（米 → 秒），**必须重新证明**可采纳性，不可沿用旧结论
- [ ] 组合启发式（取 max）后再次验证可采纳性
- [ ] 性能上记录：单次调用耗时、每查询调用次数、展开节点数

## 6. 双向 A\* 专题调研

> §3.2 记录的是从 Organic-Maps 源码里读到的两条具体做法；本节是**双向 A\* 本身的
> 系统调研**——它相对单向 A\* 的设计空间、正确性陷阱、文献结论与适用条件。

### 6.1 基本思想与两个方向的定义

双向 A\* 从起点与终点**同时**做最佳优先搜索，期望两个搜索在某处相遇，
从而把"半径 R 的球"变成"半径 R/2 的两个球"，理论上显著减少扩展量。

约定（本项目采用，与 §3.2.1 一致）：

| 方向 | 在哪个图上搜 | 距离含义 | 启发函数 |
|---|---|---|---|
| 正向 | 原图 `adj`，自 `start` 生长 | `g_f[v] = d(start, v)` | `h_f(v) = h(v, goal)`——v **到终点**的估计 |
| 反向 | **反向图** `radj`，自 `goal` 生长 | `g_b[v] = d(v, goal)` | `h_b(v) = h(start, v)`——**起点**到 v 的估计 |

**一条易错点（重复强调，因为代价极高）**：反向侧的启发函数必须估计
"起点到 v"，不能也用"v 到终点"。若两侧都用同一个目标，反向搜索的启发值方向
与它的扩展方向相反，一致性立即失效。

### 6.2 三种启发式评估策略（文献分类）

双向启发式搜索的文献把"如何用启发值引导两个方向"分为三类
（综述与分类见 [Kaindl & Kainz, JAIR 1997](http://www.cs.cmu.edu/afs/cs/project/jair/pub/volume7/kaindl97a.pdf)）：

| 策略 | 正向用什么 | 反向用什么 | 特点 |
|---|---|---|---|
| **front-to-end**（端到端） | `h(v, goal)` | `h(start, v)` | 每个方向只用自己的目标；当前实现以此构造平衡势函数 |
| **front-to-front**（端到端） | 估计"到对侧前沿某节点"的距离 | 同 | 启发值更强，但每次评估要对对侧前沿做最小化，代价高 |
| **perimeter**（周界） | 用对侧前沿构造估计 | 同 | 折中方案 |

最早的双向启发式算法 **BHPA（Pohl, 1971）** 属于 front-to-end。
本项目的势函数由端到端距离启发式构造；两侧却在**同一重加权图**上用距离键搜索，
并非简单地把两个未经平衡的 `g+h` 值相加。

### 6.3 ⚠️ 核心难点：终止条件

**这是双向 A\* 最容易做错、也最容易被低估的部分。**
文献明确指出：实现双向**启发式**搜索的关键问题之一就是
"设计一个高效的终止条件"（[HAL 综述](https://hal.science/hal-01388530v1/document)）。

> **更正旧稿中的过度概括**：未经配平的两侧 `f` 不能直接相加；但“两个堆顶来自不同
> 节点集合，所以 `min_g_f + min_g_b` 一概无效”是错误说法。经典双向 Dijkstra 在堆按真实
> `g` 排序、`best` 是可行路径上界且相遇/跨边候选正确更新时，确有安全的提前停止条件。
> 当前代码采用平衡势函数方案，具体公式见下；旧原型的失败测试只说明那套具体队列键与
> 更新组合失败，不能据此否定一般定理。

#### 当前实现：平衡势函数与共享重加权图

将端到端启发式平衡成一个势函数：

```
p(v) = (h(v, goal) - h(start, v)) / 2
w'(u,v) = w(u,v) - p(u) + p(v)
```

若每条有向边均满足 `w'(u,v) >= 0`，正反两侧便在同一重加权图上运行 Dijkstra。
其队列键为 `k_f(v)=g_f(v)-p(start)+p(v)`、`k_b(v)=g_b(v)-p(v)+p(goal)`。
`best` 是已发现可行完整路径的原始代价时，安全停止条件为：

```
min(k_f) + min(k_b) >= best + p(goal) - p(start)
```

任一完整路径的重加权长度等于其原始长度加固定常数 `p(goal)-p(start)`，因此队列下界
与当前可行路径上界可在同一度量下比较。这与 A* 可行势及重加权视角一致
（[Goldberg & Harrelson, SODA 2005](https://www.microsoft.com/en-us/research/publication/computing-the-shortest-path-a-search-meets-graph-theory/)）。
本实现默认用 Haversine 构造势函数，并在搜索时拒绝负原边权或负重加权边；自定义启发式
必须另行保证其对图边可行。

#### 为什么难：`best` 的候选与"下界"来自不同的集合

设某节点 `m` 同时被两侧访问过，则 `g_f[m] + g_b[m]` 是**一条真实路径的长度**，
可以作为上界候选 `best`。问题在于**何时可以停止**——即如何论证
"没有更短的路径了"。

对未经配平、分别使用不同启发势的两侧 A*，不能仅凭直觉把两侧最小 `f` 值相加：

```
❌  f_f(top) + f_b(top) >= best   ⟹  停止
```

是否构成下界取决于两侧势函数的关系；一般情况下没有平衡势函数的推导，条件可能过早
成立。不要把旧原型中该写法失败泛化成所有双向 A* 公式都不成立。

#### 旧原型中真实 g 前沿条件的失败（不等于一般定理）

旧原型的该次测试也出现了错误结果，但这本身不能推出经典双向 Dijkstra 停止式不成立：

```
⚠️  旧原型的 top_f + top_b >= best    只有在 top 真是 min-g 且 best/候选更新符合前提时才可用
```

标准双向 Dijkstra 的前沿和停止式有成熟证明；必要前提包括队列按真实 `g` 排序、`best`
始终为可行路径上界，并正确检查节点相遇及跨边路径。旧稿没有把失败原型的队列键和
候选更新逐项对应到这些前提，因此该反例只能作为那一实现版本的回归用例，不能作为
“两个集合不同，所以不存在下界”的证明。当前平衡势函数实现使用自己的共享重加权停止界。

#### 保守回退：为什么"两个方向都跑到队列空"一定正确

若让两个方向都收敛到队列空，则对最优路径上的**任意**节点 `v` 都有：

```
g_f[v] = d(start, v)      （正向已收敛）
g_b[v] = d(v, goal)       （反向已收敛）
⟹  g_f[v] + g_b[v] = 最优路径长度
```

因此对"两侧都访问过的节点取 `min(g_f + g_b)`"必然取到最优值。
这是最保守也最可靠的做法，代价是失去剪枝、扩展量上升。

#### 工程注意

候选可在 settled 或松弛时更新，前提是两侧标签对应的父链确实连成一条可行路径；
终止界必须与堆排序使用的同一距离度量一致。即使 `best` 正确，**父链拼装**仍可能出错（§6.4）。

### 6.4 路径拼装：三个必须显式处理的点

双向搜索最隐蔽的缺陷不在距离、而在**拼出来的路径**。以下三点在本项目都实际踩过
（详见配套实测记录）：

| # | 要求 | 不做的后果 |
|---|---|---|
| 1 | **反向搜索必须走反向图** | 在混有单向边的图上会造出图中不存在的路径，得到**比真最优还小**的荒谬距离 |
| 2 | **两条父链的方向语义必须分别确认** | 正反两侧"父节点"的含义可能相反（一侧指前驱、一侧指后继），搞反后反向段每步都用了反向边 |
| 3 | **取权必须按 edge id，不能按节点对反查** | 存在平行边时会取到另一条边，导致"报告距离正确、拼出的路径却更长" |

**第 3 点在双向场景下尤其危险**：报告值可能恰好等于最优值（因为 `best` 是对的），
但拼出的路径**长于**最优——此时若只校验"端点正确"，会完全漏过这个错误。

### 6.5 什么时候双向 A\* 真的更快（重要，反直觉）

**文献结论：双向启发式搜索并不保证比单向扩展更少。**

Kaindl & Kainz（JAIR 1997）系统分析了双向启发式搜索，并给出
**反例表明双向可能扩展比单向更多的节点**；该文的核心结论之一是
双向搜索的收益高度依赖启发式与问题结构。
另有工作专门讨论"何时应该从双向切回单向"
（[Switching from Bidirectional to Unidirectional Search, IJCAI 1999](https://www.ijcai.org/Proceedings/99-2/Papers/072.pdf)）。

结合本项目的两条约束，可以给出更具体的判断：

| 因素 | 对双向有利 | 对本项目的事实 |
|---|---|---|
| 单次扩展开销 | 越低越好（双向的收益是"少扩展"，但每个方向都要维护独立的堆/表/启发式） | **纯 Python 下很高** |
| 图规模 | 越大越有利（节省是相对量） | 几百节点，规模小 |
| 启发式强度 | 越强，单向 A\* 越快，双向的**相对**优势可能反而下降 | 平面投影属"便宜但偏弱" |
| 有向性 | 无向/双向可通行最理想 | **混有单向边**，反向图必须单独建 |

**结论（本项目判断）**：
- 双向 A\* 在**正确性**上完全可以做到与 Dijkstra 一致；
- 但它的**性能收益没有保证**，且在本项目的规模与语言条件下很可能为负；
- 因此**不应把双向 A\* 作为默认算法**，而应作为"有明确终止条件 + 有实测数据"
  之后才考虑的选项（见 §8.4、§9.2）。

### 6.6 双向 A\* 的检查清单

实现或评估双向 A\* 时逐项确认：

- [ ] 反向搜索是否运行在**反向图**上（有向图必需）
- [ ] 反向启发函数是否估计"**起点到 v**"（而非"v 到终点"）
- [ ] 两侧父链的**方向语义**是否分别确认过（前驱 vs 后继）
- [ ] `best` 是否来自两条真实父链构成的可行完整路径（暂定标签也可，不要求都 settled）
- [ ] 若用 A* 提前停止，两侧是否共享可行势/重加权度量，停止界是否含端点势差
- [ ] 若用双向 Dijkstra 停止式，队列键是否真是各侧最小未确定 `g`，并正确更新相遇点/跨边
- [ ] `best` 与两侧父链是否同步（是否存在"报告距离正确、路径却更长"）
- [ ] 路径长度是否按 **edge id** 逐段累加，而非按节点对反查
- [ ] 是否验证了**路径逐段真实存在**（只验距离会漏掉致命错误）
- [ ] 性能上是否记录：两侧各自的扩展数、总扩展数、与单向 A\* 的对比
- [ ] 是否有反例测试（尤其是单向边、平行边、不可达点对）

## 7. 路径重建与路径信息输出

> 对应用户提出的"路径重建和路径信息输出，可能大概也是我们来做"。

### 7.1 统一返回结构

现状（§2.1）：两个算法的返回签名不一致，Dijkstra 缺边序列。
**调研结论：应当统一为一个结果对象**，字段至少包含：

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| `found` | 是否可达 | 显式区分"不可达"与"出错" |
| `node_path` | 节点序列 | 前端画线、段落归属 |
| `edge_path` | **边 id 序列** | 取道路属性、去重、与原始数据对齐 |
| `distance` | 总距离（米） | 结果主指标 |
| `expanded` | 展开（settled）节点数 | 性能分析的核心口径 |
| `pushed` | 入堆次数 | 诊断重复松弛 |
| `solved` | 结果是否可信（如一致性未被破坏） | 让"降级"可被上层感知 |
| `algorithm` | 算法标识 | 日志与对比 |

**工程理由**：统一结构后，三个算法可以用**同一套验证脚本**对拍，
这是后续所有实验的基础设施。

### 7.2 路径重建：必须按 edge id 取权

**调研结论（一条硬性要求）**：

```
❌ 错误做法：已知节点对 (u, v)，在邻接表里找第一条 u→v 的边
✅ 正确做法：父链里存下搜索当时使用的 edge id，重建时按 eid 取权
```

**为什么**：本项目数据存在**平行边**（同一对节点之间多条边，§2.3）。
按节点对反查会取到另一条边，导致"沿节点链累加的长度 ≠ 报告的长度"。
GraphHopper 的 `SPTEntry` 同样存边索引（§3.1.3），原因相同。

**父链的推荐形式**：`parent[v] = (edge_id, u)`，语义为"经由 edge_id 从 u 到达 v"。
这样单张表就同时给出了前驱节点与进入边，无需 `prev[]` + `prev_edge[]` 两张表。

### 7.3 路径信息输出：可以带出的道路属性

数据侧（`osm_loader` 输出的 `Edge`）已具备以下字段，建议随路径一并输出：

| 属性 | 用途 |
|---|---|
| `name` | 路线文字描述（"沿 XX 路行驶") |
| `road_type` | 道路等级，前端可差异化渲染 |
| `speed_kmh` | 时间估算（若做最快路径） |
| `length_m` | 分段长度 |
| `allowed_modes` / `closed` / `toll` | 通行约束的透明化 |

**注意**：本轮调研范围内，重点是**结构上留好位置**（`edge_path` 已能支撑），
属性的实际拼装属于实现细节，见配套实测记录。

### 7.4 路径输出的自检项

| 检查 | 目的 |
|---|---|
| 端点正确（首 = 起点，末 = 终点） | 拼装方向没搞反 |
| 路径**逐段**在原图中真实存在 | 防止"数字对但走不通"的路径 |
| 边长累加 == 报告距离 | 防止按错误边取权（§7.2） |
| 节点序列无重复 | 防止拼装时插入瞬移 |

第 2、3 条尤其重要：有向图上的双向拼装、以及平行边取权，
都可能产出**距离看起来正常、但路径在图上不存在**的结果。
只验证距离是不够的。

## 9. 不适用与本轮不建议做的方向

明确列出"不做什么"及其理由，避免后续重复讨论。

### 9.1 不适用（有硬性限制）

| 方向 | 不适用的理由 |
|---|---|
| **radix heap / 整数专用队列** | 本项目边权是浮点米数；整数化会引入舍入误差，破坏"与 Dijkstra 逐位一致"的验证标准（§4.4） |
| **直接相加未经配平的两侧 A* `f` 值** | 不应当作通用下界；须先推导两侧势函数关系，或采用共享可行势的安全停止界（§6.3） |

### 9.2 本轮不建议做（可做，但超出范围）

| 方向 | 理由 |
|---|---|
| **CH / MLD / CRP 实现** | 需要预处理、存储、路径解压、正确性边界一整套工作，属于另一个工程档次；应与基础算法对比**分开报告**，不该混进同一轮结论 |
| **把双向搜索当作默认算法** | 在本项目规模与纯 Python 条件下未必划算；应先有正确的终止条件与实测数据再定（见配套实测记录） |
| **用合成图结论替代真实路网结论** | §4.3：几何性质直接决定几何启发式的强弱，合成图不能代表真实路网 |

### 9.3 一个容易被忽略的提醒

不要用论文或开源引擎报告的加速比作为本项目的预期值。
文献结论绑定其数据规模、硬件与实现语言；本项目是纯 Python、
几百节点规模。**所有结论都必须在本项目数据上重新测量。**

【启发函数推荐】
  候选       平面投影（局部近似，须另行验证可采纳性与一致性）
  消融对照   h=0、Haversine
  强启发式   ALT、max(几何, ALT)  ← 下一步首选
  必须离线   一致性检查 w + h(v) − h(u) ≥ 0
  必须缓存   启发值按节点缓存，（g, h)同放一字典

【路径输出】
  统一结构    found / node_path / edge_path / distance / expanded / pushed / solved
  取权方式    按 edge id，不能按节点对反查（平行边）
  自检       端点 + 逐段真实性 + 长度自洽 + 无重复节点

【双向 A*（§6）】
  基本形态   正向用 h(v,goal)、反向用 h(start,v)；反向必须在反向图上搜
  评估策略   端到端启发式构造平衡势函数；两侧在共享重加权图上跑 Dijkstra
  势函数     p(v)=(h(v,t)-h(s,v))/2；w'(u,v)=w(u,v)-p(u)+p(v)>=0
  安全停止   min(k_f)+min(k_b) >= best + p(t)-p(s)，best 为可行完整路径上界
  注意       经典双向 Dijkstra 的 min_g_f+min_g_b 条件有前提；不能把 f 堆顶附带的 g
             当作未确定集合的最小 g。两侧跑空正确但更保守。
  拼装三要点 ① 反向走反向图 ② 两侧父链方向语义分别确认 ③ 按 edge id 取权
  ⚠️ 文献     Kaindl & Kainz 1997 证明双向可能扩展比单向更多；收益无保证
  ⚠️ 本项目   不应作为默认算法，需先有正确终止条件与实测数据（§6.5）
