# 开源导航引擎设计亮点总结：OSRM 与 Valhalla

> **调研对象：** Open Source Routing Machine（OSRM）、Valhalla  
> **调研方式：** 官方项目文档查阅、在线演示界面观察、少量公开接口功能验证  
> **文档定位：** 以亲自体验的功能亮点为主、官方架构资料为辅；不进行算法跑分或全面产品排名  
> **资料核对时间：** 2026 年 11 月

## 1. 调研概述

现代导航引擎不只是计算“起点到终点的一条线”，而是由**道路网络数据、路由算法、通行成本模型、对外服务接口、导航指引和地图可视化**等部分共同组成。

OSRM 和 Valhalla 均建立在 OpenStreetMap（OSM）道路数据生态之上，但工程设计侧重点不同：

- **OSRM** 强调高性能道路路径查询，提供相对独立、职责清晰的路由 API；采用 CH（Contraction Hierarchies）和 MLD（Multi-Level Dijkstra）两条预处理与查询流水线。
- **Valhalla** 强调分层瓦片化路网与运行时动态成本模型，提供路线规划、交通方式与偏好控制、逐步导航指引、时间/距离矩阵及等时圈等能力。

需要特别说明：**在线演示地图展示的功能，只是底层导航引擎能力的一部分**。不能因为某功能没有出现在演示网页中，就认定引擎不支持该功能。


## 2. OSRM：面向高性能路由服务的设计

### 2.1 路网预处理与快速路径查询

OSRM 使用 C++ 实现，面向 OSM 道路网络进行高性能路线计算。其典型工作流程可以概括为：

```text
OSM 道路数据
    ↓
数据提取与路由属性处理（osrm-extract）
    ↓
CH 路线：收缩预处理（osrm-contract）
或 MLD 路线：分区（osrm-partition）→ 权重定制（osrm-customize）
    ↓
启动路由服务（osrm-routed）
    ↓
通过接口查询路径、矩阵等结果
```

**设计亮点：** 将较重的路网准备工作与日常查询分离，通过预处理或分层组织减少查询阶段的搜索成本。

- **CH（收缩层次）**：预先按照一定次序收缩节点，并加入必要的捷径边，以加快后续路径查询。其优势是查询效率高，但路网权重变化时通常需要相应的更新或重新预处理。
- **MLD（多层 Dijkstra）**：将路网组织为多级分区，通过分区和定制步骤支持高效查询，也更方便适应某些道路权重更新情形。OSRM 官方项目说明中一般建议优先使用 MLD；某些大型矩阵场景中 CH 仍可能有优势。

这里的 CH 和 MLD 是**后端可选的计算方案**；仅凭在线地图无法确定某次公开演示请求实际使用了哪条处理流水线。

### 2.2 标准化、模块化的路由服务

OSRM 将不同导航能力拆分为用途明确的服务接口：

| 服务 | 主要用途 | 设计特点 |
|---|---|---|
| `Route` | 两点或多点路径规划 | 返回路线几何、距离、时间，可请求备选路线与转向步骤 |
| `Nearest` | 最近道路匹配 | 将给定坐标关联到附近候选道路位置 |
| `Table` | 时间/距离矩阵 | 一次返回多组位置间的出行成本 |
| `Trip` | 多地点访问顺序优化 | 根据地点集合尝试构建更合理的访问次序，采用启发式求解 |
| `Match` | GPS 轨迹地图匹配 | 将带有噪声的轨迹点匹配到道路网络 |
| `Tile` | 路由元数据瓦片 | 输出用于查看路网及其部分内部属性的矢量瓦片 |

**设计亮点：** 不同能力通过清晰的 API 独立提供，调用端既可以做简单导航，也可以构建批量路线分析、轨迹处理或路网调试等应用。

> 说明：上表列出了官方文档支持的服务；本次实际调用验证的是 `Route`、`Nearest`、`Table` 和 `Trip`。`Match`、`Tile` 的能力描述依据官方资料，不能视为本次均已完成接口实测。

### 2.3 在线地图体验：普通用户直接感受到的功能

在进入后端接口前，我们先通过 OSRM 在线地图进行了多组真实路线规划，观察了基础交互、路线呈现和结果复用方式。

| 体验项目 | 实际操作与观察 | 体验亮点 |
|---|---|---|
| 两点路线规划 | 设置深圳南山区的起终点，在地图上生成路线，并查看距离与预计时间 | 核心功能入口集中，用户容易找到规划结果 |
| 起终点交换 | 对 NS03 交换起终点，显示的路线距离从约 6.6 km 变为约 6.4 km | 一键重算；用户能够观察正、反方向路线差别 |
| 多途经点规划 | 在线地图成功加入途经点并生成连续路线 | 不局限于单一 A-B 两点规划 |
| 逐步导航指引 | 显示道路名称、转弯方向、分段距离等 | 将地图上的线路转换为可跟随的导航步骤 |
| 交通方式 | 操作汽车、骑行、步行选项并观察路线变化 | 不同出行方式可得到不同路线 |
| 地图样式 | 找到 Streets、Outdoors、Satellite 等底图选项 | 便于用户切换观察环境 |
| 单位、语言 | 看到 Metric/Imperial 与语言设置入口 | 照顾不同地区或阅读习惯 |
| 搜索反馈 | 输入不存在的地点时出现 `No results found` | 对无效搜索给出明确状态反馈 |
| 路线分享 | 生成分享链接，并实际重新打开 | 路线结果可被分享与复现 |
| GPX 导出 | 导出 `route.gpx` 并检查轨迹坐标 | 路线不仅是屏幕上的线，还可转为外部地理数据 |

#### 2.3.1 深圳路线规划：我们看到了什么

在南山区的三组路线中，我们记录了以下在线界面结果：

| 测试编号 | 路线距离（界面约数） | 预计时间（界面约数） |
|---|---:|---:|
| NS01 | 1.8 km | 2 分 30 秒 |
| NS02 | 2.4 km | 3 分 30 秒 |
| NS03 | 6.6 km | 8 分钟 |

这里记录的是**特定起终点、特定公开服务状态下的实际显示结果**，不是“深圳所有路线”的统计表现。对 NS03 交换方向后，路线距离约为 6.4 km；这提醒我们，在有向道路网络上，反向路线并不必然完全一致。

#### 2.3.2 导航步骤：不止给出路线几何

OSRM 在线演示将规划结果与逐步转向说明结合起来。我们可以在地图上观察路线，同时在说明区域阅读转弯方向、沿途道路名称和各段距离。

这一功能的设计价值在于：**路线计算输出的几何线条并不天然等于用户看得懂的导航信息**。将线路转化成分步骤说明，才能把“算法结果”变成“实际导航”。

要注意，逐步导航指引是**一条路线内部的操作说明**，不是后文 Table API 的“多个地点之间的时间矩阵”。

#### 2.3.3 路线结果可以分享、复用和导出

我们验证了 OSRM 的路线分享链接能被重新打开，也导出了 GPX 路线文件。此前检查的 GPX 文件含一条轨迹和 **59 个轨迹坐标点**，说明在线规划结果可以离开网页保存，用于其他软件显示或进一步处理。

这里的体验亮点不是“多了一个按钮”，而是**将一次性的交互结果转化为可复现、可交换的数据**。本次未验证 GPX 必然包含独立的逐步导航指令或所有途经点的原始语义。

### 2.4 核心接口功能：我们实际得到的结果

**（1）备选路线与路线成本选择**

针对同一组起终点，`Route` 服务返回两条可选路线：

| 方案 | 距离 | 预计行驶时间 |
|---|---:|---:|
| 路线 1 | 6,563.6 m | 447.2 s |
| 路线 2 | 6,293.7 m | 450.6 s |

这组结果显示：**距离更短的路线不一定预计用时更少**。导航引擎需要依据设定的道路权重或通行成本进行路线选择，而不是只比较几何长度。

**（2）最近道路匹配**

向 `Nearest` 服务输入一个深圳市道路附近坐标，并请求 3 个候选位置，接口返回 `code: Ok`、三个候选道路匹配结果以及相应的道路名称、位置和匹配距离；其中一个候选名称为“深南大道”。这说明道路位置匹配可以作为坐标输入与路网查询之间的基础环节。

**（3）多 OD 时间矩阵**

通过 `Table` 服务获取三个地点之间的行驶时间（单位：秒）：

| 出发地 \ 目的地 | A | B | C |
|---|---:|---:|---:|
| A | 0 | 447.2 | 512.1 |
| B | 451.8 | 0 | 198.1 |
| C | 577.8 | 342.8 | 0 |

该矩阵不仅能一次表达多组 OD 成本，还显示了道路通行的**方向性**：例如 A→C 与 C→A 的时间不同。需要注意，矩阵表示“不同地点之间的出行成本”，并不是逐步转弯导航指令。

**（4）多地点行程顺序优化**

在固定首尾地点的五地点案例中，原始输入顺序为 `A → D → C → B → E`，`Trip` 服务返回 `A → B → C → D → E`。采用同一组地点与首尾约束，另用 `Route` 服务按原始顺序计算，形成如下对照：

| 指标 | 按原始顺序 | Trip 调整后 | 本次变化 |
|---|---:|---:|---:|
| 路线距离 | 20,558.3 m | 17,740.8 m | 减少约 13.7% |
| 预计时间 | 1,550.9 s | 1,256.5 s | 减少约 19.0% |

这一结果验证了该案例中的**顺序调整与出行成本改善**，但不能推出对任意地点组合都能获得相同比例的收益，也不能证明启发式结果必然是全局最优。

### 2.5 路网调试与开发者可视化

OSRM 提供与路由数据相关的瓦片服务，其在线调试地图可用于观察道路网络及部分属性信息。在此前打开的步行模式调试地图中，能够观察到彩色路网、速度标注（例如 `4 km/h`、`5 km/h`）以及图例。

**设计亮点：** 将“给普通用户展示规划路线”和“给开发者检查道路网络”区分为两种视图，便于观察路网结构及已处理的属性数据。

需要注意：本次没有在该调试地图中验证 CH 节点收缩动画或捷径边绘制，不应将其写成已经存在并被验证的功能。

### 2.6 OSRM 的设计特点归纳

1. **预处理与查询分工清晰**：围绕高频路线查询组织后端计算流程。
2. **接口职责明确**：路线、道路吸附、矩阵、轨迹匹配和行程优化分为不同服务。
3. **兼顾用户功能与开发者工具**：既有简洁的在线路线演示，也有用于调试路网的工具。
4. **适合服务化集成**：以标准化请求和结构化结果对外提供能力。

## 3. Valhalla：动态成本、分层数据与多样化导航能力

### 3.1 分层瓦片化路网

Valhalla 的官方设计强调 **tiled hierarchical graph（分层瓦片化图）**：道路网络被组织为可分块访问、具有层级结构的数据，利于路由时读取和缓存所需区域的信息。

**设计亮点：** 有助于降低部分场景中的内存压力，并为区域数据、离线使用及局部更新提供工程基础。这里说的是架构设计目标，实际效果取决于数据、部署方式与应用环境。

### 3.2 模块化路径规划处理链

Valhalla 将位置匹配、路径搜索、成本计算和导航指引组织为不同模块。其官方架构中常见的职责分工为：

```text
请求输入
   ↓
Loki：输入位置与路网道路边关联
   ↓
Thor：路径搜索、矩阵、等时圈等计算
   ↕
Sif：运行时通行成本与道路偏好模型
   ↓
Odin：转向动作与文字/语音导航指引
   ↓
结构化导航结果
```

其中，**Thor** 的常规非时间依赖路径规划包括双向 A*；另有用于时间依赖场景的相应 A* 搜索及面向公交换乘的多模式算法。它并非在所有类型的请求中只使用一种 A* 算法。

**设计亮点：** 路径搜索与成本模型、导航指引生成分离，各模块关注不同职责，有利于支持多种出行方式与导航结果形式。

### 3.3 动态通行成本模型与多种路线偏好

Valhalla 使用**运行时动态成本（dynamic costing）**评估道路边和相关通行操作。除路线长度外，还可以根据交通方式、道路属性、时间条件及用户偏好影响路线计算。

在在线演示的 `Advanced Settings` 中，我们实际观察到以下设置入口：

| 设置类别 | 观察到的选项示例 |
|---|---|
| 车辆属性 | 宽度、高度、最高速度 |
| 道路偏好 | 高速公路、收费道路、渡轮 |
| 通行限制 | 道路封闭与访问限制等 |
| 路线成本 | 特殊道路和通行操作的成本相关参数 |
| 导航设置 | 导航语言等 |

**设计亮点：** 通过成本模型将不同用户需求转化为不同的路径选择条件；界面上则将常用功能与高级参数分层组织。


### 3.4 在线演示界面：主要功能和操作感受

与 OSRM 的简洁路线页面相比，本次体验中 Valhalla 在演示界面左侧直接组织了较多操作入口。我们没有把所有入口都逐一跑通，而是优先体验了**能够直接看见结果差异**的功能。

| 界面或设置 | 实际观察 |
|---|---|
| `Directions` | 在柏林生成了正常的路线，界面显示距离与预计时间 |
| 多路线展示 | 同时看到主路线及两条备选路线，分别提供距离和时间信息 |
| `Show Maneuvers` | 展开后可见独立的逐步转向指引卡片 |
| 路线显示开关 | 各路线卡片提供独立显示控制 |
| `Export` | 在路线卡片中看到导出操作 |
| 交通方式图标 | 可见自行车、步行、汽车、货车、公交等选项 |
| `Add Waypoint` | 提供增加途经点的操作入口 |
| `Optimize Route` | 提供路线优化入口 |
| `Isochrones` | 实际生成了 10 分钟可达范围的彩色区域 |
| `Tiles` | 可见瓦片相关功能入口 |
| `Advanced Settings` | 浏览车辆参数、道路偏好、成本与限制条件等设置项 |

**最直观的界面体验：** Valhalla 将“生成路线”“比较路线”“阅读导航步骤”“调整规划偏好”组织在同一演示应用内，用户无需自行阅读接口返回的 JSON 就能看到部分高级功能的实际效果。

### 3.5 多路线卡片与逐步导航指引

在 Valhalla 在线演示中，我们实际观察到**一条主路线与两条备选路线**，界面以独立卡片展示各路线的距离和预计时间，并提供路线显示控制、导航步骤和导出入口。

示例结果：

| 路线 | 距离 | 预计时间 |
|---|---:|---:|
| 主路线 | 0.4 km | 1 分 23 秒 |
| 备选路线 1 | 0.6 km | 2 分 44 秒 |
| 备选路线 2 | 0.8 km | 2 分 42 秒 |

此外，`Show Maneuvers` 可展开逐步导航指引，按顺序显示**行驶方向、道路名称、分段距离和预计时间**。从设计上看，Valhalla 将“路径计算结果”和“人类易读的导航说明”区分开来，再在界面中组织呈现。

#### 3.5.1 备选路线为什么值得单独展示

我们在柏林规划了一条短距离路线，演示界面不只显示一条线路，还同时列出了两条备选路线。各路线有自己的卡片、距离与时间信息，用户可以直观看出路线之间的差异，而不是面对一组不易理解的数字。

此次数据中，主路线 0.4 km / 1 分 23 秒；两条备选路线分别为 0.6 km / 2 分 44 秒和 0.8 km / 2 分 42 秒。由于这是短距离示例，不适合将结果推广为该系统所有路线的典型表现。

#### 3.5.2 逐步导航指引：把路由结果拆成驾驶动作

点击 `Show Maneuvers` 后，我们观察到卡片式的转向说明，例如：

| 展示的步骤 | 距离 | 预计时间 |
|---|---:|---:|
| 沿 Friedrichstraße 向南 | 129 m | 19 秒 |
| 左转进入 Anton-Wilhelm-Amo-Straße | 225 m | 56 秒 |
| 右转 | 7 m | 7 秒 |
| 到达目的地 | — | — |

从体验上看，每一步不仅有文字，还有与动作对应的方向信息，能帮助用户理解**现在走哪条路、接下来怎么转**。

**与时间矩阵的区别：** 导航指引按一条路线内部的先后动作展开；时间矩阵则比较多个地点组合之间的出行成本，两者不是同一个功能。

### 3.6 等时圈与可达范围可视化

`Isochrones` 用于表达**从某个位置出发，在给定时间或距离限制内可到达的区域**，与从 A 到 B 的路径计算不同。

本次在线演示中，已成功生成**柏林某位置的驾车 10 分钟等时圈**，地图以彩色范围展示可达区域，同时可以看到最大范围、时间间隔及边界概化等设置。

**设计亮点：** 将底层路网计算结果进一步组织为空间范围，扩展了导航引擎在交通可达性分析、区域服务覆盖等方向的用途。

### 3.7 高级设置体验：更丰富的个性化规划入口

本次特别查看了三组 `Advanced Settings` 页面。比起只选择起终点，这些选项让我们直观地认识到：成熟导航软件可以针对**车辆条件、道路类型和用户偏好**组织更细致的规划参数。

| 观察到的设置 | 面向什么需求 |
|---|---|
| 车辆宽度、车辆高度 | 特定车辆的尺寸条件 |
| 最高速度、速度类型 | 速度模型或行驶约束 |
| `Use Highways` | 偏好或回避高速公路 |
| `Use Tollways` | 偏好或回避收费道路 |
| `Use Ferries` | 渡轮使用偏好 |
| `Shortest` | 更偏向距离最短的规划选项 |
| 道路封闭、权限和路况相关设置 | 特殊通行约束 |
| 收费站、闸门、渡轮等成本项 | 细化通行代价 |
| 导航语言 | 调整指引的语言 |
| Server / Base URL | 切换服务端连接配置 |

**设计亮点有两层：**

1. **参数层面**：把不同车型、道路偏好和成本因素作为可配置条件，而不是假定所有用户都需要同一种路线。
2. **交互层面**：把这些专业参数放在高级设置里，普通用户仍然可以先使用简单的路线规划页面，不必在首页面对大量陌生选项。


### 3.8 多种服务能力与扩展性

根据 Valhalla 官方 API 文档，其能力还包括：

- `route`：多交通方式路径与导航指引；
- `optimized_route`：多地点访问顺序优化；
- `sources_to_targets`：时间与距离矩阵；
- `isochrone`：等时圈或等距离区域；
- `trace_route`、`trace_attributes`：轨迹地图匹配及相关道路属性；
- 高程查询等辅助服务。

这些能力说明 Valhalla 并不只提供“较复杂的演示界面”，也有相对完整的后端路由与空间分析服务。上述接口并非全部在本次调研中进行了直接调用测试。

### 3.9 Valhalla 的设计特点归纳

1. **瓦片化、分层化数据结构**：注重路网读取、内存和数据组织。
2. **搜索算法与动态成本分离**：支持不同交通方式、偏好与时间相关路线。
3. **导航结果分层生成**：先形成路径，再组织转向步骤与导航说明。
4. **空间分析与导航相结合**：除了路线，还提供矩阵、等时圈、轨迹匹配等服务。
5. **面向演示与使用的界面组织**：多路线卡片、详细导航步骤与高级设置比较直观。

下表不是两个引擎的完整功能清单，而是从本次**实际操作与截图**出发，筛选出最容易解释、最有代表性的功能。

| 项目 | 功能亮点 | 我们实际看到了什么 | 体验价值 |
|---|---|---|---|
| OSRM | 路线分享和 GPX 导出 | 生成分享链接、重新打开并检查导出的轨迹文件 | 规划结果可复用、可交换 |

| Valhalla | 等时圈 | 成功生成柏林驾车 10 分钟可达范围 | 将路线规划拓展为可达性空间表达 |

### 4.1 为什么这些功能具有代表性？

- **规划结果不仅要“算出来”，还要“看得懂”**：OSRM 的转向指引、Valhalla 的路线卡片和逐步导航展示，强调结果解释。
- **规划结果不仅要“显示”，还要“复用”**：路线分享、GPX 导出和结构化接口，为后续处理提供入口。
- **路线规划不仅是 A→B 的单点需求**：多 OD 矩阵与多地点优化，说明导航引擎可支持批量分析和复杂行程组织。
- **地图不仅能画一条线**：路网调试地图展示道路属性，等时圈展示可达区域，两者代表两种不同的可视化用途。
- **功能丰富不等于界面必须复杂**：Valhalla 将高级设置与普通操作分层，OSRM 则保持演示地图相对精简。

## 5. 两个引擎的设计侧重点对照

| 比较维度 | OSRM | Valhalla |
|---|---|---|
| 核心定位 | 高性能道路路径规划与路由服务 | 多交通方式路径规划及路网分析服务 |
| 代表性路径计算 | CH、MLD 两类后端流水线 | A* 系列算法、分层路网及动态成本 |
| 路网数据组织 | 通过预处理构建查询结构 | 分层瓦片化图结构 |
| 成本模型特点 | 在数据处理与查询流程中组织道路权重；MLD 支持定制阶段 | 在运行时使用动态成本模型 |
| 服务能力 | 路线、道路匹配、矩阵、轨迹匹配、行程优化、调试瓦片 | 路线、矩阵、行程优化、轨迹匹配、等时圈、高程等 |
| 本次较突出体验 | 多点优化案例、矩阵与道路匹配接口、调试地图 | 备选路线卡片、逐步导航、高级设置、等时圈 |
| 在线演示风格 | 以基础路线规划和地图操作为主 | 功能参数和空间分析入口更集中、更丰富 |

**比较边界：** 上表意在概括设计侧重点，而不是“有/无功能”排行榜。例如，Valhalla 同样具有矩阵与优化路线服务；OSRM 的公开演示界面没有等时圈入口，也不能据此断言所有 OSRM 相关应用都无法实现可达范围分析。

## 6. 结论

OSRM 和 Valhalla 展现了成熟开源导航引擎的两种具有代表性的工程设计思路。

**OSRM** 突出的亮点是**高性能路由查询组织方式与清晰的服务接口**：通过 CH/MLD 等查询加速流程，将基础路径规划拓展为可复用的道路匹配、矩阵计算、行程优化和路网调试能力。

**Valhalla** 突出的亮点是**分层瓦片路网、动态成本模型以及丰富的导航与空间分析能力**：将道路位置关联、路径搜索、成本计算和导航指引分离，并通过路线卡片、高级设置和等时圈等界面形式呈现较完整的功能链条。

两者共同说明，成熟导航系统的价值不仅来自单一路径算法，还来自**路网数据质量、模块化架构、可扩展接口、合理的成本模型及清晰的结果呈现**。以上判断基于官方项目说明和本次有限的公开服务与界面测试，不代表完整的性能或质量测评。
