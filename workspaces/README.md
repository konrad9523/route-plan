## 四个地方要分清（最容易搞混的地方）

```text
① 本机草稿区（不上传，只有自己看得到）
   个人工作区/<你的角色>/
   放：收件箱、临时实验、日报、未整理的笔记、个人工具
   每次克隆仓库后自己建，已写进 .gitignore

② 自己 Fork 的阶段留痕区（上传到自己的 Fork，不提 PR）
   member_workspaces/<你的角色>/    分支：workspace/<成员>
   放：阶段记录、草稿、实验过程
   作用：留痕，让队友知道你在做什么 —— 注意 Fork 不是私密空间

③ 角色成果区（上传，全组可见）  ← 你正在看的这里
   workspaces/<角色>/              分支：feature/<成员>-<任务> + PR
   放：成果索引、结论、数据表、截图、说明
   作用：让其他四个人快速看到"这个角色做出了什么"

④ 正式交付位置（上传，全组维护）
   src/path_planning/  api/  web/  tests/  tools/  docs/  data/
   放：项目正式的代码、文档、数据、测试
   经过 PR 审查，是最终交付物
```

**流向是单向的**：

```text
本机草稿区 ──整理──► Fork 阶段留痕区 ──挑选──► 角色成果区 / 正式交付位置
```

> **② 与 ③ 必须走不同分支**：`workspace/<成员>` 只推自己 Fork、不提 PR；
> `feature/<成员>-<任务>` 从 `upstream/main` 建、只装要交付的文件。
> 原因与命令见 [`团队协作与项目管理原则.md`](../docs/operations/团队协作与项目管理原则.md) **§2.4.1**——
> **`.gitignore` 挡不住已提交的文件**，草稿一旦提交就会跟着 PR 一起上去。

## 一条防重复规则

**同一个文件只能有一个正式位置。**

| 放这里 ✅ | 不放这里 ❌ |
|---|---|
| 成果索引（README） | 代码副本（代码在 `path_planning/`） |
| 数据表格、结论 | 正式文档副本（文档在 `docs/`） |
| 截图、说明材料 | 大体积原始数据（数据在 `data/`） |

**需要引用代码或文档时，用相对链接指过去，不要复制一份。**

判断方法：**"其他角色需要读代码才能看懂吗？"**
需要 → 放正式目录；不需要 → 放这里。

## 每个目录里有什么

每个角色目录都有一份 `README.md`，回答三个问题：

1. **我这个角色负责什么**
2. **我的成果放在哪里**（逐项列出实际路径）
3. **当前状态**：已完成什么、进行中什么、还没开始什么

**建议从"当前状态"表开始看**——那是了解进度最快的方式。

## 怎么往这里加成果

1. 在**本机草稿区**做实验和整理
2. 判断成果类型：
   - **代码 / 数据 / 正式文档** → 提交到正式位置
   - **索引 / 结论 / 说明 / 截图** → 提交到这里
3. 更新对应 `README.md` 的"当前状态"表
4. 走分支 + PR，请至少一位非作者审查
5. 在 `CHANGELOG.md` 记一条

> ⚠️ **不要用 `git add .` 一把提交**。逐项确认路径，
> 不要把本机草稿、缓存、临时文件带进仓库。
