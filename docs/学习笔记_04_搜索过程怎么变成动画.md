# 第 1 课：算法算完就没了，动画没东西可播

## ① 问题

现在跑一次查询：

```python
result = plan_route(graph, src, dst, algorithm="astar")
print(result.expanded_states)     # 768 —— 摸了 768 个节点
```

**你只知道"摸了 768 个"，但不知道"按什么顺序摸的"。**

而动画需要的是**过程**：第 1 步摸了哪、第 2 步摸了哪……最后路径才浮现出来。

**所以必须让算法在搜索时"记笔记"。**

## ② 记什么

最直接的想法：**每发生一件事就记一条**。

```python
[{"step": 0, "kind": "pop",      "node": 1,  "cost": 0.0},
 {"step": 0, "kind": "discover", "node": 2,  "cost": 100.0},
 {"step": 0, "kind": "discover", "node": 4,  "cost": 900.0},
 {"step": 1, "kind": "pop",      "node": 2,  "cost": 100.0},
 ...]
```

**这个做法能work，但会撞墙。** 先看实测数据（552 节点真实路网）：

| 场景 | 扩展事件数 | 这种格式的 JSON |
|---|---|---|
| 单次查询（shortest） | 98 | 小 |
| 单次查询（fastest） | 768 | 中 |
| **最长的一次查询** | **1381** | **39 KB** |
| **外推到 10 万节点** | **约 25 万** | **约 7 MB** ❌ |

**7 MB 塞给浏览器是不能接受的**——页面会卡死。

## ③ 停下来自问

> **问**：为什么不能把每个事件都塞给前端？
> **答**：因为事件数随图规模线性增长，10 万节点时约 25 万个事件、约 7 MB，浏览器扛不住。

# 第 2 课：动画真正需要的信息其实很少

## ① 想清楚"边界"到底是什么

先问自己：**要画出"边界节点"，需要知道每个节点的什么信息？**

朴素想法：需要知道每个节点"什么时候被发现的"。

**但仔细想想**：

```text
某一步的 边界 = 到这一步为止"已被发现的节点"  −  "已被确定的节点"
```

因为一个节点只要被发现了，就只有两种命运：

* 还在队列里等 → **边界**
* 已经被取出 → **已访问**

**没有第三种。**

## ② 于是只需要两个序列

| 序列 | 长度 |
|---|---|
| `pop_order`：第 k 步取出了哪个节点 | = 扩展事件数 |
| `discovered_order`：按发现顺序排列的节点 | = 被发现的节点数 |

**两个序列的长度都不超过节点数，而且不随边数增长。**

再配一个平行数组 `discovered_after_steps` 记录"从第几步开始算已发现"，
就能重建任意一帧。

## ③ 这个发现省了多少

| 方案 | 552 节点最长查询 | 10 万节点（推算） |
|---|---|---|
| 事件字典列表 | 39 KB | ~7 MB |
| **序列数组** | **39 KB** | ~7 MB |

**咦，怎么没省？** 因为长度都是"事件数"级别。

**真正的省法在下一课**——降采样。

# 第 3 课：踩过的三个坑（都是实测发现的）

这一课是这篇笔记最有价值的部分。**这三个坑我都真的踩了，而且都是被测试抓出来的。**

## ① 坑一：把节点 ID 存成了字典的键

我第一版是这样设计的：

```python
found_at: dict[int, int]       # {节点: 步号}
settled_cost: dict[int, float] # {节点: 代价}
```

序列化成 JSON 时，字典的**键和值各存一次**，于是节点 ID 被存了两遍。

**实测结果**：

```text
紧凑格式 = 5.0 KB
朴素格式 = 5.8 KB
压缩比   = 1.16x      ← 几乎没省
```

**更糟的是**，我第一版甚至出现了"压缩后反而更大"：

```text
紧凑 = 4.1 KB
朴素 = 3.2 KB
压缩比 = 0.79x        ← 负优化！
```

**修正**：改成"顺序表 + 平行数组"，**永远不出现以节点 ID 为键的字典**。
修正后：

```text
紧凑 = 3.8 KB
朴素 = 5.8 KB
压缩比 = 1.53x        ← 现在真的省了
```

而且我把这条约束写成了**测试**：

```python
def test_compact_contains_no_dict_keyed_by_node(self):
    """体积关键：不出现以节点 ID 为键的字典。"""
    compact = result.trace.to_compact()
    for key, value in compact.items():
        if key in {"algorithm", "preference", "stats"}:
            continue
        self.assertIsInstance(value, list, f"{key} 应该是数组，而不是字典")
```

> **经验**：设计"紧凑格式"时，**字典是敌人**。能用平行数组的地方就用平行数组。

## ② 坑二：同一节点被重复记录

每次松弛一条边，我都调了一次"记录发现"：

```python
recorder.record_discover(edge.to_node)
```

**但一个节点会被松弛很多次**（每次找到更短的路径就会重新松弛）。

测试直接抓出来：

```text
AssertionError: 73 != 152
       ↑唯一节点数   ↑记录条数
```

**152 条记录里只有 73 个不同的节点**——重复了一倍多，白占体积。

**修正**：记录器内部用集合去重。

```python
def record_discover(self, node_id: int) -> None:
    if node_id in self._discovered:      # ← 已经记过了
        return
    self._discovered.add(node_id)
    self.trace.discovered_order.append(node_id)
    ...
```

**修正后效果**（最长那次查询）：

```text
发现事件数  1387  →  543
JSON 体积   53.5 KB  →  39.3 KB
```

> **经验**：记录"首次发生的事件"时，**一定要想清楚会不会重复触发**。

## ③ 坑三：边界的时序搞错了两次

这个坑最隐蔽，我**连着错两次**。

**第一次**：我写的判据是 `after < step`。结果边界**延迟了整整一步**：

```text
discovered_after_steps = [0, 1, 1, 2]     ← 节点 2 和 4 在第 1 步被发现
step=1  已访问=[1]  边界=[]               ← 但它们没出现在边界里！
```

**第二次**：我干脆把时间判断去掉，结果 `step=0`（还没开始搜索）时边界就装满了：

```text
step=0  已访问=[]  边界=[1, 2, 4, 3]      ← 开始之前怎么会有边界？
```

**根因是"步号"的语义没定义清楚。** 正确的表达是：

> 节点是在**处理第 k 步的过程中**被松弛出来的。
> 所以"站在第 k 步"时，这次发现**已经发生了**。

因此记录时应存 `已完成的 pop 次数 + 1`，判据是 `after <= step`：

```python
# 记录时
self.trace.discovered_after_steps.append(self._steps_done + 1)

# 重建时
frontier = [node for node, after in zip(...)
            if after <= step and node not in visited_set]
```

**最终正确的时序**（4 节点链，可对照）：

```text
pop_order              = [1, 2, 3, 4]
discovered_order       = [1, 2, 4, 3]
discovered_after_steps = [1, 2, 2, 3]

step=0  已访问=[]        边界=[]       ← 正确：还没开始
step=1  已访问=[1]       边界=[]       ← 正确：刚取出起点，还没处理出边
step=2  已访问=[1,2]     边界=[4]      ← 正确：起点处理完，邻居进边界
step=3  已访问=[1,2,3]   边界=[4]
step=4  已访问=[1,2,3,4] 边界=[]       ← 正确：全部取出
```

> **经验**：凡是涉及"时间/顺序"的字段，**必须先写出语义定义，再写代码**。
> 我这两次错误都不是手误，而是**语义没想清楚**。

## ④ 停下来自问

> **问**：`step=1` 时边界为什么是空的？
> **答**：因为边界里的节点是在"处理起点"的过程中才被发现的，那要到第 2 步才反映出来。这是真实时序。

> **问**：为什么测试能抓出这些坑？
> **答**：因为我写了"边界与已访问不能重叠"、"末帧边界必须清空"、"step=0 必须为空"这类**不变量断言**。

# 第 4 课：降采样——大图必须用

## ① 为什么需要

即使压缩到 39 KB，10 万节点仍会到约 7 MB（推算）。**必须能"少记一些"**。

## ② 怎么降

```python
trace = result.trace.downsample(max_steps=500)
```

**行为**：按固定间隔抽取主时间轴，**保留首尾**。

**实测效果**（最长那次查询，1381 步）：

| 限制 | 步数 | JSON |
|---|---|---|
| 不限制 | 1381 | 39.3 KB |
| 500 | 691 | 24.6 KB |
| 200 | 231 | 14.8 KB |
| 50 | 53 | 11.0 KB |

## ③ 一个诚实说明

降到 50 步后体积仍有 11 KB，**因为 `discovered_order`（发现顺序表）没有压缩**——
边界重建需要完整的发现信息。

**当前规模无所谓**；如果将来上 10 万节点，需要给发现事件也加降采样。
我把这条写进了接口文档的"已知限制"。

> **经验**：优化到哪一步、还剩什么瓶颈，**要写下来**。不写，下次就忘了。
> （我自己就在这份笔记里纠正了两个之前写错的数字。）

# 第 5 课：性能——开关必须是"真开关"

## ① 设计原则

`trace` 默认 **关闭**。因为：

* 批量性能测试要跑几千次查询，**不能为可视化付代价**；
* 但搜索循环是热路径，加判断也有成本。

**做法**：用一个"空对象"记录器。

```python
class TraceRecorder:
    def record_pop(self, node_id, cost, via_edge=None):
        if not self.enabled:      # ← 关闭时立刻返回
            return
        ...
```

搜索循环里无条件调用，**关闭时每次调用只是"进来又出去"**。

## ② 实测开销

**测量方式**很重要：600 组查询、**交错跑 7 轮取中位数**。

> 我第一次测的时候只跑了 400 次、单轮，得到 "+4.4%"，第二次得到 "+10.2%"，
> 第三次得到 "+84%"——**波动这么大，说明测法有问题**（系统噪声、顺序效应）。
> 交错轮次 + 中位数之后才稳定下来。

| 偏好 | trace 关闭 | trace 开启 | 绝对增加 | 相对 |
|---|---|---|---|---|
| fastest | 4.387 ms | 5.064 ms | **+0.677 ms** | +15.4% |
| shortest | 1.496 ms | 2.170 ms | **+0.674 ms** | +45.1% |

**关键读法**：绝对增量几乎相同（0.677 / 0.674），说明**开销按事件数线性**，与偏好无关。
相对百分比差得多，只是因为分母不同。

## ③ 关闭时的成本

我专门测了"空调用"本身：

```text
每次空调用  = 0.0281 微秒
每查询调用  = 438 次
合计        = 0.0123 毫秒
占单次查询  = 0.91%
```

**0.91%，可以忽略。** 所以不需要为它增加复杂度（比如把调用点改成 `if trace:`）。

## ④ 结论

| 场景 | 用不用 trace |
|---|---|
| 批量基准测试 | ❌ **不要**（会让数字虚高 15–45%） |
| 交互演示 / 可视化 | ✅ 用（+0.7 ms，人感觉不到） |
| 对比报告的数据采集 | ❌ 不要 |

## ⑤ 停下来自问

> **问**：为什么基准测试绝不能开 trace？
> **答**：会让耗时虚高 15–45%，污染性能数据。

> **问**：为什么不用 `if trace:` 包住调用点来省那 0.91%？
> **答**：不值得——增加代码分支和复杂度，换来的收益不到 1%。

# 第 6 课：这套接口怎么复用到作业 2 和 3

## ① 作业 2 的 CH 预处理动画

CH 预处理记录的是**图结构变化**（收缩了谁、加了哪些捷径边），
**不是搜索过程**。所以**不能硬塞进 `SearchTrace`**。

**但可以复用设计模式**：

```python
@dataclass
class ContractionTrace:
    contraction_order: list[int]                    # 第 k 步收缩了哪个节点
    shortcut_added: list[tuple[int, int, int]]      # (from, to, mid)
    nodes_contracted_after_step: list[int]
```

**共享的是"主时间轴 + 平行数组"这个模式，不是同一个类。**

## ② 作业 3 的路径动画

路径动画**不需要 SearchTrace**，只需要：

* `result.geometry`（折线坐标）
* `result.edge_ids` / `node_ids`

**建议单独做一个 `animate_along(result, t)`**，与搜索过程解耦。

## ③ 三处共用的渲染约定

| 状态 | 颜色 | 数据来源 |
|---|---|---|
| 已访问 | 冷色（灰/蓝） | `state["visited"]` |
| 边界 | 暖色（橙/红） | `state["frontier"]` |
| 最终路径 | 高亮粗线 | `state["path"]` |

**统一约定**，这样三处动画看起来是一套系统。

## ③ 技术选型建议

| 组件 | 建议 | 理由 |
|---|---|---|
| 后端 | **FastAPI** | 已装，无额外依赖 |
| 前端地图 | **Leaflet** | 单文件引入，比 MapLibre 简单；552 节点用不着矢量瓦片 |
| 数据格式 | `trace.to_compact()` → JSON | 已设计好 |
| 渲染分层 | 三个图层：已访问 / 边界 / 路径 | 对应 `state_at` 的三个返回值 |

**关键**：前端**只消费 JSON**，不 import Python 任何东西。
