```powershell

```

服务只绑定本机回环地址。启动脚本检查 552 个节点、1400 条有向边的校园路网；API 路线请求已经实测通过。若要直接调用，当前测试起终点为 `9626752368` → `11896284285`，例如最短距离请求：

```powershell
$body = @{ source=9626752368; target=11896284285; algorithm='astar'; preference='shortest' } | ConvertTo-Json
Invoke-RestMethod 'http://127.0.0.1:8077/api/route' -Method Post -ContentType 'application/json' -Body $body
```

## 开源全链路演示：GraphHopper + GraphHopper Maps

在项目根目录打开 PowerShell，一键启动武汉校区附近的 OSM 路网后端和地图前端：

```powershell
& .\references\navigation-open-source\tools\start-graphhopper-cug.ps1
```

浏览器地图：<http://127.0.0.1:3000/>；GraphHopper API：<http://127.0.0.1:8989/>；路网/profile 信息：<http://127.0.0.1:8989/info>。结束时运行：

```powershell
& .\references\navigation-open-source\tools\stop-graphhopper-cug.ps1
```

启动后可重复执行三种 profile 的 API 验收用例，并生成 JSON 结果：

```powershell
& .\references\navigation-open-source\tools\verify-graphhopper-cug.ps1
```

结果文件：[`graphhopper_cug_profiles.json`](../../references/navigation-open-source/cases/output/graphhopper_cug_profiles.json)。

前端和后端都只绑定本机；前端地址检索关闭，避免依赖外部 API Key，路线服务本身完全在本机。OSM 底图瓦片由 OpenStreetMap 在线提供，因此看底图需要网络；地图保留 © OpenStreetMap contributors 署名。首次运行会用本地 OSM XML 导入并建立 GraphHopper 图缓存，之后启动直接加载缓存。

当前 OSM 小区域快照于 2026-09-26 从 Overpass API 获取，范围约为南北纬 30.505–30.545、东西经 114.371–114.417；XML 有 11,612 个节点、1,768 条 highway 道路。GraphHopper 导入后形成 3,144 个路网节点、4,180 条边，实际 bbox 约 114.335–114.439°E、30.500–30.585°N。快照不包含高程，因此这次可验证普通道路规划，但不能代表 DEM 应急避险。

可用同一组起终点比较 car、foot、bike 三个交通 profile（这是道路基础速度模型估计，不含实时交通）：`30.516,114.375` → `30.538,114.406`。本轮实测 car 为约 6.64 km / 413 秒，foot 为约 5.38 km / 3,875 秒，bike 为约 6.12 km / 1,225 秒；三者都返回有效路线。示例请求：

```powershell
$start = '30.516,114.375'
$end = '30.538,114.406'
$profile = 'car' # 也可以是 foot 或 bike
$uri = "http://127.0.0.1:8989/route?point=$start&point=$end&profile=$profile&calc_points=true&points_encoded=false&instructions=true"
Invoke-RestMethod $uri
```

GraphHopper Maps 的本地生产 bundle 和 150 项 Jest 测试均已通过；启动脚本进一步实测了前后端健康状态和跨域访问。脚本可重复运行：检测到正确服务时会复用，不会重复占用端口。OSM 数据使用需遵守 ODbL，并保留来源说明；参见 [Overpass API 使用文档](https://wiki.openstreetmap.org/wiki/Overpass_API) 和 [OpenStreetMap 法律与署名说明](https://wiki.openstreetmap.org/wiki/Legal_FAQ)。

## OSRM Windows 原生编译与 CUG 路线 API

OSRM Backend 已在本机 Visual Studio 2022 上完成 Release 编译，使用仓库自带 vcpkg manifest 安装的依赖、`x64-windows-static-md` triplet 和 OSRM 自带的 MLD（Multi-Level Dijkstra）算法。第一次配置/编译耗时较长，依赖归档缓存和编译目录会留在本机；以后源码或依赖没有变化时可增量复用。

完整流程（从源码构建到可请求服务）如下：

```powershell
# 仅源码变更/首次准备时需要：配置依赖并编译 Release
& .\references\navigation-open-source\tools\build-osrm-vs2022.ps1 -Build

# 从已下载的 CUG 附近 OSM XML 生成 OSRM 图、MLD 分区和权重
& .\references\navigation-open-source\tools\prepare-osrm-cug.ps1

# 启动本机 API，默认 http://127.0.0.1:5000；重复执行会复用同一数据服务
& .\references\navigation-open-source\tools\start-osrm-cug.ps1

# 验收 Route 正反向、Nearest 道路吸附、Table OD 矩阵
& .\references\navigation-open-source\tools\verify-osrm-cug.ps1

# 不使用时停止由本脚本管理的 OSRM 进程
& .\references\navigation-open-source\tools\stop-osrm-cug.ps1
```

验收结果在 [`osrm_cug_api.json`](../../references/navigation-open-source/cases/output/osrm_cug_api.json)。本轮实测：正向驾车路线 6,628.6 m / 466.7 s、9 个导航步骤；反向 5,908.7 m / 473.6 s、8 步；Nearest 将查询点吸附到距离 82.4 m 的道路；Table 返回 2×2 距离/时间矩阵。OSRM 的 URL 坐标顺序是 `longitude,latitude`，和 GraphHopper demo 中常见的 `latitude,longitude` 输入表达不同，调用时尤其要留意。

OSRM 当前准备的是 `car.lua`，所以这次只验证驾车路网与 API。步行/骑行需要分别用相应 Lua profile 重新 `osrm-extract` 并生成各自的数据集；OSRM 不是带地图 UI 的完整导航 App，这个 demo 也没有接上 OSRM Frontend。它适合学习高性能 C++ 路由服务、OSM 导入、MLD 预处理、HTTP Route/Nearest/Table 接口；地图渲染和跨 profile 展示仍由 GraphHopper + GraphHopper Maps 演示。

停止脚本只会终止路径、可执行文件和端口都匹配的 OSRM 进程。如果服务是从提升权限的终端启动的，停止时也需要使用同等权限；无法确认进程归属时脚本会拒绝终止。

## Valhalla Windows 核心引擎构建

Valhalla 已用 VS 2022 / CMake 完成 Release 核心构建，并已把 CUG 附近 OSM XML 转成 PBF、生成 tiles、运行了三种交通方式的真实路线。首次配置前需要将固定版本的 Git 子模块补齐；本机 Git for Windows 的 shell 工具不在默认 `PATH`，所以当前机器使用下面的准备命令：

```powershell
$source = '.\references\navigation-open-source\projects\Valhalla'
$env:PATH = 'C:\miniconda\Git\usr\bin;C:\miniconda\Git\mingw64\bin;C:\miniconda\Git\cmd;' + $env:PATH
$env:GIT_EXEC_PATH = 'C:\miniconda\Git\mingw64\libexec\git-core'
git -C $source submodule update --init --recursive
& .\references\navigation-open-source\tools\build-valhalla-vs2022.ps1 -MaxDownloadRetries 100 -Build
```

构建脚本保留 vcpkg 哈希校验，通过 curl 缓存被本机代理阻断的依赖源包；使用短 build 路径避免 MSVC 路径限制；打开 UTF-8 编译；只给 pkg-config 暴露 Release 库目录，避免把 Debug 静态库带入 Release 链接。脚本根据 Valhalla 自己的 Windows 指引关闭 `ENABLE_SERVICES`：核心库、路由引擎、`valhalla_build_tiles` 等数据工具可编译，但独立 HTTP 服务依赖的 `prime_server` 在该平台未受支持。关键二进制 `valhalla_build_tiles.exe --help/--version`、`valhalla_build_admins.exe --help/--version` 和 `valhalla_service.exe --help` 均通过。

为减轻 D 盘占用，Valhalla 32.9 GB 的构建目录已迁至 `F:\route plan\.valhalla-build-vs2022`；D 盘原路径保留 junction，现有构建和路线脚本无需改路径。复制逐项校验后，经 junction 重跑了三种路线，再清理 D 盘旧副本；D 盘可用空间增加约 26 GB。OSRM 的 12.45 GB 构建目录当时有运行中的 `osrm-routed` 进程，因此暂留 D 盘以避免中断该 API；参考源码与数据也没有搬动。

可重复准备和验收 CUG 数据：

```powershell
& .\references\navigation-open-source\tools\build-valhalla-cug.ps1
& .\references\navigation-open-source\tools\verify-valhalla-cug.ps1
```

第一条会在缺少时安装固定版本的 `pyosmium`，流式转换 OSM XML→PBF，再依次构建 admins、routing tiles 和 tile archive；第二条通过 `valhalla_service config.json route <JSON>` 的本地 action 模式实测 auto、pedestrian、bicycle 三种路线，并更新 [`valhalla_cug_routes.json`](../../references/navigation-open-source/cases/output/valhalla_cug_routes.json)。当前结果分别约为驾车 6.644 km/7.24 分钟、步行 5.381 km/64.49 分钟、骑行 6.140 km/21.91 分钟，都返回逐步 maneuvers。构建日志得到 3,038 个图节点和 8,092 条有向边。它不是 HTTP 服务；没有初始化实时交通数据。这个小区域快照没有行政边界关系，`admins.sqlite` 里为 0 个 admin polygon，所以可用于校园级路由学习，不代表完整行政区/跨境数据生产。参见仓库内 [Valhalla 构建说明](../../references/navigation-open-source/projects/Valhalla/docs/docs/start/building.md) 和 [Valhalla 数据构建架构说明](../../references/navigation-open-source/projects/Valhalla/docs/docs/contributing/architecture/mjolnir/index.md)。

## 如何理解这些结果

目前有四套可运行的路径规划入口：课程项目自己的 Python 原型（校园 GraphML）、GraphHopper + GraphHopper Maps（武汉校区附近 OSM 数据）、OSRM Backend 的 CUG 驾车 HTTP API，以及 Valhalla 的 CUG 本地 route action。GraphHopper 串起道路数据→图导入/缓存→路线 API→地图前端，并支持 car/foot/bike；OSRM 串起 OSM→C++ extract→MLD partition/customize→HTTP Route/Nearest/Table；Valhalla 则提供 OSM PBF→admins/tiles/archive→多 costing route 的源码实践。Valhalla 在此 Windows 构建中仍没有可用 HTTP 服务。OSRM Frontend、MapLibre 等其他仓库仍是各自源码/模块的构建验证，没有与这些演示合并成同一个导航栈。

这还不是完整车载/手机导航：没有地址地理编码、实时定位/地图匹配、语音播报、实时交通或 DEM 应急代价；应急场景还需高程栅格与独立危险/封路图层。Valhalla Windows 核心和 CUG 本地路线 action 已就绪，但官方构建说明将 `prime_server` HTTP 服务列为不支持 Windows。Organic Maps 仍未构建：本机缺 SDK/NDK，F 盘报告的可用空间看起来足够，但我没有写入工作区授权范围外的磁盘，也没有替用户接受 Android SDK 许可证。要继续这项构建，需要明确允许把大型 Android SDK/NDK 装到 F 盘，并由用户确认许可；官方构建指南还要求准备至少 30 GB 空间。OSRM Backend 已有本地可用的驾车 API，GraphHopper + Maps 仍是最完整的可视化学习链路。路径规划组可从这些源码和开发者文档对照路网建模、MLD/A*、代价配置与 API，再将学到的图建模和约束规划移植回课程项目。
