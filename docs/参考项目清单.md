## 0. 先看这里：初期到底需不需要下载外部项目

**结论：不需要。第一个阶段（Dijkstra + A* + 可视化）只看你们自己的仓库就够。**

### 为什么

你们仓库里已经有一份**完整可跑、真实数据、有测试**的学习材料，比任何外部项目都更适合入门：

| 你们已有什么 | 在哪 | 它覆盖了链路里的哪一环 |
|---|---|---|

| 路网数据是怎么来的（代码） | `learning_osmnx_networkx/route_demo.py` | ① → ② 数据获取与建模 |
| 有向图模型 | `path_planning/models.py` | ② 图结构 |
| 代价模型（权重） | `path_planning/costs.py` | ③ 权重 |
| Dijkstra + A* | `path_planning/router.py` | ④ 算法 |
| 7 个自动化测试 | `tests/test_router.py` | ⑦ 验证 |
| 静态地图出图 | `route_demo.py` 的 `save_map()` | ⑥ 可视化 |
| 入门教程 | `docs/学习笔记_01_从零读懂内核.md` | 全部 |

**这条链已经闭合了。** 你现在缺的不是资料，是把这 440 行代码真正读懂。

### 那外部项目什么时候用

```text
读懂自己代码（现在）        →  不用外部项目
```

**一句话**：外部项目是"字典"，不是"教材"。别抱着字典学认字。

## 4. RoutingKit 阅读顺序（做 CH 时按此顺序）

克隆下来后**不要从头翻目录**，按这个顺序读：

| 顺序 | 文件 | 看什么 | 对应你们的任务 |
|---|---|---|---|
| 1 | `doc/ContractionHierarchy.md` | 整体流程；**"收缩顺序可复用"**那一段 | 想清 CH 与动态权重的矛盾 |
| 2 | `src/contraction_hierarchy.cpp` → `estimate_node_importance()` | 节点重要性公式（level + 新增边数/删除边数 + 跳数） | 节点重要性排序 |
| 3 | 同文件 → `contract_node()` | 怎么加捷径边、witness search 怎么调 | 节点收缩 |
| 4 | 同文件 → `ContractionHierarchyQuery::run()` | **双向搜索的正确终止条件**（队列顶 ≥ 当前最优才停） | CH 查询 |
| 5 | 同文件 → `unpack_forward_arc()` / `unpack_backward_arc()` | 捷径边用"两条弧"表示、递归解压 | 捷径解压 |
| 6 | `include/routingkit/contraction_hierarchy.h` | 数据结构：`Side` 结构、`rank` / `order` | CH 数据结构设计 |
| 7 | `include/routingkit/id_queue.h` | 工业级优先队列怎么处理等代价平局 | 解决我们的堆崩溃问题 |
| 8 | `doc/CustomizableContractionHierarchy.md` | **只读概念，不读代码**——"换权重不重排序"的正规方案 | CH 与交通共存的长期方案 |

### 三个已确认的关键结论（可直接引用）

1. **收缩顺序可复用**：文档明确写 *"two graphs that have similar arcs can have very similar contraction orders"*，并提供 `build_given_order()` / `build_given_rank()`。**含义**：交通权重变化时不必重算顺序，只需用现成顺序重建索引。
2. **双向查询终止条件**：`forward_queue.peek().key >= shortest_path_length` 且反向同理，两者都满足才停。**不是**"两个方向访问过同一节点就停"。
3. **捷径边不存中间节点列表**，而是用 `is_shortcut_an_original_arc` + 两个弧 ID 表示，解压时递归。**注意**：`mid_node` 字段只在内部的 `ContractionHierarchyExtraInfo` 里，公开结构中没有——如果你们要展示"捷径经过哪些节点"，需要自己额外存。

## 5. 下载方式

### 方式一：ZIP 直链（不用装 git）

```
https://github.com/用户/仓库/archive/refs/heads/master.zip
https://github.com/用户/仓库/archive/refs/heads/main.zip
```

不同项目默认分支名不同（`master` 或 `main`），两个都试一下。例如：

```
https://github.com/RoutingKit/RoutingKit/archive/refs/heads/master.zip
https://github.com/Project-OSRM/osrm-backend/archive/refs/heads/master.zip
```

### 方式二：git clone（体积可控）

```powershell
cd D:\pycharm\projects\route_plan

git clone --depth 1 https://github.com/RoutingKit/RoutingKit.git references/RoutingKit
git clone --depth 1 https://github.com/networkx/networkx.git references/networkx
```

**说明**：

- `--depth 1` 只拉最新一次提交，不要完整历史，**体积能小十倍以上**；
- `references/` 目录已加入 `.gitignore`，克隆进去**不会污染项目版本库**；
- 建议**不要**完整克隆 Valhalla / SUMO / GraphHopper，它们体积巨大且初期用不上，需要时看单个文件即可。

## 6. 三个必须提醒的坑

### 坑 1：这些引擎下下来**也跑不起来**

Valhalla / OSRM / GraphHopper 需要 C++ 工具链或 Java + Maven，还要准备 PBF 数据并跑预处理（几十分钟到几小时）。

**它们对你们的价值是"读源码和读文档"，不是"运行"。** 别把时间花在编译上。

能直接 `pip install` 用的只有 **OSMnx**、**scgraph**、**NetworkX**。

### 坑 2：`--depth 1` / ZIP / 完整 clone 的区别

| 方式 | 体积 | 有历史？ | 依赖 git？ |
|---|---|---|---|
| `--depth 1` | 小 | ❌ | ✅ |
| ZIP | 中 | ❌ | ❌ |
| 完整 clone | 大（可能几百 MB） | ✅ | ✅ |

对学习用途，**前两种都够**，你们几乎不需要看历史提交。

### 坑 3：不要把参考项目当成"现成答案"抄

你们的交付物要求**自研四种算法 + 算法实验报告**。抄来的实现：
- 讲不清原理，答辩必被问穿；
- 无法和 Dijkstra 对拍验证；
- 无法解释性能数字怎么来的。

**正确用法**：读思路 → 用自己的代码实现 → 和 NetworkX / Dijkstra 对拍验证 → 在报告里注明参考来源。
