# 开源导航项目源码与开发者文档学习指南（全链路版）

> 目标读者：路径规划组及需要理解整套导航系统的组员  
> 目标：挑出值得读源码、能看懂模块协作、并且适合动手复现的开源项目。  
> 核验日期：2026-09-26。项目版本、运行环境和文档会更新，开始实践前以项目当前 README 为准。

## 一、先说结论：不要指望一个仓库讲完全部导航

你们要理解的不是单独一个“最短路算法”，而是一次导航请求如何穿过多个边界：

```text
OSM / DEM / 交通事件
  → 清洗、坐标和属性处理
  → 建立路网图、空间索引及可查询数据
  → 地址/地点解析、起终点吸附
  → 按交通主体和偏好计算候选路线
  → 路线几何、距离时间和转向指令
  → 地图匹配、偏航检测、重新规划
  → API、地图渲染、语音/跨平台界面
  → 测试、部署、数据更新
```

开源项目通常有意分层：路由引擎不一定带完整地图 App；渲染器不负责算路线；地理编码和 DEM 也常是独立服务。因此最适合你们的不是“找一个全都包办的项目”，而是挑一组边界清楚、源码与开发文档都能读的参考项目。

**建议的学习组合：**

1. **先继续做本仓库的 OSMnx + NetworkX 小练习**：最容易理解数据如何变成图、图如何变成路线。它是教学入口，不是完整导航产品。
2. **拿 GraphHopper 引擎 + GraphHopper Maps 跑一次前后端联调**：最适合观察浏览器界面如何把请求交给路由服务、又如何把结果画出来。
3. **读 Valhalla 的架构与 API**：重点看数据构建、动态代价、多交通方式、地图匹配和高程。
4. **读 Organic Maps 的目录结构和构建文档**：看一个真正的离线、跨平台导航 App 如何组织数据、搜索、路由、渲染和平台代码。
5. **按需读 OSRM**：重点看从 OSM PBF 预处理到 HTTP 路由服务的工程流水线。

## 二、候选项目对比

| 项目 | 它是什么 | 最值得学的链路 | 开发者资料与源码可读性 | 对你们的判断 |
|---|---|---|---|---|
| [OSMnx](https://github.com/gboeing/osmnx) + [NetworkX](https://github.com/networkx/networkx) | Python 路网获取、图分析和算法库 | OSM 数据 → NetworkX 路网 → 最短路 → 保存/绘图 | Python 文档和源码入口清晰；适合从函数调用跟进去 | **最适合入门和复现**，但没有定位、语音、导航状态机或完整 App |
| [GraphHopper](https://github.com/graphhopper/graphhopper) + [GraphHopper Maps](https://github.com/graphhopper/graphhopper-maps) | Java 路由引擎 + Web 路线规划界面 | PBF 导入 → 图数据/权重 → HTTP API → 浏览器选点、请求、展示路线 | 有 quick start、核心文档、配置示例；源码按 core、web-api、navigation、map-matching 等模块拆分；Maps 仓库给出本地开发和测试步骤 | **最推荐作为你们的全链路联调样板**；需注意它不是完整的跨平台语音导航 App |
| [Valhalla](https://github.com/valhalla/valhalla) | C++ 路由引擎及配套库 | OSM/高程数据构建 → tiled graph → 多模式路径规划 → 地图匹配/高程/等时圈 API | 官方有 Mjolnir、Meili、API 等架构与开发说明；能力覆盖与你们的扩展想法高度相关 | **最适合路径规划进阶和 DEM 接入思路**；代码规模大，不建议初学者从头编译后再开始读 |
| [Organic Maps](https://github.com/organicmaps/organicmaps) | 离线地图与导航应用，面向 Android、iOS、桌面端 | 地图数据生产/下载 → 搜索 → 离线路由 → 渲染 → 平台 UI 与导航引导 | `docs/STRUCTURE.md` 明确说明平台、数据、工具、路由、渲染和平台抽象目录；`docs/INSTALL.md` 讲构建 | **最适合看“完整导航产品如何分层”**；代码量大、C++ 与多平台语言混合，不适合照抄成课程项目 |
| [OSRM backend](https://github.com/Project-OSRM/osrm-backend) + [OSRM frontend](https://github.com/Project-OSRM/osrm-frontend) | C++ 路由服务 + Web 地图前端 | OSM PBF → extract → partition/customize → HTTP 服务 → 前端 | `docs/tools.md` 把预处理命令逐个解释，`docs/http.md` 说明 API；前端仓库可对照请求和地图展示 | **最适合看数据生产和高性能路由服务**；不是完整跨平台语音导航系统，重点偏道路驾驶和后端服务 |

GraphHopper 的引擎 README 提供本地启动方法，GraphHopper Maps 可配置为连接本地服务，并提供 `npm install`、`npm run serve`、测试和构建步骤；所以这一对能让你们亲眼看到 UI 与路由 API 的协作，而不只是阅读算法函数。[引擎 README](https://github.com/graphhopper/graphhopper#installation) · [Maps 开发说明](https://github.com/graphhopper/graphhopper-maps#start-development)

### 覆盖范围速查

| 模块 | 最值得参考的项目 | 说明 |
|---|---|---|
| OSM 路网下载、初步分析 | OSMnx | Python 中直接构建区域道路图，和你们 CUG 武汉练习很接近 |
| 大范围 PBF 导入与路由数据构建 | OSRM、Valhalla、GraphHopper | 关注原始 OSM 标签怎样变成可查询的图数据；OSRM 的命令流水线尤其直观 |
| 空间存储与索引 | 各路由引擎自身；需要地理编码时看 Nominatim | 路由图的高性能索引往往是引擎自有格式，不应默认等同于 PostGIS |
| 地名/地址搜索 | [Nominatim](https://github.com/osm-search/Nominatim) 或 GraphHopper 生态中的 [Photon](https://github.com/komoot/photon) | 地址解析是“文字→坐标”，和“坐标→路网节点吸附”不是同一件事 |
| 路径规划、交通主体、偏好 | GraphHopper、Valhalla | GraphHopper 的 profile/custom model 易演示；Valhalla 的动态 costing 与多模式设计值得读 |
| 定位与地图匹配 | Valhalla Meili、OSRM Match | GPS 点可能有噪声，要匹配到最可能的道路序列 |
| 路线指令/导航引导 | Organic Maps、Valhalla、GraphHopper | 规划返回的路线几何还需变成“前方右转”等引导步骤；完整端侧导航看 Organic Maps |
| 地图渲染 | GraphHopper Maps（OpenLayers）、Organic Maps（自有渲染层）；也可单看 [MapLibre GL JS](https://maplibre.org/maplibre-gl-js/docs/) | 渲染器负责把底图和路线画出来，不负责决定最优路径 |
| DEM 与地形衍生量 | [GDAL `gdaldem`](https://gdal.org/en/stable/programs/gdaldem.html)、[QGIS 地形分析教程](https://docs.qgis.org/testing/en/docs/training_manual/rasters/terrain_analysis.html)、Valhalla | GDAL/QGIS 做栅格处理；路由引擎再把坡度等特征转成路段代价 |
| AI 辅助 | 可选 [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)；它不是导航引擎 | 适合将自然语言变成受约束的工具调用流程；核心路线仍应由可测试的确定性路由服务计算 |

## 三、每个项目应该怎样读

### 1. OSMnx + NetworkX：从数据到图，先把基本概念学扎实

**看什么：**

- OSMnx 的 `graph_from_place` / `graph_from_point`：观察它怎样查询 OSM 并生成有向道路图。[图构建源码](https://github.com/gboeing/osmnx/blob/main/osmnx/graph.py)
- OSMnx routing：看最短路函数如何把权重交给 NetworkX。[路由源码](https://github.com/gboeing/osmnx/blob/main/osmnx/routing.py)
- NetworkX shortest paths：对照 Dijkstra、A* 等算法的接口和边界。[算法文档](https://networkx.org/documentation/stable/reference/algorithms/shortest_paths.html)
- 对照本仓库的 `docs/learning/osmnx_demo/route_demo.py`、`path_planning/models.py`、`path_planning/costs.py` 和 `path_planning/router.py`。

**动手任务：**在中国地质大学（武汉）附近分别跑距离最短、时间最短；记录路线为何变化；再给自己的路径规划器加“禁走高速”，用 NetworkX 的结果做正确性对照。你们现有小项目已有真实校园路网和 HTML 地图，不要为学基础再造一个相同项目。

**边界：**OSMnx/NetworkX 不会自动给你完整地址检索、地图匹配、定位导航、语音播报或可部署的生产后端。

### 2. GraphHopper + GraphHopper Maps：观察服务端与前端如何配合

建议顺序：

1. 先按 GraphHopper README 启动自带的本地 Web 服务和 Maps UI，理解地图选点后请求从哪里发出、API 返回了什么。
2. 看 `config-example.yml` 和 [profiles 文档](https://github.com/graphhopper/graphhopper/blob/master/docs/core/profiles.md)：理解“出行方式”怎样关联速度、可通行性和转向限制。
3. 看 [custom models](https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md)：把“避开高速”“偏好某类道路”“按坡度调速”映射到 edge 属性与 weighting。
4. 对照引擎的 `core/`、`web-api/`、`navigation/`、`map-matching/` 与 Maps 的 `src/`、`config.js`，沿着一次请求从界面跟到服务端，再跟回路线绘制。
5. 用同一组起终点和目标函数，对比 GraphHopper 返回结果与自己的 Python 路由结果，分析差异来自数据、吸附、道路规则还是权重。

GraphHopper 的 profile/custom model 文档明确把可通行性、速度、道路类型和权重规则联系起来，因此它特别适合学习“多主体/多目标不是复制多套算法，而是更换路网过滤规则和代价模型”。[Custom models](https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md)

**重要边界：**GraphHopper 项目仓库与其托管 Directions API 的功能、许可证和服务范围不是一回事。比如其 README 把托管 Map Matching API 列为商业 API 能力；若你们打算直接用某项功能，应确认当前开源版本实际包含什么，不要把线上服务能力默认当成可免费自托管能力。[项目说明](https://github.com/graphhopper/graphhopper#graphhopper-directions-api)

### 3. Valhalla：深入学习“路径规划模块”与扩展能力

它最值得你们的点是数据构建、costing 和 API 不是黑盒。阅读顺序：

1. [Mjolnir 架构与构建指南](https://valhalla.github.io/valhalla/contributing/architecture/mjolnir/)：看 OSM PBF 如何解析成分块路由图；文档还说明可在建图时加入高程数据。
2. [OSM 标签解析](https://valhalla.github.io/valhalla/contributing/architecture/mjolnir/tag-parsing/)：理解 OSM 的 `highway`、`access` 等原始标签如何被转换成图上的道路属性。
3. [API 目录](https://valhalla.github.io/valhalla/api/)：分别查看 route、map matching、elevation 等接口和请求/响应。
4. [Meili 地图匹配架构](https://valhalla.github.io/valhalla/contributing/architecture/meili/) 与 [库接口](https://valhalla.github.io/valhalla/contributing/architecture/meili/library-api/)：看 GPS 测量点如何匹配到道路图，以及匹配结果如何提供给后续路线逻辑。
5. [Elevation API](https://valhalla.github.io/valhalla/api/elevation/)：看怎样沿路线采样高程；再将得到的知识和你们的 DEM 应急规划设计对照。

Valhalla 的官方说明包括动态运行时 edge/vertex costing、多交通模式、地图匹配、等时圈和高程能力；因此它是你们研究“路线偏好、骑行/步行/车辆以及地形成本”的强参考。[项目能力与架构概览](https://github.com/valhalla/valhalla#overview)

**边界：**它主要是路由引擎和库，不是包含完整手机交互、离线地图下载、语音 UI 的开箱即用导航 App。读懂架构比立刻编译整个 C++ 工程更有价值。

### 4. Organic Maps：看真正的跨平台离线导航应用

从 [目录结构](https://github.com/organicmaps/organicmaps/blob/master/docs/STRUCTURE.md) 开始，不要从根目录逐个文件乱翻。它将 Android、iOS、Qt 桌面端，地图生成工具，索引器，搜索、routing、platform、storage、traffic、drape 渲染等分区列出；[构建文档](https://github.com/organicmaps/organicmaps/blob/master/docs/INSTALL.md) 则说明构建前置条件、子模块与各平台流程。

**动手方式：**先按结构文档画一张“平台 UI → 公共 C++ 核心 → 地图数据/路由/渲染”的依赖图；再任选一个入口，追踪一次用户操作如何进入公共核心、得到路线并更新地图。第一次学习不要以“成功构建 Android/iOS 全套”为目标——系统依赖较多，编译成功本身并不能帮助理解模块边界。

**边界：**Organic Maps 适合看系统架构与产品级交互，不适合把它当作你们 Python 路由器的直接替代品；其离线地图生产和存储方案也不等于你们必须照搬。

### 5. OSRM：看数据流水线、接口和前后端协作

最值得先读的是 [命令行工具文档](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/tools.md) 与 [HTTP API](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/http.md)。用自己的话复述下面这条链，并在本地跑一次小区域数据：

```text
OSM PBF → osrm-extract → osrm-partition → osrm-customize → osrm-routed
                                                   ↓
                                             HTTP 路由 API
                                                   ↓
                                             osrm-frontend
```

OSRM 文档还介绍 CH 与 MLD 两条准备路线；常规路线服务的接口之外，也有 nearest、table、match、trip 等服务。[OSRM README](https://github.com/Project-OSRM/osrm-backend#quick-start) · [前端仓库](https://github.com/Project-OSRM/osrm-frontend)

**边界：**OSRM 最擅长作为清晰、高性能的道路路由后端参考。它不替你们完成全套跨平台产品、完整语音导航 UI 或灾害应急业务规则。

## 四、把 12 个模块理解成协作接口

一条请求可以拆成以下责任边界；这比把所有代码塞进一个“导航模块”更容易分工和测试：

1. **数据生产**：从 OSM、DEM、交通事件等来源取数，标注来源、时间和许可。
2. **预处理**：修复/筛选数据，统一属性字段，检查缺失与异常。
3. **坐标与几何**：统一坐标系和单位，计算长度、投影、路段与栅格相交关系。
4. **存储与索引**：把道路图、地址索引、栅格及运行数据存成适合各自查询的数据结构。
5. **路网建模**：把交叉口、路段、方向、通行限制变成图；保存道路等级、速度、坡度等属性。
6. **代价与约束**：按步行/骑行/普通车辆/应急车辆判断可通行性，并计算各路段代价。
7. **规划算法**：在图上找满足约束且总代价最优的路线或候选路线。
8. **路线表达**：输出坐标折线、距离时间、道路名称、转向步骤和可解释的选择原因。
9. **定位匹配**：把 GPS 轨迹与道路图匹配，估计当前所在路段。
10. **交通与重规划**：接入道路封闭/拥堵等变化，检测偏航并重新计算路线。
11. **API 与客户端**：API 让模块解耦；前端负责地图交互与图层，导航客户端负责定位、语音和状态。
12. **验证与运维**：测试算法正确性、数据质量、接口契约、性能和异常场景，并管理数据更新。

典型的跨模块契约是：**地理编码输出坐标；吸附模块输出路网边/位置；规划 API 输入坐标、profile、目标和限制；引擎输出路线几何、时间距离与步骤；客户端消费路线并用定位更新进度。**其中，地址检索（“科技楼”→坐标）、吸附（坐标→道路上的位置）和地图匹配（连续 GPS 点→最可能道路序列）是三个不同问题。

## 五、你们的特色扩展：多目标、DEM 应急与 AI 助手

### 多主体与多目标

先保证普通路线正确，再把不同偏好作为 profile/代价模型，而不是把“最优”当作唯一答案：

- **路程最短**：边代价为长度；
- **时间最短**：边代价为预计通行时间；
- **少红绿灯/少转弯**：在时间或距离上叠加交叉口/转向惩罚；
- **不走高速**：先做硬约束过滤，或给高速极大代价；
- **步行、骑行、普通车、应急车**：分别定义可通行性、速度、道路偏好、转向和车辆限制。

每个结果要返回“选了什么目标、用了哪些限制、估计距离/时间、为什么避开/选择某类路”，这样路线才可解释和可比较。多目标之间可能冲突，第一版可以做多个单目标候选路线，不必一上来做复杂 Pareto 最优。

### DEM 应急路径：区分“高程”与“灾害危险度”

DEM 可以提供道路附近的高程、坡度、相对起伏等地形变量；GDAL `gdaldem slope` 能从 DEM 生成坡度栅格，QGIS 可用于可视化和地形分析。[GDAL 地形工具](https://gdal.org/en/stable/programs/gdaldem.html)

但**DEM 本身不告诉我们哪里正在洪水、火灾或塌方**。应急可行路线通常还要结合实时/情景危险区、道路封闭、桥梁与限高限重、车辆能力和救援点数据。推荐的数据融合方式是：

```text
道路中心线与 DEM 相交/采样 → 给每条道路算高程、坡度等特征
危险区/封闭事件            → 形成禁行边或风险代价
应急车辆 profile           → 定义宽度、限高、通行与转弯约束
安全优先目标               → 先满足可行与安全，再优化时间/距离
```

可以给受灾/封闭道路做**硬禁止**，对坡度大、地势低洼等做**软惩罚**，并返回替代路线及风险说明。高程影响 routing 的成熟例子可看 Valhalla，但要把“自行车爬坡代价”与“洪水避险”区分开：后者需要额外风险数据和验证。

### 路径规划智能体：让 AI 做意图转换与工具编排，不替代路由算法

可以把“别走高速，尽量少等红灯，我开的是救援车”转成严格的 JSON：`vehicle=emergency`、`avoid=[motorway]`、`objective=low_signal_delay`。随后由智能体调用你们自己的 `route()`、`risk_check()`、`compare_routes()` 工具；确定性路由核心负责实际路径，校验器检查应急硬约束，智能体负责澄清歧义、挑选工具、解释结果。LangGraph 可以作为流程编排的学习参考，但它不是地图数据、路径规划算法或导航系统本身。[LangGraph 官方概念与 API](https://docs.langchain.com/oss/python/langgraph/overview)

建议把 AI 放在 API 之上：**自然语言 → 结构化规划请求 → 路由/风险工具 → 规则校验 → 给用户解释**。AI 不应直接编造路线坐标、忽略禁行规则或在没有数据依据时宣称某条路“安全”。

## 六、推荐的四周动手路线

| 周次 | 任务 | 产出/验收 |
|---|---|---|
| 第 1 周：本仓库 | 读 OSMnx 取数与自研 Dijkstra/A*；实现最短距离、最短时间、禁高速至少三种模式 | 同一组起终点可复现；测试能检查代价与路径合法性 |
| 第 2 周：GraphHopper + Maps | 启动本地引擎和地图前端；浏览请求、响应、路线折线与 turn instructions | 画出浏览器到 API 再回来的时序图；写一页接口字段说明 |
| 第 3 周：Valhalla 或 OSRM | 选 Valhalla 学动态 costing/地图匹配/高程，或选 OSRM 学 PBF 到服务的预处理流程 | 复述一次数据构建流水线；做一个同地点路线对比表 |
| 第 4 周：Organic Maps + DEM/AI 方案 | 读目录结构和平台分层；做 DEM-道路采样设计，画 AI 调工具流程 | 提交系统模块图、应急路线数据字段表和 AI 工具契约，不要求完整移植 App |

以下是“各自深入、全员同步接口”的分配，不等于每个人只懂一个模块：

## 八、下载/运行时的现实提醒

- 第一次学习先跑本仓库现有代码和 GraphHopper 示例；不要同时下载并编译四个大型 C++/Java 项目。
- GraphHopper Maps 的 README 有开发服务器步骤；GraphHopper 引擎 README 的当前版本要求以其当前 Java 版本说明为准。把 Maps 指向本地引擎时，注意服务地址、跨域配置与 profile 名必须一致。
- Valhalla、OSRM 和 Organic Maps 的全区域数据/构建链对磁盘、内存和编译环境都有要求；先使用很小的区域数据或阅读架构，不要直接做全球数据。
- Nominatim 的完整区域数据库也很重。官方文档列出 PostgreSQL/PostGIS 等依赖，并提醒全行星导入需要大量磁盘和内存；课堂阶段不必自建全量地理编码服务。[Nominatim 架构](https://nominatim.org/release-docs/develop/develop/overview/) · [安装需求](https://nominatim.org/release-docs/develop/admin/Installation/)
- OSM 数据和软件代码有各自许可与署名要求。参考代码、底图瓦片、OSM 数据不能一概当成“免费且无限制”，交付前分别核对项目 LICENSE、数据来源和服务使用政策。

## 九、最终推荐

如果时间只够深入三个：**OSMnx + NetworkX（动手理解） → GraphHopper + Maps（跑通前后端） → Valhalla（理解规划进阶和地形相关能力）**。再用 **Organic Maps** 的结构文档补完整 App/跨平台视角，用 **OSRM** 补预处理流水线视角。

对你们最重要的不是照搬某个成熟引擎，而是能画出并解释：**输入如何变成标准化请求，路由内核如何依据 profile 和目标选路，结果怎样被 API 和地图消费，定位变化如何触发匹配与重规划，DEM 与危险数据怎样转成可审查的路段约束。**这条链理解透了，你们的路径规划模块才能和其他组员负责的模块真正接起来。
