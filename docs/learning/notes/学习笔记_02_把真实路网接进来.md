## 这篇笔记解决什么问题

笔记 01 你读懂了两套东西，但它们是**分开的**：

```text
【A 套】path_planning/         你们自己的算法
        └─ 跑在 demo.py 那张"4 个点的假地图"上

【B 套】learning_osmnx_networkx/output/graph.graphml
```

**这两套从来没接上过。** 你的算法只在假地图上跑过，真实路网从来没进过你的算法。

```text

      ↓

      ↓

```

## 第 1 课：先看看真实数据长什么样

### ① 要回答的问题

`graph.graphml` 这个 674 KB 的文件里，到底装了什么？

### ② 先跑起来，用眼睛看

在项目根目录敲（如果你发现回车后啥都没有，请直接在pycharm或vscode中打开该文件）：

```powershell
Get-Content learning_osmnx_networkx\output\graph.graphml -TotalCount 3
```

你会看到一堆 XML。别急着读懂，先看**结构**：

```xml
<key id="d14" for="edge" attr.name="length" attr.type="string"/>
<key id="d15" for="edge" attr.name="speed_kph" attr.type="string"/>
<key id="d17" for="edge" attr.name="geometry" attr.type="string"/>
...
<node id="286073497">
  <data key="d4">30.539114</data>      ← 纬度
  <data key="d5">114.4119831</data>    ← 经度
  <data key="d6">4</data>              ← 这个路口连了 4 条路
</node>
<edge source="286073497" target="9641468494" id="0">
  <data key="d9">secondary</data>      ← 道路等级
  <data key="d14">24.325386269768018</data>   ← 长度（米）
  <data key="d15">60.0</data>          ← 限速（km/h）
</edge>
```

**大概能看出三件事**：

1. 有个**属性名对照表**（`<key>` 元素），把 `d14` 这种代号翻译成 `length`；
2. `<node>` 是路口，`<edge>` 是路段；
3. **真正的属性值藏在 `<data>` 子元素里**，用 `key` 指向对照表。

### ③ 核心：为什么不能按行读

有个**很重要**的坑，我先指出来：

```xml
<node id="286073497">        ← 第 1 行
  <data key="d4">30.539114</data>    ← 第 2 行（属性在下一行！）
```

**`<node>` 和它的属性不在同一行。** 所以你不能用"读一行、切一切"的土办法——必须用**真正的 XML 解析器**。

Python 标准库里就有：

```python
import xml.etree.ElementTree as ET
root = ET.parse("文件路径").getroot()
```

### ④ 停下来自问

> **问**：为什么不能简单地按行读这个文件？
> **答**：因为 `<node>` / `<edge>` 和它们的 `<data>` 属性在不同行，而且一个标签可能跨多行。

> **问**：`d14` 是什么意思？
> **答**：只是个代号。要去文档开头的 `<key>` 表里查，才知道它是 `length`。

## 第 2 课：理解"属性名对照表"

### ① 要回答的问题

那个 `<key>` 表里到底定义了哪些属性？

### ② 先跑起来

新建一个临时文件 `probe_graphml.py`：

```python
import xml.etree.ElementTree as ET

NS = "{http://graphml.graphdrawing.org/xmlns}"
root = ET.parse("learning_osmnx_networkx/output/graph.graphml").getroot()

print("=== 属性名对照表 ===")
for k in root.iter(NS + "key"):
    print(f"  {k.get('id'):5s} 用于={k.get('for'):6s} 名字={k.get('attr.name')}")
```

运行：

```powershell
python probe_graphml.py
```

### ③ 你会看到什么

```text
  d23  用于=edge   名字=junction
  d22  用于=edge   名字=tunnel
  d21  用于=edge   名字=width
  d20  用于=edge   名字=maxspeed
  d19  用于=edge   名字=ref
  d18  用于=edge   名字=bridge
  d17  用于=edge   名字=geometry     ← 道路形状！
  d16  用于=edge   名字=travel_time
  d15  用于=edge   名字=speed_kph    ← 限速
  d14  用于=edge   名字=length       ← 长度
  d12  用于=edge   名字=oneway
  d11  用于=edge   名字=name         ← 道路名
  d9   用于=edge   名字=highway      ← 道路等级
  d7   用于=node   名字=highway
  d6   用于=node   名字=street_count
  d5   用于=node   名字=x            ← 经度
  d4   用于=node   名字=y            ← 纬度
  d2   用于=graph  名字=crs          ← 坐标系
  d1   用于=graph  名字=created_with ← 谁生成的
```

**关键点**：`for` 那一列告诉你这个属性是给节点用的、给边用的、还是给整张图用的。

> ⚠️ 注意 `d7` 和 `d9` **都叫 `highway`**，但 `for` 不同（一个是 node，一个是 edge）。所以查表时**必须同时看 `id` 和 `for`**，不能只看名字。

### ④ 核心：为什么这个表重要

因为 `<data key="d14">` 里的 `d14` **本身没有意义**。你的解析器必须先读这张表，建一个 `{"d14": "length", ...}` 的字典，才能知道每个 `<data>` 装的是什么。

这就是为什么 `osm_loader.py` 第一步就干这个（第 50 行）：

```python
key_names = {k.get("id"): (k.get("attr.name") or "") for k in root.iter(NS + "key")}
```

### ⑤ 停下来自问

> **问**：`<data key="d9">secondary</data>` 里的 `secondary` 是什么？
> **答**：道路等级。因为 `d9` 查表得到 `highway`，而 `secondary` 是 OSM 里"次干道"的意思。

## 第 3 课：三个必须处理的坑（我实测发现的）

### ① 要回答的问题

直接把 XML 读一遍就能建图吗？——**不能，有三个坑。**

### ② 坑 1：`<edge>` 的 `id` 属性不唯一！

先看现象。在 `probe_graphml.py` 里加：

```python
import collections
ids = collections.Counter(e.get("id") for e in root.iter(NS + "edge"))
print("\n=== edge 的 id 属性取值分布 ===")
for k, v in ids.most_common():
    print(f"  id={k!r}: {v} 条")
```

运行结果：

```text
  id='0': 1383 条
  id='1':   17 条
```

**1400 条边里，1383 条的 `id` 都叫 `"0"`！**

原因：OSMnx 导出的 GraphML 里，`id` 只是"同一对起终点之间的第几条平行边"的编号，**不是全局唯一的**。

**后果**：如果你直接把 `id` 当 `Edge.edge_id`，会撞上 `models.py` 第 127 行的查重：

```python
if edge.edge_id in self.edges:
    raise ValueError(f"duplicate edge id: {edge.edge_id}")
```

程序直接报错退出。

**解决办法**（`osm_loader.py` 第 67 行）：**自己按读取顺序编号**，从 0 数到 1399。

```python
next_edge_id = 0
for element in root.iter(NS + "edge"):
    ...
    graph.add_edge(Edge(edge_id=next_edge_id, ...))
    next_edge_id += 1
```

> **这是个通用经验**：外部数据的 ID 能不能直接用，**必须验证**，不能假设它唯一。

### ③ 坑 2：`geometry` 只有**一半**的边有

```python
with_geom = sum(1 for e in root.iter(NS + "edge")
                if any(d.get("key") == "d17" for d in e.findall(NS + "data")))
print(f"\n带 geometry 的边: {with_geom} / {len(list(root.iter(NS + 'edge')))}")
```

实测结果：

```text
带 geometry 的边: 731 / 1400   (52.2%)
```

**只有 52.2%！** 这就直接回答了你之前问的"边没几何数据时用路口坐标凑"——**在这份真实数据里，将近一半的边都会走那个兜底分支**。

还有更细的发现（我另跑脚本统计的）：

| 统计项 | 结果 |
|---|---|
| 带几何的边 | 731 / 1400（52.2%） |
| 几何点数 | 最少 2 个，最多若干（如 `LINESTRING` 里有 6 个点） |
| 几何方向与边方向是否一致 | **731 / 731 全部正向匹配**（首点=起点，尾点=终点） |

**最后一行很重要**：几何的首尾点和边的起点终点**方向一致**，所以你**不需要反转几何**，直接拼就行。

### ④ 坑 3：有些属性值是**列表**，不是单个值

再看一个现象：

```text
osmid    = [688794418, 98831411]
reversed = [False, True]
```

有的边是**两条 OSM 道路合并成的**，所以 `osmid` 变成了列表。

**后果**：如果你写 `float(values["osmid"])`，程序会崩。

**解决办法**：只取我们真正需要的字段（`length`、`speed_kph`、`highway`、`name`、`geometry`），这些字段实测**都是单值**。列表字段（`osmid`、`reversed`）我们暂时不用，就不去碰它。

> **这也是个通用经验**：解析外部数据时，**只读你要用的字段**，比自己造一套完整的类型转换更稳。

### ⑤ 停下来自问

> **问**：为什么不能把 GraphML 的 `id` 直接当 `edge_id`？
> **答**：因为它不唯一（1383 条都是 `"0"`），会让 `Graph.add_edge` 报"重复 ID"。

> **问**：这次真实数据里，有多少边会走"用路口坐标凑几何"那个兜底分支？
> **答**：1400 - 731 = 669 条，约 48%。

## 第 4 课：写这个"翻译器"

### ① 要回答的问题

怎么把上面这些变成代码？

### ② 完整代码在 `path_planning/osm_loader.py`

**不要照抄**，先跟着理解这四个部分。打开文件对照看：

| 部分 | 行数 | 干什么 |
|---|---|---|
| `_attr_values()` | 14–22 | 把一个元素下的 `<data>` 读成字典 |
| `parse_wkt_linestring()` | 25–42 | 把 `LINESTRING (lon lat, ...)` 解析成坐标元组 |
| `load_graphml()` 读节点 | 55–65 | 建所有 `Node` |
| `load_graphml()` 读边 | 67–93 | 建所有 `Edge`（含自己编号） |

### ③ 核心一：WKT 是什么

`geometry` 字段的内容长这样：

```text
LINESTRING (114.4119831 30.539114, 114.4120067 30.5391427, ...)
```

这叫 **WKT**（Well-Known Text），是地理数据的一种文本格式。规则很简单：

- `LINESTRING` 后跟一串括号
- 括号里是**逗号分隔的点**
- 每个点是 **"经度 纬度"**（空格分隔）

**⚠️ 注意**：又是**经度在前**！（和 GeoJSON 一样，和地图 API 通常的 `[lat, lon]` 相反）

解析代码（`osm_loader.py:25-42`）：

```python
def parse_wkt_linestring(text: str) -> tuple[tuple[float, float], ...]:
    match = re.search(r"\((.*)\)", text, re.S)     # 取出括号里的内容
    if match is None:
        return ()
    points = []
    for pair in match.group(1).split(","):          # 按逗号切成一个个点
        parts = pair.split()                        # 按空格切成 经度 / 纬度
        if len(parts) >= 2:
            points.append((float(parts[0]), float(parts[1])))
    return tuple(points)
```

### ④ 核心二：为什么 geometry 要用元组不用列表

看 `models.py` 第 42 行：

```python
geometry: tuple[Coordinate, ...] = ()
```

它要求**元组**（`tuple`）不是列表（`list`）。原因是 `Edge` 是 `frozen=True`（不可变）的，如果里面装了个可变的 `list`，理论上还能被改动，就破坏"不可变"的承诺了。

所以 `parse_wkt_linestring` 最后返回 `tuple(points)`。

### ⑤ 核心三：节点坐标 vs 边几何

搞清楚这两个是不同的东西：

| 东西 | 来自 | 用途 |
|---|---|---|
| **节点坐标** | `<node>` 的 `x` / `y` | 算法用它算启发式；没几何时用它兜底 |
| **边的几何** | `<edge>` 的 `geometry` | 画地图用，能画出道路的弯曲 |

`osm_loader.py` 第 79–80 行处理几何：

```python
geometry_text = values.get("geometry", "")
geometry = parse_wkt_linestring(geometry_text) if geometry_text else ()
```

没有就留空 `()`，`router.py` 会自动用节点坐标兜底——**这正是笔记 01 里那个测试验证的行为**。

### ⑥ 小实验：先别建图，只验证解析对不对

新建 `probe_loader.py`：

```python

print(f"edge_id 范围 = {min(g.edges)} .. {max(g.edges)}")                 # 应该是 0 .. 1399

# 随便挑一条边看看
e = g.edge(0)
print(f"\n边 0: {e.from_node} → {e.to_node}")
print(f"  长度 {e.length_m:.1f} m, 限速 {e.speed_kmh} km/h, 等级 {e.road_type}")
```

> 🎉 **做完这一步，项目才真正"活了"**：你们自己的算法 + 真实的路网 + 真实的坐标。

### ④ 但你会撞上一个报错（这是故意的）

**多试几组起终点**，你会发现有将近**一半**的查询会这样崩掉：

```text
TypeError: '<' not supported between instances of '_State' and '_State'
```

**这正是笔记 01 第 5 课那个 `try_it.py` 实验里的报错**——现在它出现在了**真实数据**上。

我实测过，在 552 节点的真实路网上随机取 500 组起终点：

| 偏好 | 成功 | 崩溃 | 崩溃率 |
|---|---|---|---|
| fastest | 230 | 269 | **54%** |
| shortest | 260 | 239 | **48%** |
| avoid_tolls | 230 | 269 | **54%** |
| no_highway | 208 | 264 | **56%** |

**差不多一半的查询会直接崩。**

### ⑤ 为什么现在才暴露

还记得笔记 01 第 5 课的结论吗：

> **"7 个测试全绿"不等于"程序没问题"。**

现在你看到活生生的例子了：

- `demo.py` 那张假地图上，所有边的长度都**故意不同**（1000、1300），所以永远不会出现"两条路代价完全相等"；
- 真实路网上，**等长的路段到处都是**（同一个等级、同一个限速，很容易算出一样的代价）；
- 一旦代价相等，`heapq` 就不知道该先处理谁，转头去比较 `_State` 对象——而它没有定义"怎么比大小"。

**这不是新 bug，是同一个 bug 在真实数据下必然暴露。**

## 第 6 课：性能初测——A* 到底快了多少

### ① 要回答的问题

A* 和 Dijkstra 在真实路网上差多少？

### ② 先跑起来

新建 `compare_real.py`：

```python
import random
from path_planning import load_graphml, plan_route, CostModel, Preference

g = load_graphml("learning_osmnx_networkx/output/graph.graphml")

# 用上节课那对起终点（已知可达，且两种偏好都不会崩）
src, dst = 1260855371, 2864441887

for pref in (Preference.FASTEST, Preference.SHORTEST):
    m = CostModel(preference=pref)
    for alg in ("dijkstra", "astar"):
        r = plan_route(g, src, dst, algorithm=alg, cost_model=m)
        print(f"{pref.value:9s} {alg:9s} 代价={r.cost:9.2f} 扩展={r.expanded_states:4d} 耗时={r.planning_ms:6.2f}ms")
```

### ③ 我实测的基线数据

**单次查询（上面那对起终点，约 1.8 km）：**

| 偏好 | 算法 | 代价 | 扩展状态 | 耗时 |
|---|---|---|---|---|
| shortest | Dijkstra | 1798.03 | 394 | 1.21 ms |
| shortest | **A\*** | 1798.03 | **98** | **0.43 ms** |
| fastest | Dijkstra | 171.51 | 332 | 1.05 ms |
| fastest | A\* | 171.51 | 237 | 1.41 ms |

**200 组随机查询的统计（更可靠）：**

| 算法 | 偏好 | p50 | p95 | max | 平均扩展状态 |
|---|---|---|---|---|---|
| Dijkstra | fastest | 0.78 ms | 3.08 ms | 4.54 ms | 332 |
| Dijkstra | shortest | 0.90 ms | 4.23 ms | 18.79 ms | 401 |
| **A\*** | fastest | 0.85 ms | 3.40 ms | 5.65 ms | **273** |
| **A\*** | shortest | 0.61 ms | 2.37 ms | 4.73 ms | **197** |

**另外：加载整张图（解析 674 KB XML）耗时约 20 ms。**

### ④ 核心：怎么看这些数字

**最重要的指标是"平均扩展状态"**，不是耗时：

| 偏好 | Dijkstra | A* | A* 少摸多少 |
|---|---|---|---|
| fastest | 332 | 273 | **-18%** |
| shortest | 401 | **197** | **-51%** |

**"最短"模式下 A* 只摸了将近一半的状态。** 这就是启发式的作用——它让搜索"朝终点方向摸"，而不是四面八方均匀扩散。

**为什么这次耗时差异不明显（0.78 vs 0.85 ms）？**

因为图太小了（552 个节点）。A* 省下的计算量，被"每次扩展都要多算一次 Haversine 距离"的开销抵消了。

> **这是个重要认识**：**图越大，A\* 的优势越明显。** 在 552 个节点上，A* 的启发式开销（三角函数）和它省下的扩展次数差不多打平；到了 10 万个节点，省下的扩展次数会远远超过启发式开销。

**所以：现在不要急着说"A* 没比 Dijkstra 快"。** 要看**扩展状态数**这个更本质的指标，等图变大后再看耗时。

### ⑤ 停下来自问

> **问**：552 节点的图上，A* 和 Dijkstra 耗时差不多，那 A* 是不是没用？
> **答**：不是。A* 少扩展了 18–51% 的状态，这是本质优势。耗时差不多只是因为启发式本身有计算成本，图小的时候两者打平。
