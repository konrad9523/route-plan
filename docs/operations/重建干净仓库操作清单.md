> **目的**：把当前仓库的**文件内容**保留，但把课程课件从**提交历史**中移除。
> **背景**：`第1次课_GIS算法设计与分析--导航系统全景与架构设计.pptx` 存在于早期提交（`bfd9f46`、`b4c4841`）中，
> 而删除文件**不会**让历史里的内容消失——有仓库读取权限的人仍可从历史中取回。
> **验证日期**：2026-09-29

> **仓库可见性尚未确认**：本文档早期版本写的"仓库当前为 Public"**未经核实**，
> 已撤回该断言。匿名查询 GitHub API 时被限流（60 次/小时已用尽），无法判定。
> **请自行确认**：用无痕窗口打开 https://github.com/konrad9523/route-plan
> —— 能看到代码即 Public，看到 404 即 Private。
> **这一项直接决定要不要做后面的事**，见第 0 步。

> **提交数量（2026-09-29 实测）**：本地 `main` **29** 个提交，远程 `origin/main` **12** 个，
> **尚未推送 17 个**（远程停在 `b4c4841`，正是加课件的那次提交）。早期版本写的"37 个提交"是估值，已更正。

## 0. 先做决定（不要跳过）

| 要决定的事 | 选项 | 影响 |
|---|---|---|
| **仓库当前可见性** | Private / Public / 待确认 | **Private 则课件只有被邀请的协作者能取到，本清单可以不做** |
| **课件能否被同学看到** | 能 / 不能 / 待确认 | 决定是否需要清理历史 |
| **是否保留提交历史** | 丢弃 / 保留 | 丢弃才能彻底移除课件；保留则课件仍在 |
| **是否保留 Issue 与协作者** | 保留 / 可重建 | **决定只能选方案 C（改写历史）；方案 A/B 会丢 Issue，需重新邀请协作者** |

**先走这条判断链**：

1. **仓库是 Private？** → 只有被邀请的人能访问，课件没有被公开分发。
   若这些协作者本来就是同学，**不必做任何清理**。
2. **仓库是 Public，但课件是老师发给全班的教学材料？** → 你并不是在泄露别人的秘密，
   风险有限；可以选择**保持现状**，把精力留给作业。
3. **仓库是 Public，且课件不应外传？** → 需要清理历史。
   **要保留 Issue 与协作者就选方案 C**；不在乎 Issue 才考虑方案 A/B。

## 1. 三个方案对比

| 方案 | 做法 | Issue / 协作者 | 缺点 |
|---|---|---|---|
| **A. 新建干净仓库** | 用当前文件重新初始化 Git，推到一个全新仓库 | **全部丢失**：Issue 要重建，协作者要重新邀请，旧链接与 Fork 全部失效 | 失去全部提交历史（实测 29 个） |
| **B. 新仓库 + 手工重建提交** | 同 A，但按模块分多次提交，模拟一份可读历史 | **全部丢失**，同 A | 比 A 多花 1~2 小时 |
| **C. 改写历史** | 用 `git filter-repo` 从历史中剔除课件，原仓库强推 | **完全保留**：同一个仓库，Issue、协作者、Fork、链接都不受影响 | 需要装工具；强推改写共享历史；**每个组员必须重置本地仓库** |

**关键区别只有一句话**：**方案 C 是"同一个仓库换掉历史"，方案 A/B 是"换个仓库"。**
你建立的 Issue、邀请的协作者、别人 Star/Fork 的记录都绑在**仓库身份**上，
所以只有方案 C 能保住它们。

**方案 C 的真实代价**（不是"不推荐"三个字能概括的）：

| 代价 | 说明 | 本次情况 |
|---|---|---|
| 需要装 `git filter-repo` | `pip install git-filter-repo`，一条命令 | 低 |
| 必须强推 `main` | 与《团队协作与项目管理原则》§7 的"禁止强推"冲突，**需要全组明确同意** | 需你确认 |
| 组员必须重置本地仓库 | 各自 `git fetch && git reset --hard origin/main`，**未推送的成果会丢** | **现在只有你一个分支、17 个提交未推，是做这件事的最佳时机** |
| 已打开的 PR 会受影响 | 基于旧提交的 PR 需要重新打开 | 当前无开放 PR |

> **时机判断**：本地只有 `main` 一个分支（无其它功能分支），远程也只有 `main`。
> 没有并行开发、没有开放 PR、组员尚未 Fork 出实质成果——
> **这是改写历史代价最小的窗口期**。等四个人都开始提 PR 之后再动，代价会高很多。

**推荐**：先做第 0 步的判断。
- 判断结果是 1 或 2 → **什么都不做**，把精力留给作业 1。
- 判断结果是 3 → **选方案 C**（要保住 Issue 与协作者）或 **方案 A/B**（不在乎 Issue，想要一个彻底干净的新起点）。

## 2. 方案 A：新建干净仓库（完整步骤）

### 第 0 步：确认没有未提交改动

```powershell
Set-Location -LiteralPath 'D:\pycharm\projects\route_plan'
git status --short
```

**输出应为空。** 若有改动，先按下面的方式处理，**不要带着未提交改动继续**：

```powershell
git add 确认过的路径
git commit -m "类型(范围): 说明"
```

> ⚠️ **绝不要在有未提交改动时执行 `git restore` / `git checkout`** —— 会直接丢弃内容且无法恢复。
> 本项目已经发生过一次这样的事故。

### 第 1 步：给旧仓库做一份完整备份

```powershell
Set-Location -LiteralPath 'D:\pycharm\projects'
Copy-Item -Recurse -Path 'route_plan\route_plan\.git' -Destination 'route_plan_git_backup'
```

如果 `.git` 不在 `route_plan\route_plan\.git`，按实际路径调整。**备份是唯一回退手段**，必须做。

同时另存一份工作区快照（防止误删）：

```powershell
Compress-Archive -Path 'route_plan\*' -DestinationPath 'route_plan_snapshot.zip' -CompressionLevel Fastest
```

### 第 2 步：新建干净目录，只拷贝必要文件

**不要**直接复制整个 `route_plan/`——里面有大体积的编译产物和被忽略目录。

```powershell
Set-Location -LiteralPath 'D:\pycharm\projects'
New-Item -ItemType Directory -Path 'route-plan-clean' | Out-Null

# 只复制被版本控制的目录与文件
$items = @(
  'path_planning', 'api', 'web', 'tests', 'data', 'docs', 'workspaces',
  'learning_osmnx_networkx', '.github',
  'README.md', 'LICENSE', 'CHANGELOG.md', '.gitignore'
)
foreach ($i in $items) {
  Copy-Item -Recurse -Path "route_plan\$i" -Destination 'route-plan-clean\'
}
```

**复制完必须核对**（见第 4 节验证清单），特别确认：

- ✅ `data/campus_552.graphml` 在
- ✅ `.gitignore` 在且内容正确
- ❌ **没有** `第1次课_*.pptx`
- ❌ **没有** `.osrm-build-vs2022/`、`.valhalla-build-vs2022/`、`第三方代码/`、`references/`、`个人工作区/`、`A3_临时工作区/`

### 第 3 步：在新目录初始化 Git 并做第一次提交

```powershell
Set-Location -LiteralPath 'D:\pycharm\projects\route-plan-clean'
git init -b main
git add -A
git status --short          # ★ 仔细看这一眼，确认没有不该进去的文件
git commit -m "chore: 项目初始提交（干净历史）"
git log --oneline
```

**`git status --short` 这一步不能省。** 如果看到课件、编译产物、个人草稿，先停下来查清原因。

### 第 4 步：在 GitHub 建新仓库

1. 打开 <https://github.com/new>
2. Repository name：建议 `route-plan`（若同名旧仓库还占着，可先改名旧仓库或换个名字）
3. **Private / Public 按第 0 步的决定选**
4. **README、.gitignore、License 三个复选框全部不要勾**（否则远端会多出本地没有的提交，首次推送易冲突）
5. 创建，记下地址，形如 `https://github.com/OWNER/route-plan.git`

### 第 5 步：推送并验证

```powershell
Set-Location -LiteralPath 'D:\pycharm\projects\route-plan-clean'
git remote add origin https://github.com/OWNER/route-plan.git
git remote -v
git push -u origin main
```

推送后**立刻在网页上验证**（见第 4 节）。

### 第 6 步：组员重新关联

**组员有两种做法**：

**做法一（推荐）：重新 Fork 新仓库**

```powershell
# 各人先把自己 Fork 里还想保留的东西导出/复制出来
# 然后删除旧 Fork，Fork 新仓库，重新克隆
git clone https://github.com/<你的用户名>/route-plan.git
Set-Location route-plan
git remote add upstream https://github.com/OWNER/route-plan.git
git remote -v
```

**做法二：改动现有克隆的远端**

```powershell
Set-Location 你的项目目录
git remote -v                        # 先看当前指向
git remote set-url origin https://github.com/<你的用户名>/route-plan.git
git remote add upstream https://github.com/OWNER/route-plan.git
git fetch upstream
```

> ⚠️ **做法二有风险**：本地历史与新仓库历史**无关**，直接 `git pull` 会报
> `refusing to merge unrelated histories`。安全做法是重新克隆（做法一）。

### 第 7 步：处理旧仓库

**先不要删。** 建议：

1. 把旧仓库**改名为 `route-plan-archive`** 或直接**转为 Private**
2. 观察至少一到两周，确认新仓库工作正常
3. 确认无误后再删除旧仓库

## 3. 方案 B：新仓库 + 按模块重建提交

如果你希望新仓库的历史**可读**，把第 3 步的单个初始提交换成按模块分批提交：

git add tests

## 3.5 方案 C：改写历史（**要保留 Issue 与协作者就选这个**）

方案 A/B 会换掉仓库身份，Issue、协作者、Fork、外部链接全部失效。
**如果这些对你有价值，唯一的选择是改写历史**——同一个仓库，只换掉历史。

### 3.5.1 为什么这条路在本次是可行的

改写历史通常被劝阻，因为要强推共享分支。但本次的处境很特殊：

| 条件 | 实测 | 为什么重要 |
|---|---|---|
| 本地分支 | **只有 `main`**，无功能分支 | 没有需要 rebase 的并行开发 |
| 远程分支 | 只有 `main` | 没有别处引用旧历史 |
| 开放 PR | 无 | 不会有关联 PR 被自动关闭 |
| 组员成果 | 尚未开始（作业 1 阶段） | 没有人的工作会因重置而丢失 |
| 未推送提交 | 17 个（都只在你本地） | 改写后一次性推上去即可 |

**结论：现在是代价最小的窗口期。** 等四个人都提过 PR 之后再改，就要协调四个人重置仓库。

### 3.5.2 完整步骤

> **先读这段，否则第 3 步会失败**：网上大多数教程写 `git filter-repo ...`，
> 但那条命令要求脚本位于 git 的 `--exec-path` 或 `$PATH` 中，**pip 安装并不会做到**
> （PyPI 包无任何依赖声明，也不注册 git 子命令）。
> Windows 上直接用**长格式**调用最稳：`python <脚本路径> <参数>`。
> 官方文档也把长格式列为 Windows 的推荐做法，见
> [INSTALL.md 的 Notes for Windows Users](https://github.com/newren/git-filter-repo/blob/main/INSTALL.md#notes-for-windows-users)。
>
> **前置要求**（已核对）：git ≥ 2.22（本机 2.54.0 ✓）、Python ≥ 3.6 ✓。

```powershell
# 0) 先备份（改写不可逆，这一步不能省）
Set-Location -LiteralPath 'D:\pycharm\projects'
Copy-Item -LiteralPath 'route_plan' -Destination 'route_plan-backup-20260929' -Recurse

# 1) 下载单文件脚本（filter-repo 的全部逻辑就在这一个文件里）
Set-Location -LiteralPath 'D:\pycharm\tools'
Invoke-WebRequest -Uri 'https://raw.githubusercontent.com/newren/git-filter-repo/main/git-filter-repo' -OutFile 'git-filter-repo'
# 或：pipx install git-filter-repo   （作者推荐，自动配好命令，但需要先装 pipx）

# 2) 进仓库，确认工作区干净、且已备份
Set-Location -LiteralPath 'D:\pycharm\projects\route_plan'
git status --short          # 应为空

# 3) 从所有历史中彻底剔除课件（长格式 + --force；本仓库非新克隆，必须加）
python 'D:\pycharm\tools\git-filter-repo' --path '第1次课_GIS算法设计与分析--导航系统全景与架构设计.pptx' --invert-paths --force

# 4) 验证：历史里再也搜不到它
git log --all --pretty=format: --name-only | Sort-Object -Unique | Select-String "pptx"
#    应无输出

# 5) 确认内容没被误删（对比提交数与文件数；filter-repo 会自动清理旧对象）
git rev-list --count HEAD
git ls-files | Measure-Object

# 6) filter-repo 会移除 remote，重新加上
git remote add origin https://github.com/konrad9523/route-plan.git

# 7) 先确认远程没被别人动过，再强推（这一步会覆盖远程历史，请确认已通知全组）
git ls-remote origin main
git push --force origin main
```

> **如果第 3 步报 `not a fresh clone`**：这是 filter-repo 的安全机制——
> 它默认拒绝在非新克隆的仓库上改写，以免你误操作毁了唯一的副本。
> **本仓库不是新克隆**（有 29 个本地提交、还有未推送内容），所以**必然需要 `--force`**：
> 确认备份已做、且你清楚后果后，在命令末尾加 `--force`。
> 官方手册明确说明该选项的作用就是"Ignore fresh clone checks"，并且警告
> **不要养成无脑加 `--force` 的习惯**——否则哪天在错目录里执行就没人拦你了。
> 见 [FRESH CLONE SAFETY CHECK AND --FORCE](https://github.com/newren/git-filter-repo/blob/main/Documentation/git-filter-repo.txt)。
>
> **推送时不要直接用 `--force-with-lease`**：filter-repo 会自动把远程跟踪分支
> 重映射为本地分支（它内部执行 `git fetch -u . refs/remotes/origin/*:refs/heads/*`
> 再 `git remote rm origin`），此时 `--force-with-lease` 拿不到可靠的旧引用，
> 可能报错或误判。**先确认远程确实没被别人动过，再用 `--force`**：
>
> ```powershell
> git ls-remote origin main        # 记下 hash，与 GitHub 网页上的最新提交比对
> git push --force origin main     # 确认一致后再强推
> ```

### 3.5.3 改写之后：每个组员必须做一次

**这一步不能省**，否则组员的本地仓库与远程历史不一致，一推送就会把课件"推回来"。

```powershell
# 组员本地，丢弃本地 main 后重新拉取
git fetch origin
git checkout main
git reset --hard origin/main     # ⚠️ 会丢弃本地未提交的改动，先备份

# 更干净的做法：直接删掉重新克隆
```

> ⚠️ **`git reset --hard` 会丢弃未提交的改动**。
> 按《团队协作与项目管理原则》§7，执行前必须先确认 `git status` 干净，
> 且**不允许在有未提交改动时执行**。

### 3.5.4 方案 C 的残余风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **旧提交哈希仍可访问一段时间** | GitHub 不会立即回收不可达对象，知道旧 SHA 的人短期内仍可能访问 | 如确需彻底，改写后联系 GitHub Support 请求清理缓存；或改用方案 A |
| **Fork 里仍有旧历史** | 别人的 Fork 是独立副本，改写上游不影响它 | 通知 Fork 过的人同步或删除 Fork |
| **组员忘了重置** | 一推送就把课件推回来 | 推送后立刻按 4.3 复查，并让每人确认已重置 |

> **诚实的结论**：方案 C 保住了 Issue 与协作者，但**不如方案 A 彻底**——
> 方案 A 是全新仓库，旧对象根本不存在；方案 C 依赖 GitHub 回收旧对象。
> 如果课件**绝对不能外传**，就该选方案 A 并接受重建 Issue 的成本。

### 4.3 历史彻底性检查（可选但推荐）

## 5. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| **误删有用文件** | 复制时漏了某个目录 | 靠第 1 步的备份恢复；复制后对照 `git ls-files` 清单逐个核对 |
| **带了未提交改动** | 新仓库缺最新内容 | 第 0 步必须确认 `git status` 干净 |
| **大文件混入** | `.git` 体积异常大 | 4.1 的体积检查；发现后查 `git ls-files` 找出来 |
| **新旧历史冲突** | `refusing to merge unrelated histories` | 组员**重新克隆**，不要复用旧克隆 |
| **误删旧仓库** | 不可恢复 | 第 7 步：先改名/转 Private，观察一两周再删 |
| **组员本地有未推送成果** | 重建后丢失 | **重建前通知全组**：先把自己的成果推到自己 Fork 或导出备份 |
| **文件被进程占用** | 删除旧文件报 `Permission denied` | 先停掉占用进程（如已启动的 `uvicorn`），或重启后删除 |
