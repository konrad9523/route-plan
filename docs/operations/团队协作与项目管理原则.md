## 1. 三条核心规则

这三条不是形式要求，而是为了解决已经发生过的真实问题（见 1.5 节的真实反例）。
若已经提交了混在一起的改动，补救办法见 1.4 节。

### 1.1 规则一：一个提交只做一件事

**判据**：这个提交是否服务于**一个可解释、可验证、可回退的逻辑目标**？
是 → 合格；夹带了**无关目标** → 拆开。

**要分清"一个目标"和"一个文件"**：

| 情形 | 该不该拆 | 为什么 |
|---|---|---|
| 修复一个 bug + 补上守护它的回归测试 | **不拆** | 测试是这次修复的验收证据，拆开会让修改与守护脱节 |
| 修复一个 bug + 顺手把 README 里的错别字改了 | **拆** | 两件事互不依赖，回退其一不该牵动另一件 |
| 移动目录 + 为保持可运行而同步改 import/调用路径 | **不拆** | 属于同一次结构调整；不同步改，程序就是坏的 |
| 移动目录 + 顺便重构了某个函数的内部实现 | **拆** | 后者是功能改动，与"搬家"无关 |

> **⚠️ 连词不是硬判据。** 说明里出现"和/也/以及/顺便"只是**提示复核**，
> 不是自动拆分的理由——上面第一行就带"和"，却应当是一个提交。
> **按目的判断，不要按字面或文件数量判断。**

| ✅ 合格 | ❌ 不合格 |
|---|---|
| `docs(operations): 增加提交粒度规则与真实反例` | `docs: 更新文档和配置，顺便删掉旧文件` |
| `fix(router): 修复优先队列等代价崩溃` | `fix: 修几个 bug` |
| `chore: 移除根目录课程课件` | `chore: 整理项目结构` |
| `feat(web): 增加搜索动画控制条` | `feat: 前端改完了` |

**为什么重要**：提交粒度决定出问题时能不能快速定位，
**以及能不能只回退其中一件事**。一个提交改了 20 个互不相关的文件，
事后既说不清"影响了什么"，也无法单独撤回其中一项。

### 1.2 规则二：结构性改动单独提交

**"结构性改动"** 指重命名、移动文件/目录、批量删除。这类改动会让 `git log --stat` 充满 `旧路径 => 新路径`，**把真实内容改动淹没**。

**做法**：先单独提交一次"只移动/只改名"，再提交内容修改。

```powershell
# 第一次提交：只移动，不改内容
#   ⚠️ 不要用无路径的 `git add -A`——它会把工作区里所有未跟踪文件
#   （本机草稿、下载的数据、临时脚本）一起暂存进来。
#   只暂存这次确实要移动的路径。
git add docs/development docs/project docs/learning
git status --short                       # 确认清单里只有预期文件
git commit -m "refactor(docs): 按功能将文档归入六个分类目录"

# 第二次提交：再改内容
git add docs/development/路径规划模块开发说明.md
git commit -m "docs(development): 同步代码现状，补充已知限制"
```

> 重命名用 `git mv 旧路径 新路径`，Git 会识别为 rename，历史更清晰。
>
> **例外**：像本项目"源码移入 `src/`"这种改动，移动与引用更新**必须在同一个提交里**
> ——只移动不改 import，程序就是坏的，那个提交无法单独通过测试。
> 这类"原子结构调整"应整体提交，并在说明里写清两部分内容。

### 1.3 规则三：说明写"为什么和影响什么"，不只写"做了什么"

**第一行必须让人看懂"改了什么"；正文按情况补"为什么改、影响什么、怎么验证"。**

| 改动性质 | 说明要求 |
|---|---|
| 新增功能、纯文档、配置 | **第一行写清做了什么即可** |
| **修 bug、性能改动、结构性改动、任何会改变接口或行为的改动** | **正文必须补上：为什么改、怎么验证的、影响谁** |
| 涉及决策取舍的改动 | 正文补一句"否决了什么方案、为什么" |

> **为什么不是"一律都写"**：正文写厚了没人读，写薄了出事查不到。
> 上面的分档是**按出错代价**定的——改错一个常量能被立刻发现，
> 改错一个启发式函数或搜索终止条件却**不报错、只给错结果**，
> 那种改动必须留下推理过程。

正文推荐四段式（项目内 33 个提交的既有写法）：

```text
为什么：
<当时遇到了什么问题；不复现会怎样>

改了什么：
<关键改动点；有取舍的地方写清>

验证：
<跑了什么、结果是什么；没能验证的部分要明说>

影响：
<接口/数据/他人需要跟着改的地方；没有就写"无">
```

**第一行格式**：`类型(范围): 动词开头的简短说明`

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat` | 新增功能 | `feat(a3/ch): 实现捷径边双向查询` |
| `fix` | 修复错误 | `fix(a2/search): 处理起终点相同的情况` |
| `perf` | 性能改进 | `perf(a3/ch): 减少查询阶段的临时对象` |
| `refactor` | 不改变外部行为的结构调整 | `refactor(a1/graph): 简化边加载逻辑` |
| `test` | 测试与基准 | `test(a5): 补充有向图固定用例` |
| `docs` | 文档 | `docs(operations): 增加双层工作区制度` |
| `chore` | 构建、配置、依赖 | `chore: 忽略本机调试脚本` |
| `revert` | 撤回已有提交 | `revert: 撤回误合并的基准数据` |

**禁止**：`update`、`fix bug`、`改了一下`、`最终版`、`111`、`第二次提交`——这些说明在半年后没有任何追溯价值。

> **范围写不写？** 小项目可省略。写的时候指向**模块或角色**（`router`、`a3/ch`、`operations`），
> 不要写人名——人会换、角色会调，**目录和模块不会**（见第 10 节）。

### 1.4 补救：已经提交了才发现混了多件事

**判据**：`git show --stat <提交>` 里有**两个以上互不相关的目录**，就属于混提交。

按"推到哪了"分三种情况，**代价从低到高**：

#### 情况一：还没推送 → 软回退重提（最简单）

```powershell
git reset --soft HEAD~1          # 撤销提交，改动全部回到暂存区
git restore --staged .           # 取消暂存，逐个挑
git add 文件组A ; git commit -m "第一件事"
git add 文件组B ; git commit -m "第二件事"
```

#### 情况二：已推送到自己的 Fork → 本地重排后强推**自己的分支**

```powershell
git rebase -i HEAD~3             # 把 pick 改成 edit，逐个拆分
# 或在 reset --soft 后重提，再：
git push --force-with-lease origin 你的分支名
```

**只允许强推自己 Fork 上的任务分支**，绝不能碰 `main` 与 `upstream`。

#### 情况三：已合并进共享 main → 先停下，走流程

**不要自己动手改共享历史。** 按顺序做：

1. 在 Issue 里说明"哪个提交混了什么"，评估影响范围
2. 若只是说明不好看、内容没问题 → **不值得改**，接受它
3. 若确实需要拆（例如某项改动要单独 revert）→ **找仓库管理员**，
   由管理员按 §7 的例外条款处理

> **判断标准**：拆历史的代价是"所有人要重置仓库"。
> 如果只是"看着不整齐"，**代价远大于收益**。
> 只有当混提交**阻碍了正常操作**（无法单独回退、无法定位问题）时才值得拆。

### 1.5 真实反例：一次提交塞了五件事

**事件**：2026-09-27 的一次提交，说明写的是"新增五角色学习路线"，实际包含 **23 个文件、+1559 / -39 行**，混了五类互不相关的改动：

| 实际包含 | 行数 |
|---|---|
| 新增协作手册 | +475 |
| 新增编译验证记录 | +147 |
| 新增学习指南 | +216 |
| 新增学习路线（**说明里只提了这一项**） | +520 |
| 文档目录重组（大量重命名） | 多处 |
| 新增 `.github/` 模板与 `CHANGELOG.md` | +84 |
| 删除课程课件 | **-618 KB** |

**后果**：

1. **GitHub 仓库首页每个文件右侧显示"最后一次改动它的提交说明"**。这一次提交改了 23 个文件，于是这 23 个文件旁边**全挂着同一句"新增五角色学习路线"**——包括那些和它毫无关系的文件。这正是"提交说明看起来都一样"的直接原因。
2. 想查"文档分类什么时候改的"或"课件什么时候删的"，只能逐个翻 diff。
3. 想撤回其中某一项（比如课件删除）**无法单独撤回**，必须整体 revert，把无关改动一起回退。

**按规则一应拆成 6 次提交**：

```text
chore: 添加 Issue 与 PR 模板
docs(operations): 新增团队协作手册
docs(validation): 新增开源项目编译验证记录
refactor(docs): 按功能将文档归入六个分类目录
docs(learning): 新增五角色学习路线
chore: 移除根目录课程课件
```

**记住**：提交粒度不是洁癖，是**出事时能不能快速定位**的差别。

### 1.6 后续处理：混在一起的提交已拆分（2026-09-29）

上面那个反例最初只被"改写了提交说明"，但**问题并没有解决**——
因为根因不是说明写得不好，而是**提交本身就混了多件事**。
说明只能描述其中一件，其余文件看着就是"消息与文件对不上"。

后来用重放历史的方式把 4 个混提交拆成 10 个单一职责的提交，
提交总数 33 → 39。拆分前后同一个文件旁边显示的消息：

| 文件/目录 | 拆分前 | 拆分后 |
|---|---|---|
| `.github/` | `docs: 按模块重组文档目录，补协作规范与学习路线` | `chore: 添加 Issue 与 PR 模板` |
| `api/`、`tests/` | `refactor: 更新路网迁移后的引用并改名学习路线文件` | `refactor: 更新路网迁移后遗留的硬编码路径` |
| `README.md` | `test: 新增端到端接口冒烟测试与文件清单生成工具` | `docs: 精简 README 到"是什么、怎么跑、看哪里"` |

#### 拆分方法（可复用）

```powershell
# 按顺序重放历史，不碰工作区；每个拆分点用"索引回退"造出中间树
# 1) git read-tree <该提交的树>          索引 = 该提交的完整状态
# 2) git update-index --index-info ...  把"本批不提交"的文件改回父提交版本
# 3) git commit-tree $(git write-tree)  生成中间提交
```

两个必须做的断言（本次都靠它们提前发现问题）：

1. 本提交改动的每个文件都必须被某一组覆盖，否则报错——防止漏拆
2. 全部拆分完成后，**最终树必须与原提交的树完全一致**——防止拆错内容

> **踩过的坑**：脚本一开始在每组之后无条件追加一个"收尾提交"，
> 结果多出 9 个重复提交。干跑时那行日志只在有剩余文件时才打印，
> **所以干跑看不出来**，是比对提交数（33 → 42，预期 38）才发现的。
> **教训：干跑之外一定要核对计数，不能只看日志有没有报错。**

## 2. 双层工作区制度（本项目核心组织方式）

### 2.1 为什么是"双层"

个人在工作中会产生两种内容：

| 类型 | 特点 | 该放哪 |
|---|---|---|
| **阶段性的、不想全组看到的** | 草稿、实验、日报、个人工具、未完成的分析 | **不该进共享仓库** |
| **准备给全组看的成果** | 成果索引、结论、数据表、截图 | 该进共享仓库 |

**一层解决不了**：全放本机 → 队友看不到进展；全进共享仓库 → 个人内容被所有人看到。

所以用**两层**：

```text
第一层：本机草稿区（不推送）
   个人工作区/<成员代号>/

第二层：个人 Fork 里的成员工作区（推送，只有自己能改）
   member_workspaces/<成员代号>/

共享仓库（只有经过审查的成果才进来）
   docs/  path_planning/  api/  web/  tests/  data/  workspaces/<角色>/
```

### 2.2 仓库拓扑：共享仓库 + 每人 Fork

```text
        共享主仓库（upstream）
        github.com/<owner>/route-plan
                 ▲
                 │ PR（只有审查通过的成果）
                 │
   ┌─────────────┼─────────────┬─────────────┐
   │             │             │             │
 Fork A1      Fork A2       Fork A3       Fork A4 ...
（成员各自完整的仓库副本，可自由提交推送）
```

| 远端名 | 指向 | 用途 |
|---|---|---|
| `origin` | **自己的 Fork** | 日常提交推送，随便推，不影响别人 |
| `upstream` | **共享主仓库** | 同步别人的成果；只用来发 PR 和拉取更新 |

**关键性质**：往自己的 Fork 推送**不需要任何审查**，也不影响共享仓库的 `main`。
所以 `member_workspaces/` 里可以有半成品、多次迭代、甚至推翻重来。

#### ⚠️ Fork 不是私密空间（这一条最容易被误解）

"自己的 Fork"听起来像私人仓库，**不是**。GitHub 官方文档明确说明：

| 事实 | 含义 |
|---|---|
| **Fork 的可见性由上游决定**，不能单独修改 | **上游公开 → 你的 Fork 也是公开的**；上游私有 → Fork 私有 |
| **上游所有者可读取该网络内所有 Fork** | 你推到 Fork 的内容，共享仓库所有者看得到 |
| **同一 Fork 网络共享 Git 数据** | 任何仓库中的提交可能从同网络的其他仓库访问，**Fork 不等于隔离** |
| **权限继承要看仓库可见性** | 私有 Fork **继承上游的团队权限**（**个人权限不继承**）；公开 Fork **不继承**上游权限结构，由各 Fork 所有者自己控制 |
| 私有仓库被移除访问权时，其私有 Fork **会被删除** | Fork **不能当唯一备份** |

> **别把"整个网络内所有人权限相同"当结论**：
> 公开与私有的继承规则不同，团队权限与个人权限也不同。
> 唯一可以放心的一条是——**Fork 不是用来保密的**。

**所以**：

- `member_workspaces/` 的作用是**不打扰队友、不污染 `main`**，**不是保密**
- 不要往里放凭据、密钥、不该公开的材料、未获授权的数据
- **"不想让全组看到"的内容放本机第一层**（`个人工作区/`，被 `.gitignore` 排除），
  或干脆不要写下来
- 阶段成果要留痕时，**Fork 之外再留一份本机备份**

### 2.3 第一层：本机草稿区

每人克隆后在本机项目根目录建 `个人工作区/<角色>/`。**已被 `.gitignore` 排除，不会推送。**

用途：收件箱、临时实验、日报、未整理笔记、个人工具。

参考结构（可自行调整）：

```text
个人工作区/A3/
├── 00_收件箱/        收到但还没分类的文件
├── 01_学习草稿/
├── 02_代码实验/
├── 03_报告草稿/
├── 99_归档/
```

> **它不是备份，也不进版本控制。** 需要留痕的内容必须进入第二层或共享仓库。
> 现存的 `A3_临时工作区/` 仍被忽略，A3 可继续使用，确认内容后再迁入统一目录。

### 2.4 第二层：Fork 里的成员工作区

每人在**自己的 Fork** 里维护 `member_workspaces/<成员代号>/`。

**这是"工作一段时间后更新一次"的地方**：阶段性提交推送只更新自己的 Fork，队友不会被打扰，共享仓库的 `main` 也不受影响。

**再强调一次这是设计意图，不是缺陷**：Fork 工作区里可以有半成品。它的作用是**留痕**——让别人知道你在做什么、做到哪一步，但不要求可交付。

#### 2.4.1 两条分支，各管一件事（**必须分开**）

这是本项目最容易做错的地方：**用一条分支既装阶段成果又提 PR**，
结果 PR 里混进了不该交付的草稿文件。

| 分支 | 从哪里建 | 往哪推 | 提 PR 吗 | 装什么 |
|---|---|---|---|---|
| **`workspace/<成员>`** | 自己 Fork 的 `main` | **只推自己的 Fork**（`origin`） | **不提** | 阶段记录、草稿、实验、日报 |
| **`feature/<成员>-<任务>`** | **`upstream/main`** | 先推自己的 Fork，再向 `upstream` 发 PR | **提** | **只装准备交付的文件** |

**为什么必须分开**：`.gitignore` **只能阻止未跟踪的文件进入 Git**，
**无法把已经提交过的文件从 PR 中排除**。
如果阶段成果和交付成果在同一条分支上，PR 就会带上 `member_workspaces/` 里的草稿——
这是**改 `.gitignore` 也救不了**的。

```powershell
# ===== 分支一：工作痕迹，只推自己 Fork，不提 PR =====
git switch main
git switch -c workspace/A3
# … 阶段内容写进 member_workspaces/A3/ …
git add member_workspaces/A3/
git commit -m "chore(workspace): A3 第一周实验记录"
git push origin workspace/A3          # 只推自己的 Fork

# ===== 分支二：交付，从上游 main 建，只装该交的文件 =====
git fetch upstream
git switch -c feature/A3-ch-query upstream/main
# … 只动要交付的文件 …
git add path_planning/ch.py
git add tests/test_ch.py
git diff --cached --stat               # ✅ 确认清单里没有 member_workspaces/
git commit -m "feat(a3/ch): 实现捷径边双向查询"
git push -u origin feature/A3-ch-query
# 然后在网页上向 upstream 的 main 发 PR
```

> **发 PR 前的固定动作**：`git diff --cached --stat` 看一遍清单，
> 确认**没有 `member_workspaces/`、`个人工作区/`、缓存、大文件**。
> PR 模板里也有对应检查项（见 `.github/PULL_REQUEST_TEMPLATE.md`）。

### 2.5 共享仓库里的角色成果区

共享仓库另有 `workspaces/<角色>/`，用途与 Fork 工作区**不同**：

| | Fork 里的 `member_workspaces/` | 共享仓库里的 `workspaces/` |
|---|---|---|
| 谁看得到 | **上游所有者与该网络内的协作者**（Fork 不是私密空间，见 §2.2） | 全组 |
| 内容 | 阶段性的、未整理的 | **准备给别人看的成果** |
| 质量要求 | 无 | 能被非作者读懂 |
| 更新频率 | 随意 | 阶段性更新 |
| 进入方式 | 推自己 Fork 的 `workspace/<成员>` 分支 | 从 `upstream/main` 建 `feature/` 分支发 PR |

**一句话**：Fork 工作区是**我的工作痕迹**，共享仓库的成果区是**给别人的成果交付**。

#### 2.5.1 `member_workspaces/` 要不要进 `.gitignore`？

**不进。** 它是 Fork 里要**提交并推送**的内容，忽略它就推不上去了。

> **更正一处错误解释**：本文档曾写"共享仓库的 `.gitignore` 管不到 Fork"——
> **这不准确**。`.gitignore` 就是一个普通仓库文件，Fork/克隆之后
> **在该工作区里照样生效**。它依据**路径**与**文件是否已被跟踪**工作，
> 与 `origin`/`upstream` 指向谁无关。
>
> 所以"不忽略它"的真正理由不是"规则管不到"，而是
> **"我们就是要提交它"**——这是内容决定，不是权限决定。

| 目录 | 在哪 | 是否忽略 | 理由 |
|---|---|---|---|
| `个人工作区/` | **本机**（共享仓库工作区里） | ✅ 已忽略 | 是本机草稿，绝不该提交 |
| `member_workspaces/` | **各自的 Fork** | ❌ 不忽略 | 是 Fork 里要**提交推送**进去的内容 |
| `A3_临时工作区/` | 本机 | ✅ 已忽略 | 历史遗留，见 §2.3 |

> **真正防止草稿混进 PR 的办法是 §2.4.1 的两条分支，不是忽略规则。**
> 因为 `.gitignore` **挡不住已经提交过的文件**——它只影响未跟踪文件。

`workspaces/` 下按角色定制结构。每个角色的产出形态不同，不强求一致。

### 3.1 A1 数据线

```text
workspaces/A1_数据/
├── README.md            # 角色职责 + 成果索引 + 当前状态
├── 01_路网清单/          # 每个数据集一张卡片：规模、来源、许可、生成命令

├── 03_数据质量/          # 连通性、孤立节点、几何缺失率等体检结论
├── 04_接口对接说明/      # 与上下游的接口契约、变更流程、常见误用
└── 05_文档报告/          # 数据相关的正式报告
```

**成果核心**：让人**看懂数据是什么**。实际数据文件放 `/data/`，这里放索引与结论。

### 3.2 A2 算法正确线

```text
workspaces/A2_算法/
├── README.md
├── 01_实现清单/          # 每个算法：状态、入口函数、复杂度、已知边界
├── 02_正确性证据/        # 对拍结果、边界用例、与标准实现的差异
├── 03_算法对比/          # 各算法在固定查询集上的差异
└── 04_文档报告/          # 算法设计与验证报告
```

**成果核心**：**凭什么说它是对的**。对拍数据表比代码更重要。

### 3.3 A3 性能与测试线

```text
workspaces/A3_性能/
├── README.md
├── 01_基准方法/          # 查询集定义、测量规程、如何复现
├── 02_基准结果/          # 实测数据表（p50/p95/max、扩展状态数）
├── 03_实验结果/          # CH 预处理、加速比、消融实验、适用边界
├── 04_测试结果/          # 测试清单、覆盖矩阵、回归结果、已知盲区
└── 05_文档报告/          # 性能测试报告、测试报告
```

**成果核心**：**数字是怎么来的** + **"测试通过"不等于"程序正确"**。
本角色负责**测试策略与集成回归**，必须如实记录测试盲区，而不只是贴一张全绿截图。

#### 3.3.1 测试职责边界（A3 不是"唯一的测试员"）

**容易搞错的一点**：说"A3 负责测试"**不等于**"只有 A3 能写、能跑测试"。
那样会让 A3 变成**合并瓶颈**——所有人都等他验证，他一忙整条线就停。

| 谁 | 负责什么 |
|---|---|
| **每位代码作者** | **验证自己的改动**：跑相关测试，并**为修复/新功能补上对应测试**（见 §3.7）。这是**提交前**的动作，不是等别人来验 |
| **任何成员** | 都可以运行测试，也可以在审查 PR 时跑；发现问题直接提 |
| **A3** | 测试**策略**（怎么测、测什么、用什么基准）、**集成回归**（改动汇总后整体跑一遍）、**性能基准**、记录**覆盖矩阵与已知盲区** |

**A3 的准入线**：只在"**汇入 main 之前**"和"**性能数字**"这两件事上当守门人。
日常开发中，作者自己的验证是**第一道也是必须的一道**。

**哪些 PR 需要 A3（或同等能力的替代审查人）复核**——按改动风险分档，
**不是所有 PR 都等他**：

| 改动类型 | 谁必须看 | 说明 |
|---|---|---|
| **算法正确性、启发式、搜索终止条件** | 非作者的算法/测试同伴 | 看对拍与边界证据；作者是该项负责人时，找另一位懂算法的 |
| **性能结论、CH 预处理与查询、基准数字** | **A3 或具备相应能力的替代人** | 作者为 A3 时，**必须由非作者**复核 |
| **数据字段、单位、坐标系、API 响应变更** | **至少相关接口消费者**参与确认 | 光"通知"不算确认；要说明迁移方式 |
| 文档措辞、注释、个人阶段记录 | **任意一位非作者**即可 | 不需要 A3 参与 |
| 前端界面、演示材料 | 任意非作者 + 素材来源负责人核对数字 | 不让 A3 成为演示材料的瓶颈 |

> **替代审查人**：A3 忙或不在时，由协调者指定**另一位有能力判断该风险的人**，
> **不能把"无人回复"当成批准**（见 §12.3 的等待与阻塞）。

> **一句话**：A3 负责"**测的方法与整体结论**"，
> 每位作者负责"**我这次改动是对的**"。两者都不是可选项。

### 3.4 A4 交互线

```text
workspaces/A4_交互/
├── README.md
├── 00_前端源代码/        # 源码索引（代码本体在 /web/，不复制副本）
├── 01_界面说明/          # 每个页面：功能、操作步骤、依赖什么数据
├── 02_演示流程/          # 界面侧的操作步骤与可演示性（与 A5 协作）
├── 03_可视化结果/        # 截图、录屏、动画片段
└── 04_文档报告/          # 界面设计与实现说明
```

**成果核心**：**能被"看"到**。截图与录屏的价值高于代码说明。

### 3.5 A5 演示材料线
```text
workspaces/A5_演示/
├── README.md
├── 01_PPT与讲稿/         # 四次汇报 + 最终答辩的幻灯片与讲稿
├── 02_视觉设计/          # 界面视觉与交互建议（交 A4 实现）
└── 03_素材收集/          # 从其他角色成果区汇集的图表、截图、数据
```

**成果核心**：**把全组成果讲出来**。本角色负责 PPT 与辅助前端设计，
**不写前端代码**（前端实现在 A4）；**不承担测试职责**（策略与集成回归在 A3，
各自改动的验证由作者本人负责，见 §3.3.1）。
每份演示材料都要含"预判提问"与"失败备用方案"。

### 3.6 一条防重复规则

**同一个文件只能有一个正式位置。**

| 放成果区 ✅ | 放正式目录 ❌ |
|---|---|
| 成果索引（README） | 代码副本（代码在 `path_planning/`） |
| 数据表格、结论 | 正式文档副本（文档在 `docs/`） |
| 截图、说明材料 | 大体积原始数据（数据在 `data/`） |

判断方法：**"其他角色需要读代码才能看懂吗？"** 需要 → 正式目录；不需要 → 成果区。
需要引用时用**相对链接**指过去，不要复制。

### 3.7 测试与验证的最低要求

**"测试通过"不等于"程序正确"。** 本项目有实测证据：
曾出现过 **56 个测试全绿、真实路网上崩溃率仍有 55.5%** 的情况。

| 改动类型 | 最低要求 |
|---|---|
| **修复一个 bug** | **必须补一个在修复前会失败的测试**——否则无法证明修好了，也无法防止复发 |
| 新增算法 | 与基准算法**对拍**：比较**路径代价**，不是比较边序列（等代价时两条路都对） |
| 改动搜索循环、代价模型、启发式 | 必须重跑对拍与一致性校验；这类改动**不报错、只给错结果** |
| 改动前端或接口 | 跑 `python tools/smoke_api.py`（真实 HTTP，43 项） |
| 改文档结构、目录、角色区 | 跑 `python tools/check_docs.py`（围栏配对、目录树一致性） |
| 新增数据 | 记录来源、许可、规模与已知缺陷；不可达点等问题要写进数据说明 |

**测试报告要如实记录盲区**（哪些场景没被测到），而不是只贴一张全绿截图。
成果区的 `04_测试结果/` 专门放这个。

> **一句话判据**：如果这个改动错了，**出错时会不会抛异常**？
> 不会（只给错结果）→ 必须写测试守住它。

## 5. 标准工作流程

### 5.1 一次性准备（每人做一次）

#### 5.1.1 配置本机提交身份（每台电脑做一次）

Git 使用提交身份标注 Commit 作者。**本项目只用 GitHub 提供的 `noreply` 邮箱；不要把注册邮箱或个人邮箱配置为 `user.email`。**

1. 登录 GitHub，点击头像 → `Settings` → `Emails`。
2. 勾选 `Keep my email addresses private`；建议同时勾选 `Block command line pushes that expose my email`。
3. 在同一页面复制 GitHub 显示的完整 `noreply` 邮箱。地址可能含数字 ID 和用户名，也可能是旧格式；照抄自己页面上的地址，不要手动拼接或照抄队友的。
4. 在 PowerShell 中配置姓名和邮箱。`YOUR_NOREPLY_ADDRESS` 必须替换成刚复制的地址；姓名按组内约定使用小写缩写，例如 `wc`。

```powershell
git config --global user.name "wc"
git config --global user.email "YOUR_NOREPLY_ADDRESS"
```

**5. 在项目目录里核对"实际生效"的身份，而不是只看 global 值。**

`--global` 只是三层配置（system / global / 仓库本地）中的一层，
**仓库本地配置会覆盖它**，所以查 global 并不能证明这个仓库的提交用了什么身份。

```powershell
# 在仓库目录里执行（不是随便哪个目录）
git config --show-origin --get user.email   # 显示这个值来自哪个配置文件
git var GIT_AUTHOR_IDENT                    # 显示"下一次提交实际会用"的作者身份
```

- `git config --show-origin` 会告诉你值来自 `global` 还是 `.git/config`（本地）
- `git var GIT_AUTHOR_IDENT` 是**实际会写进提交**的姓名与邮箱
  ——**以它为准**

若本地配置是旧邮箱，清掉它让 global 生效：

```powershell
git config --unset user.email      # 只影响当前仓库
```

> **每人用自己账号的 noreply 地址**，不要共用某位成员的用户名或邮箱
> （否则两个人的提交在统计里会混成一个人）。

GitHub 官方步骤见[设置提交邮箱](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)和[邮箱地址说明](https://docs.github.com/en/account-and-profile/concepts/email-addresses)。

#### 5.1.2 Fork 并配置远端（每人做一次）

```powershell
# 1. 在 GitHub 网页上 Fork 共享仓库到自己账号

# 2. 克隆自己的 Fork
git clone https://github.com/<你的用户名>/route-plan.git
Set-Location route-plan

# 3. 添加共享仓库为 upstream
git remote add upstream https://github.com/<owner>/route-plan.git
git remote -v
```

### 5.2 每项任务的闭环

```text
① 建 Issue（负责人、目标、验收条件、涉及模块、最终交付位置）
② 同步 upstream 最新 main，从它建【交付分支】feature/<成员>-<任务>
③ 阶段实验走另一条分支 workspace/<成员>，只推自己 Fork，不提 PR
   （两条分支为什么必须分开，见 §2.4.1）
④ 交付内容整理好，提交到共享仓库的对应位置
⑤ 发 PR 前查【整分支差异】（不是暂存区，见 §5.3）；推分支 → 向 upstream 发 PR
⑥ 至少一位非作者审查 → 合并 main
```

**CHANGELOG 什么时候写**（此前主规则与 PR 模板说法不一致，现统一为前者）：

| 情形 | 做法 |
|---|---|
| 该改动**需要被别人知道**（接口/数据/行为变更、重要修复、性能结论） | **随这个 PR 一起写进 `Unreleased`**，审查时一并看 |
| 纯内部整理、措辞修正、个人阶段记录 | **不必写**——提交与 PR 已经留痕 |
| 阶段性汇总（如"作业 1 完成"） | 需要时由负责人**另开一个 PR** 单独写 |

> **判断标准**：**"别人不看我这个 PR，会不会因此做错事？"**
> 会 → 写进 CHANGELOG；不会 → 不写。
> 不要为了凑条目而写，也不要漏掉会影响到别人的变更。

### 5.3 命令流程

```powershell
# 开始前同步
git status --short --branch
git switch main
git pull --ff-only upstream main

# 建【交付分支】：从 upstream/main 建，不要从 workspace/<成员> 建
git switch -c feature/a3-ch-query upstream/main

# 改完先看差异
git status --short
git diff --check
git diff

# 只暂存本次任务的文件（不要习惯性 git add .）
git add src/path_planning/router.py
git add tests/test_router_regressions.py
git diff --cached --stat
git diff --cached

# 按"一件事"提交
git commit -m "perf(a3/ch): 减少查询阶段的临时对象"

# ★ 提交之后、发 PR 之前：检查【整个分支】，而不是暂存区 ★
#   暂存区此时已空，`git diff --cached` 可能什么都看不到，
#   但分支上可能已经带着草稿提交（见下方说明）
git fetch upstream
git diff --name-status upstream/main...HEAD
git log --oneline upstream/main..HEAD
git diff --check upstream/main...HEAD

# 推到自己的 Fork
git push -u origin feature/a3-ch-query

# 在 GitHub 网页上向 upstream 发 PR
```

> **⚠️ 为什么必须检查整个分支**
>
> `git diff --cached --stat` **只比较"暂存区 vs HEAD"**，它是**每次 commit 前**该做的检查。
> 一旦内容已经提交、暂存区为空，它可能**没有任何输出**——
> 即使你的分支上已经带着 `member_workspaces/` 草稿。
>
> **反例**：第一次提交误加了 `member_workspaces/A3/`，第二次提交是正常代码。
> 两次提交后查暂存区，清单是空的；但发 PR 时，草稿仍在分支差异里。
>
> `git diff --name-status upstream/main...HEAD`（三点，注意是三个点）
> 比较的是"分支相对上游基线改了什么"，才能回答"这次要合入什么"。
> 两者配合：**提交前看暂存区，发 PR 前看整分支。**

**阶段成果走另一条分支**（不进 PR）：

```powershell
# 第一次：从自己 Fork 的 main 创建
git switch main
git switch -c workspace/A3

# 以后每次复用同一条分支（再用 -c 会报"分支已存在"）
git switch workspace/A3

git add member_workspaces/A3/
git commit -m "chore(workspace): A3 本周实验记录"
git push origin workspace/A3          # 只推自己 Fork
```

> **注意基点是哪条分支**：`git switch -c <新分支>` **不带基点**时，
> 是从**当前所在分支**分出去。上面显式先 `git switch main` 再创建，
> 就是为了避免"刚好停在 workspace 分支上、结果把它当成基点"。
>
> **切换分支会切换受跟踪的文件**：`member_workspaces/A3/` 会随分支出现或消失，
> 这是正常的。**交付时只挑成熟内容放进正式目录，不要把整条阶段分支 merge 进交付分支。**

**提交前的固定动作**：跑测试。

```powershell
python -m unittest discover -s tests -v
```

## 6. 文件、数据与安全

1. **不提交** `.env`、密码、Token、API Key、含凭据的配置。放本机环境变量或被忽略的本地配置，并提供不含秘密的示例。
2. **地图数据、课件、第三方源码**上传前先确认授权、许可证、体积和课程要求。优先提交**下载/处理脚本 + 字段说明 + 小型可公开样例**。
3. **`.gitignore` 只能阻止未跟踪文件进入 Git；它不能从历史中清除已提交的内容。** 若敏感内容已推送：先轮换凭据，再通知仓库负责人处理历史，**不要自行强推改写共享历史**。
4. **仓库权限是仓库级别，不是文件夹级别。** 提交到远程仓库后，获得访问权的成员通常都能读到。**不要依赖文件夹名称保密。** 需要真正隔离的内容应放在独立且权限受控的位置。
5. 临时结果放本机忽略目录；要共享时提交**可复现脚本 + 小型汇总 + 数据来源**，不要提交无法解释的二进制产物。

> **本项目已有教训**：一次提交里删除了课程课件，但该文件**仍在更早的提交历史中**。
> 删文件不会让历史里的内容消失。涉及授权的内容必须在**首次公开前**决定处理方式。

## 7. 明确禁止的操作

- 不直接在共享仓库的 `main` 上修改、Commit 或 Push。
- 不对共享分支运行 `git push --force` 或 `--force-with-lease`。
- 不运行 `git reset --hard`、`git clean -fd`、`git checkout .` 来"试着修好"。
- **不用 `git restore <路径>` / `git checkout <路径>` 去覆盖有未提交改动的工作区文件**
  ——它会直接丢弃该文件的内容且无法恢复。执行前先看 `git status`。

  **要分清三种情况**（原文档把它们混为一谈，是错的）：

  | 命令 | 作用对象 | 默认恢复来源 | 危险吗 |
  |---|---|---|---|
  | `git restore --staged -- <路径>` | 暂存区 | **HEAD** | ✅ 安全，工作区文件不动 |
  | `git restore <路径>` | **工作区** | **暂存区**（不是 HEAD！） | ⚠️ 危险，丢弃未暂存改动 |
  | `git switch <分支>` | — | — | ⚠️ 未提交改动通常被带走；与目标分支冲突时才拒绝切换 |

  **要点**：`git restore <路径>` 的默认来源是**暂存区**。
  只有暂存区与 HEAD 恰好一致时，"恢复为 HEAD"与"恢复为暂存区"才结果相同
  ——这正是它容易写错的原因（本项目实测验证过：
  HEAD=A、暂存区=B、工作区=C 时，该命令把工作区变成 **B**）。
  要指定来源必须显式写 `--source=<提交>`。
- 不用 `git add .` 代替逐项检查，不提交未经确认的删除、课件、缓存、大数据、密钥。
- 不把同一份文件放在两个位置（正式目录 + 成果区副本）。
- 不在未通知的情况下改动其他角色负责的接口、单位约定或数据契约。
- 不把未经验证的结果写成"已通过"。
- 不把 GitHub 密码、令牌、API Key 发到 Issue、PR、代码、日志或群聊。

### 7.1 唯一的例外：仓库管理员维护历史

上面"不对共享分支强推"是**默认规则**。但它有一个**严格限定的例外**：
仓库管理员在**首次公开前、且尚无其他协作者**时，为清理历史而改写并强推 `main`。

**为什么必须有这个例外**：本项目真实发生过两次——

| 时间 | 起因 | 做了什么 |
|---|---|---|
| 2026-09-29 | 早期提交含课程课件，删文件不能让历史里的内容消失 | 用 `git filter-repo` 移除课件，强推 main |
| 2026-09-29 | 多个提交混了不相关改动，导致文件列表消息错配 | 重放历史拆成单一职责提交，再次强推 main |

规则如果写"绝对禁止"，这两次就成了"违规操作"；而它们确实是**正确处理**
（课件地址实测返回 404）。**规则要能描述正确做法，不能把正确做法定义成违规。**

#### 允许的四个前提（缺一不可）

| 前提 | 怎么确认 | 这部分证据**不能**证明什么 |
|---|---|---|
| 1. **有可用备份** | `git bundle create 备份.bundle main` + `git bundle verify` | bundle **只覆盖从 `main` 可达的历史**；其他独立分支、未提交与未跟踪文件**不在其中**，需另外保存 |
| 2. **无他人未推送成果** | **逐一问过**有访问权的成员并得到回复 | `git log upstream/main --pretty=%an` **只能看到该引用上的提交作者**——发现不了别人的本地分支、未提交文件和未推送成果。**不能用作者列表替代询问** |
| 3. **受影响者明确同意** | 需要动手的人**逐一确认**；未回复**不等于**同意 | "群里发过通知、没人反对"**不算**确认（有人可能没看到） |
| 4. **改写后立即恢复防护** | 强推完成后**立刻**把规则集设回 `Active`（见 §9.1） | 页面显示"已保存"不等于核验过，按 §8.9 的表逐项看 |

> **适用范围**：这套前提**只用于破坏性维护**（改写已发布的历史）。
> 日常 PR、合并、回退都**不需要**走这套审批。

#### 推送用带期望值的 lease，不要裸强推

首版写的是"先 `git ls-remote` 核对、再用 `--force`"。这有个**竞争窗口**：
读取 SHA 与推送之间，远端仍可能产生新提交，而裸 `--force` 会**覆盖掉它**。

**正确做法**：把刚才读到的 SHA 作为期望值交给 `--force-with-lease`，
由 git 在推送那一刻核对。它**不依赖** filter-repo 是否保留了远程跟踪引用
（首版"跟踪引用被删所以只能裸强推"的推论**不成立**）：

```powershell
# 1) 记下当前远端 main 的 SHA
git ls-remote upstream main

# 2) 推送时带上期望 SHA —— 若远端已变，推送被拒绝而不是覆盖
git push --force-with-lease=refs/heads/main:<刚才记下的SHA> upstream main
```

#### 必须避开的做法

- **不要在有协作者已提交成果时改写**——他们的本地仓库会与远程失联，
  且**一推送就把被清理的内容推回来**
- **不要用裸 `--force`**（见上）
- **不要在改写后忘记恢复规则集**——本项目真实发生过：规则集被关闭后未及时恢复，
  期间任何有写权限的人都能绕过 PR 直接强推 `main`
- **不要宣称"服务端已彻底删除"**。单个链接 404 只能证明**那个链接**当前访问不到；
  Fork、他人克隆、PR 引用与平台缓存都不在验证范围内。
  报告时只说**实际验证过的访问结果**。GitHub Support 的清理协助有适用条件，
  **不能写成对任意课程文件的删除保证**

#### 改成"改历史"之前，先考虑更便宜的做法

**已经进了团队协作阶段的项目，优先用新增修正提交或针对性 `git revert`。**
只有"说明不好看"这一条，**不构成**改写共享历史的理由——
代价是所有人要重置仓库，收益只是整齐。

真正的数据泄露（凭据、未授权材料）另走协调处置流程，不由个人决定。

#### 非管理员遇到同样问题怎么办

**不要自己动手。** 按 §1.4 情况三处理：写进 Issue、评估影响、
**联系仓库管理员**。若只是"看着不整齐"，接受它比改写更划算。

## 8. 常见问题

### 8.1 提交后发现说明写错了（还没推送）

```powershell
git commit --amend -m "修正后的说明"
```

### 8.2 提交后发现漏了文件（还没推送）

```powershell
git add 漏掉的文件
git commit --amend --no-edit
```

### 8.3 已经推送了，想撤回

**不要重写历史**。用 `git revert` 生成反向提交，通过 PR 合并：

```powershell
git log --oneline
git revert <提交号>
```

### 8.4 推送被拒（远端有新提交）

```powershell
git fetch upstream
git switch main
git pull --ff-only upstream main
git switch feature/你的分支
git merge main
```

有冲突时逐段处理 `<<<<<<<` / `=======` / `>>>>>>>`，跑测试，再 `git add` 并完成提交。
不确定哪边对就**停下来找对方一起看**；未完成时可 `git merge --abort`。

### 8.5 想丢弃某文件的未提交修改

**两个命令作用对象不同，先看清你要哪个：**

```powershell
# 只取消暂存：把文件移出暂存区，来源是 HEAD；工作区文件一点不动（安全）
git restore --staged -- 路径/文件

# 覆盖工作区文件：来源默认是【暂存区】，未暂存改动永久丢失（危险）
git restore -- 路径/文件              # ⚠️ 执行前务必确认 git status

# 若确实要恢复成 HEAD 版本（而不是暂存区版本），必须显式指定来源
git restore --source=HEAD -- 路径/文件
```

> **最容易搞错的一点**：`git restore <路径>` 默认从**暂存区**恢复，不是从 HEAD。
> 如果这个文件刚 `git add` 过、之后又改了，那么执行它会把文件变回
> **你暂存的那一版**，而不是仓库里那一版。两者只在"暂存区恰好等于 HEAD"时才一样。

### 8.6 误把 Token 或密钥推上去

立即撤销/轮换凭据，通知仓库负责人。**只删文件或新增提交并不能让历史中的秘密消失**；
不要自行强推改写共享历史。

### 8.7 内容和位置该放哪一层

按顺序问三个问题：

1. **需要读代码才能看懂吗？** → 是，放 `path_planning/` 等代码目录
2. **是准备给全组看的成果吗？** → 是，放共享仓库的 `workspaces/<角色>/` 或 `docs/`
3. **只是阶段性的、还在变？** → 推到自己 Fork 的 `member_workspaces/`

### 8.8 推送被拒，说违反了仓库规则（GH013）

**现象**：

```text
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Cannot force-push to this branch
remote: - Changes must be made through a pull request.
```

**这不是你操作错了，是规则集在正常工作。** 说明你试图直接改动 `main`。

| 你做了什么 | 正确做法 |
|---|---|
| 直接 `git push origin main` | 改推自己的任务分支，然后开 PR |
| `git push --force origin main` | **不该做**。若确实需要（见 §7.1 例外），找仓库管理员 |
| 往 main 推任何东西 | 一律走 `feature/xxx` 分支 + PR |

```powershell
# 正确流程
git switch -c feature/a3-你的任务
git push -u origin feature/a3-你的任务    # 推自己的 Fork 或 upstream 的分支
# 然后在网页上向 upstream 的 main 发 PR
```

### 8.9 我关闭过规则集，怎么确认已经恢复

**规则集被关闭期间，任何有写权限的人都能绕过 PR 直接强推 `main`。**
维护完成后必须立刻恢复，并**核对它真的生效**。

#### ⛔ 不要用"推一次 main 试试"来验证

这个做法**曾经写在本节里，已删除**。它看着像测试，实际有三个致命问题：

1. **它会真实写入远端 `main`。** 如果规则集还关着，这次推送会**成功**——
   等于"为了验证保护是否存在，先把 `main` 改掉了"
2. **成功之后无法保证还原。** 所谓"再推回本地 main"依赖"远端没有别人的新提交"，
   而这个前提在验证的那一刻**恰恰不成立**（正因为不知道远端状态才要验证）
3. **成员机器上 `origin` 通常是自己的 Fork，`upstream` 才是共享仓库**（见 §2.2）。
   推 `origin` 测的是自己 Fork 的规则，**验证不了共享仓库**

#### ✅ 正确做法：只读核对，不写任何东西

在 GitHub 网页上逐项核对，**记录核查日期与核对人**：

| 核对项 | 期望值 | 在哪看 |
|---|---|---|
| Enforcement status | `Active` | `Settings` → `Rules` → `Protect main` |
| Target branches | 包含默认分支 `main` | 同上 |
| 规则列表 | `non_fast_forward`、`deletion`、`pull_request` | 同上 |
| Require approvals | 与 §9.1 约定一致（本仓库为 1） | 规则详情里的 pull_request 参数 |
| Bypass list | 空 | 同上 |

```powershell
# 只读命令：查看远端 main 当前指向哪个提交（不产生任何写入）
git ls-remote upstream main
```

> **⛔ 不要用"在自己 Fork 上推一下试试"来验证。**
> 这一段曾经写在本节里，已删除——它证明不了任何事：
>
> - **Fork 不继承上游的分支/标签规则集**，所以推自己的 Fork 成不成功，
>   与共享仓库的保护状态**无关**
> - 没有新提交时，推送只是个"无更新"操作，根本不会触发规则检查
>
> **核查必须针对上游（`upstream`）的规则详情页**，也就是上面那张表。
> 只读、看配置，不做任何写入。

**恢复后回一句**：在 Issue 或群里写明"规则已恢复，核查日期 __，核对人 __"。
这样别人不必再自己去试。

## 9. 参考：GitHub 配置与命令速查

### 9.1 分支保护（Ruleset）

**执行时机**：先完成首次推送、确认远端已有 `main`，**再**启用规则。空仓库过早启用会拦住创建主分支。

路径：`Settings` → `Rules` → `Rulesets` → `New branch ruleset`

| 项 | 值 |
|---|---|
| 名称 | `Protect main` |
| Enforcement | `Active` |
| Target | `Include default branch` |
| Require pull request | 开启，至少 **1** 个 Approval |
| Dismiss stale approvals | 开启 |
| Require conversation resolution | 开启 |
| Block force pushes | 开启 |
| Bypass 人员 | 不设置 |

> **注意**：分支保护与规则集在 **Free 计划下只适用于公开仓库**，
> 私有仓库需要付费计划（GitHub Team/Pro/Enterprise）。
> 依据见 [受保护分支的可用性](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)
> 与 [关于规则集](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)。
>
> ⚠️ **不要为了启用保护，就把含课程材料或未获授权数据的仓库改成公开。**
> 那会**立刻公开全部历史**（包括历史中已删除的文件），代价远大于"没有分支保护"。
> 正确的取舍顺序是：**先决定内容能不能公开，再决定用什么可见性**；
> 保护措施是"公开之后"才需要考虑的事。
>
> 没有稳定 CI 时**不要**添加必需的 Status checks，否则 PR 永远无法合并。

#### 本仓库的实际配置（记录于 2026-09-29）

> **核查来源与时效说明**：下表来自 **2026-09-29 通过 GitHub REST API
> 读取仓库规则集**（`GET /repos/konrad9523/route-plan/rulesets`）的结果，
> **不是**当前时刻的实时保证。规则可被有权限的人随时修改或关闭。
> **动手前请自行按 §8.9 的核对表在网页上重看一眼**，并以此为准。

| 项 | 记录值（2026-09-29） |
|---|---|
| 规则集名称 | `Protect main` |
| Enforcement | `Active` |
| Target | `Include default branch`（只保护 `main`） |
| 规则 | `non_fast_forward`（禁强推）、`deletion`（禁删除）、`pull_request`（须 PR + 1 批准） |
| Bypass 人员 | 空 |

**由此推出的三条**：

1. **在规则集处于 `Active` 且配置未被修改时**，"必须走 PR"是强制的，不是建议。
   其他人不要指望"反正推不进去就没事"——PR 是唯一通道。
2. **但"推不进 main"不是绝对保证**。GitHub 允许给规则集配置 **bypass 名单**，
   且**有管理权限的人可以随时修改、禁用或删除规则集**。
   所以这条规则防的是"**误操作**"，不是"**恶意绕过**"。
   **不要把规则集当成安全边界**——真正的边界是只把该进仓库的东西放进仓库。
3. **规则只作用于它的 Target（默认分支）**。往其他分支强推不会被拦——
   所以**别把"推得上"当成"这样做没问题"**。

#### ⚠️ 临时关闭规则集：风险与限时恢复清单

只有 §7.1 的例外情形（管理员维护历史）才需要临时关闭。**关闭期间等于没有保护。**

**关闭前**：

- [ ] 备份已完成并验证（`git bundle verify`）
- [ ] 已通知全组，且确认无人有未推送成果
- [ ] 记下当前 `git ls-remote upstream main` 的 hash（恢复后要核对）

**恢复清单（做完立即执行，不要拖）**：

## 10. 为什么这样组织（设计依据）

| 决策 | 依据 |
|---|---|
| **按功能分共享目录，不按成员姓名分** | GraphHopper 用 `core` / `map-matching` / `navigation` / `web-api`；OSRM 与 Valhalla 同样按功能组织。成员会换、角色会调，**目录不该跟着重排** |
| **用 Fork 隔离个人阶段成果** | 仓库权限是仓库级、文件夹级无法保密；Fork 是完整的独立远端，个人内容留在自己的 Fork 里 |
| **共享仓库另设角色成果区** | 五个角色的产出形态不同（数据/算法/性能/交互/验证），统一结构会导致"该放的没地方放" |
| **一个 PR 聚焦一个 Issue** | GraphHopper 贡献指南明确要求一个 PR 只做一件事并带测试 |
| **禁止直接推主分支** | OSRM 贡献指南记录了主分支只接收 PR 的做法 |
| **较大的改动先开 Issue 讨论** | Valhalla 贡献指南的建议；避免做完才发现方向不对 |
| **本机草稿不应进版本控制** | 它既不是备份也不该公开；需要留痕的内容进入 Fork 工作区或共享仓库 |

## 11. 重要决策记录

**为什么需要这一节**：决定散落在聊天记录和 CHANGELOG 里，三个月后没人说得清
"当初为什么这么定"。这里只记**影响多人、且推翻需要成本**的决定。

**格式**：决定 / 原因 / 否决了什么 / 日期。**新决定追加在下方，不删旧的**——
被否决的方案本身也是信息，能防止后来者重新提出同一个已被否掉的想法。

### D1. 按技术层划分五个角色，而不是按模块

**日期**：2026-09-18　**相关**：`docs/project/五角色任务分解与扩展方案.md`

**决定**：分成 A1 数据 / A2 算法正确 / A3 性能 / A4 交互 / A5 演示材料五条线，
四次作业**不换岗**。

**原因**：按模块分会让同一个人每次作业都在学新东西，做不深；
而且作业 2 上 CH 之后图要重写、可视化要重做，按模块分接不住。

**否决**：按"加载/算法/可视化/文档"等模块分工；一人一角色的简单分法
（两个算法人手、只有一个算法角色，会把 CH 这种高风险任务漏掉）。

### D2. 测试与验证职责从 A5 移到 A3

**日期**：2026-09-29　**相关**：第 3 节、`workspaces/A3_性能/README.md`

**决定**：A5 由"验证评估线"改为"演示材料线"（只做 PPT 与讲稿）；
测试归 A3，角色名改为"性能与测试线"。

**原因**：测试一直是 A3 在做（SearchTrace 的 19 项测试、回归测试、56 项测试套件），
角色名与实际工作长期对不上；且**性能与测试本就该同一人负责**——
测出来的加速比可不可信，只有测量者说得清。

**否决**：维持 A5 兼测试（职责名与实际不符，写文档和汇报都要额外解释）。

### D3. 用"改写历史"而非"新建仓库"清理课件

**日期**：2026-09-29　**相关**：`重建干净仓库操作清单.md` §3.5

**决定**：用 `git filter-repo` 从历史中移除课件并强推 `main`，**不新建仓库**。

**原因**：新建仓库会丢掉仓库身份，**Issue、协作者、Fork、外部链接全部失效**；
而"改写历史"是同一个仓库换掉内容，这些全部保留。当时无协作者、无开放 PR，
是代价最小的窗口期。

**否决**：新建干净仓库（丢 Issue 与协作者）；接受课件留在历史里（可接受，
但既然代价很低就顺手清了）。

**结果**：旧提交直链实测返回 **404**，服务端也彻底清除，比预期更干净。

## 12. 交付约定（提案，待组内确认）

> **状态**：本节是**建议**，来自外部审查意见与项目管理资料的启发，
> **尚未经五人组确认**。确认前，前面各节的硬规则优先。
> 目的不是增加流程，而是回答三个最常扯皮的问题：
> **"什么算做完"、"等不到审查怎么办"、"谁该看这个 PR"。**

### 12.1 任务完成的定义（可核对，不看百分比）

一个任务算完成，需要满足：

- [ ] 验收标准满足（Issue 里写清的那几条）
- [ ] 相关验证**可重复**：`python -m unittest discover -s tests` 与
      `python tools/smoke_api.py` 通过（纯文档任务改为跑 `tools/check_docs.py`）
- [ ] 至少一位**非作者**审查通过
- [ ] 成果在**正式位置**，不是只在自己 Fork
- [ ] 接口/数据/限制的变更**已同步到文档**
- [ ] PR 已合并且关联了 Issue

**阶段完成**（比任务更高一层）：

- [ ] 至少一位非作者**按 README 在约定环境跑通端到端演示**
      （数据加载 → 规划 → API → 地图显示）
- [ ] 记录**被验收的提交 SHA 与数据版本**
- [ ] 已知限制写清楚（A5 的汇报数字要能追溯到这两个值）

> **不要用"完成了 90%"这类描述**——它无法核对。
> 用"哪些用例过了、哪些还没、被什么阻塞"代替。

### 12.2 每阶段只锁定一个主要可演示目标

课程必做项与已有链路优先；交通方式、多目标偏好、DEM、AI 扩展
**逐项选择**，不承诺同时完成。

对每个要做的扩展，先说明：**收益是什么、需要谁配合、会不会影响必做项、什么条件下停**。
（D5 的"偏好延后到作业 3"就是这种取舍的先例。）

### 12.3 等待与阻塞

| 情形 | 约定 |
|---|---|
| 请求审查后**超过约定时限**无回应 | 由协调者**另找一位替代审查人** |
| **无人回复** | **不算批准**，不得据此合并 |
| 任务被阻塞 | 在 Issue 写明：缺什么、需要谁、对阶段目标的影响 |
| 优先级 | **先解除别人正在依赖的阻塞**，再开新功能 |

> 具体时限由课程安排决定，本文件不写死数字。
> 五人组建议先从"一到两个工作日"试起。

### 12.4 共同接口与并行

**可信结论依赖可信输入，但设计与准备工作可以提前并行。**

| 角色 | 可以提前做 | 对外给结论前需要 |
|---|---|---|
| A1 数据 | 字段与单位说明、小型样例、获取与质检脚本 | 数据版本、来源、缺陷明确，下游能加载 |
| A2 算法 | 小图基准、边界用例、代价与返回语义 | 与约定数据、接口、正确性证据一致 |
| A3 性能与测试 | 固定查询集、对拍规则、基准脚本、小图探索 | 基准算法与输入版本已验证，再报加速比 |
| A4 交互 | 用样例响应搭界面、动画播放器、错误提示 | 用真实响应联调，不把模拟当真实功能 |
| A5 演示 | 梳理演示主线、准备图表结构 | 素材关联真实数据与验收版本，不填未验证数字 |

> **模拟数据与样例响应必须显式标注**。提前并行不降低交付标准，
> 也不改变"作者先验证自己的改动"（§3.3.1）。

### 12.5 状态汇报就事论事

汇报用短格式：**完成了什么 / 被什么阻塞 / 影响谁 / 需要哪种帮助**。

协调者先听事实、按风险与依赖安排协助。
**这并不免除隐瞒缺陷或违反安全规则的责任**——报实情受保护，瞒报不受保护。
