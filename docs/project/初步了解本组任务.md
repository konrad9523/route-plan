# 导航系统与路径规划组项目方案（组员共享版）

> 本文根据课程 PPT、四个方向的智能体研究结果、开源项目资料，以及当前已经实现的路径规划代码整理而成。目标是让组员知道：我们要做什么、各模块如何串联、路径规划负责什么、工具如何选、每个人怎么分工，以及传统最短路之外还能做哪些有展示价值的功能。

## 1. 我们到底要做什么

我们不是只写一个“输入起点终点、输出一串节点”的算法，而是做一个可解释、可测试、能在地图上展示的导航系统原型：

~~~text
地图数据获取
    ↓
数据清洗与坐标统一
    ↓
道路网络建模（节点、边、方向、限速、道路等级、转向限制）
    ↓
路径规划（Dijkstra / A* / 多目标 / 动态重规划）
    ↓
路径结果处理（几何线、距离、时间、转弯点、文字说明）
    ↓
地图展示与导航交互
    ↓
轨迹回放、偏航检测、重新规划、效果评估
~~~

第一阶段的核心成果：

1. 使用公开地图数据构建一个小区域道路图。
2. 实现并解释 Dijkstra 与 A*。
3. 处理单行道、道路方向、道路等级、转向代价等基本约束。
4. 通过 API 返回 GeoJSON 路线。
5. 在网页地图上显示路线、起终点和路线统计。
6. 用固定测试证明算法正确，而不是只展示一张截图。

我们最终要交付的是一个“小而完整”的导航系统，而不是一个全国级地图产品。

## 2. 从 PPT 和智能体结果提炼出的系统全景

### 2.1 四层架构

| 层次 | 主要内容 | 我们的实现重点 |
|---|---|---|
| 数据层 | OSM、道路中心线、兴趣点、实时或历史轨迹、天气/风险等 | 先完成 OSM 道路数据；其他数据作为增强项 |
| 算法层 | 图建模、最短路、启发式搜索、多目标、动态重规划 | 这是路径规划组的核心 |
| 服务层 | 路线规划 API、地图匹配、轨迹服务、缓存、日志 | 第一阶段用 FastAPI 或 Flask |
| 展示层 | 网页地图、路线对比、导航提示、轨迹回放 | 可用 MapLibre GL JS、Leaflet 或 OpenLayers |

### 2.2 十二个模块如何串联

1. 数据获取：从 OpenStreetMap、Geofabrik、Overpass 或已有数据源取得道路数据。
2. 数据预处理：清洗重复线、修复几何、过滤无关道路、统一坐标系。
3. 空间数据库与索引：使用 PostGIS、R-tree 或网格索引，支持空间查询。
4. 道路网络建模：把道路转成有向图；节点是路口或道路端点，边是可通行路段。
5. 地图匹配：把 GPS 轨迹点匹配到道路边，用于轨迹回放、历史数据和偏航判断。
6. 路网权重构建：计算距离、时间、收费、风险、坡度、能耗等代价。
7. 路径规划：在图上寻找满足约束且代价最小的路线。
8. 路线后处理：合并连续路段、抽取转弯点、生成 GeoJSON、计算统计量。
9. 动态交通与重规划：根据拥堵、封路、偏航或新约束重新计算路线。
10. 导航指令生成：将转弯动作转换成“前方 300 米右转”等文本或语音。
11. 地图与交互展示：显示路线、备选路线、风险点、轨迹和导航状态。
12. 评估与运维：测试正确性、耗时、路线质量、接口稳定性和数据更新流程。

它们不是 12 个互不相关的小作业：

~~~text
数据获取 → 预处理 → 图建模 → 权重
                              ↓
                      路径规划核心
                              ↓
       后处理 → API → 地图展示 → 导航/重规划
          ↑                              ↓
          └──── 评估、轨迹、反馈、数据更新 ────┘
~~~

### 2.3 三条关键数据流

离线建图流：

~~~text
PBF / GeoJSON / Shapefile
    → GDAL / osmium / OSMnx
    → 坐标与几何清洗
    → 道路图与空间索引
    → GraphML / GeoPackage / PostGIS / 自定义格式
~~~

在线规划流：

~~~text
起点终点 + 出行方式 + 偏好 + 约束
    → 坐标校验与最近道路匹配
    → 路径搜索
    → 路线几何、距离、时间、转弯点
    → GeoJSON / JSON
    → 前端地图与导航提示
~~~

动态闭环流：

~~~text
GPS / 模拟轨迹 / 交通事件
    → 地图匹配与偏航判断
    → 更新边权或禁用路段
    → 重新规划
    → 更新前端路线和提示
~~~

## 3. 我们与其他模块的接口边界

### 3.1 路径规划组的输入

~~~json
{
  "origin": [116.397, 39.908],
  "destination": [116.410, 39.915],
  "mode": "car",
  "objective": "time",
  "avoid_tolls": false,
  "avoid_highways": false,
  "risk_tolerance": 0.5,
  "departure_time": null,
  "blocked_edges": []
}
~~~

其中 origin 和 destination 是经纬度；mode 表示出行方式；objective 表示距离最短、时间最短、风险较低或综合代价；blocked_edges 表示封路、施工或事故；departure_time 为将来支持时间依赖权重预留接口。

### 3.2 路径规划组的输出

~~~json
{
  "algorithm": "astar",
  "objective": "time",
  "distance_m": 2450.6,

  "nodes": ["n1", "n8", "n13"],
  "edges": ["e1", "e9"],
  "geometry": {
    "type": "LineString",
    "coordinates": [[116.397, 39.908], [116.402, 39.911]]
  },
  "steps": [
    {
      "instruction": "沿当前道路直行",
      "distance_m": 830,
      "duration_s": 120
    },
    {
      "instruction": "前方右转",
      "distance_m": 260,
      "duration_s": 42
    }
  ],
  "warnings": []
}
~~~

### 3.3 责任边界

- 数据组负责道路数据是否能用、字段是否合理。
- 路径规划组负责在给定道路图和代价下找到正确路线。
- 服务组负责把算法封装成 API，并处理并发、错误和日志。
- 前端组负责路线如何展示、如何交互。
- 测试与评估负责怎样证明系统有效。

## 4. 路径规划模块：我们真正要解决的问题

### 4.1 道路图不是普通的无向图

道路导航通常需要有向图：

~~~text
节点 V：路口、道路端点、必要的形状点
边 E：一段可通行道路
边属性：长度、限速、方向、道路等级、是否收费、几何坐标
图 G = (V, E)
~~~

单行道只能建立一个方向的边；双向道路通常建立两条方向相反的边。不能把所有道路简单当成无向边，否则会出现逆行路线。

### 4.2 最基本的代价函数

距离最短：边代价等于边长度。

时间最短：边代价等于边长度除以速度。

综合代价：

~~~text
cost = α × normalized_time
     + β × normalized_distance
     + γ × toll_penalty
     + δ × risk_penalty
~~~

多种指标不能直接把米、秒、元、风险分数相加，必须先归一化，或者明确每项的单位和权重。

### 4.3 Dijkstra、A* 和工程进阶路线

**Dijkstra**

- 从起点开始按当前已知代价从小到大扩展。
- 在非负边权下保证最优。
- 不使用目标位置的信息。
- 适合做正确性基线和教学演示。

**A***

- 使用 f(n) = g(n) + h(n)。
- g(n) 是从起点到当前节点的真实代价。
- h(n) 是当前节点到终点的启发式估计。
- 距离最短时可用球面距离；时间最短时不能直接把距离当成时间，应使用与时间目标匹配的下界。

推荐演进顺序：

~~~text
Dijkstra 基线 → A* → 双向 A* → 多目标与偏好权重
             → 时间依赖与动态重规划
             → Landmark / ALT → CH / MLD
~~~

CH、MLD 等预处理算法适合大规模稳定路网。课程项目第一阶段不建议一开始实现它们，应该先把图建模、权重、接口和测试做正确。

### 4.4 转向限制为什么要改变搜索状态

如果代价只取决于当前节点，可以用 node 作为状态。但“禁止从道路 A 左转进入道路 B”需要知道上一条边，因此状态要扩展为：

~~~text
state = (previous_edge_id, current_node_id)
~~~

这样才能表达禁止左转、禁止右转、禁止掉头，以及不同转弯的等待时间和风险。

## 5. 工具按模块怎么分

| 模块 | 推荐工具 | 一般怎么用 |
|---|---|---|
| 数据获取 | OpenStreetMap、Geofabrik、Overpass API | 下载区域 PBF；查询小范围要素；获取道路、路口、兴趣点 |
| 数据转换 | osmium、GDAL/OGR | 裁剪、过滤、转换 PBF、GeoJSON、Shapefile、GeoPackage |
| 坐标处理 | PROJ、PyProj | WGS84 与投影坐标互转；距离和面积计算前统一坐标 |
| 几何处理 | Shapely/GEOS | 线切割、相交、缓冲、合并、修复无效几何 |
| 路网建模 | OSMnx、NetworkX | 从 OSM 生成有向图；分析节点、边、连通性 |
| 空间数据库 | PostgreSQL + PostGIS | 保存道路与空间对象；使用空间索引和 SQL 查询附近道路 |
| 路径引擎参考 | OSRM、GraphHopper、Valhalla、pgRouting | 对比成熟系统的输入、权重、预处理、API 和性能 |
| 地图展示 | MapLibre GL JS、Leaflet、OpenLayers、Cesium | 底图、线图层、点标记、轨迹和交互；Cesium 偏 3D |
| 服务层 | FastAPI、Flask、Node.js | 提供 route、match、reroute 等接口 |
| 导航提示 | 自定义规则、TTS、Piper、eSpeak NG、Coqui TTS | 由转弯点生成文本，再转为语音 |
| 工程协作 | Git、Docker、CI | 版本管理、统一环境、自动测试和演示部署 |

工具的“长相”可以这样理解：

- OSM 数据是地图要素和标签；
- PBF 是适合大规模存储和传输的二进制地图文件；
- OSMnx/NetworkX 是 Python 图对象；
- PostGIS 是带空间类型和空间索引的数据库；
- OSRM/GraphHopper/Valhalla 是可通过 HTTP 或库调用的路由引擎；
- MapLibre/Leaflet/OpenLayers 是浏览器端 JavaScript 地图库；
- QGIS 是桌面端 GIS 制图、检查和数据处理软件。

这些工具不是互相替代的。QGIS 更适合检查和制图，OSMnx 更适合原型建模，PostGIS 更适合空间数据管理，OSRM/GraphHopper/Valhalla 更适合成熟引擎参考或对照实验。

## 6. 开源项目参考：为什么看它们

| 项目 | 主要技术特点 | 适合我们学习什么 |
|---|---|---|
| OSRM | C++，面向 OSM，道路图预处理，CH/MLD，HTTP 服务 | 大规模驾车路线、矩阵、匹配、服务接口 |
| GraphHopper | Java，Dijkstra/A*、Landmarks、Contraction Hierarchies、可配置权重 | 权重抽象、算法切换、Java 工程结构 |
| Valhalla | C++，动态 costing、分层路网、多模式、时间依赖 | 多模式、动态代价、复杂导航服务 |
| pgRouting | PostgreSQL/PostGIS 扩展，SQL 调用图算法 | 空间数据库与路由算法结合 |
| openrouteservice | 基于 OSM 的 API 服务，支持多种出行方式和等时圈 | 服务化和多功能路线 API |
| OSMnx + NetworkX | Python 原型分析工具 | 小区域实验、图检查、算法教学 |
| Neo4j GDS | 图数据库与图数据科学算法 | 图数据管理和图分析的另一种思路 |

学习策略不是复制成熟引擎，而是：

1. 用 OSMnx/NetworkX 先把小区域数据跑通。
2. 用自己的 Dijkstra/A* 解释算法过程。
3. 用 OSRM 或 GraphHopper 做结果和耗时对照。
4. 时间充足后，再增加地图匹配、偏航重规划或多目标路线。

## 7. 传统最短路之外，建议做的额外功能

额外功能不应该只追求“功能名字多”，而应该满足至少一个目标：更有用、更可解释、更容易演示，或者能体现我们对导航系统的理解。

### 7.1 第一优先级：低风险、高展示价值

| 功能 | 做什么 | 难度 | 展示价值 | 建议 |
|---|---|---:|---:|---|
| 路线解释 | 显示为什么选择这条路：距离、时间、道路等级、避开了什么 | 低 | ★★★★★ | 必做 |
| 多路线对比 | 同时给出最快、最短、少收费、少风险等候选 | 中 | ★★★★★ | 必做 |
| 轨迹回放 | 在地图上按时间播放 GPS 轨迹与规划路线 | 低 | ★★★★☆ | 强烈建议 |
| 偏航检测 | 车辆偏离规划路线超过阈值时发出提示 | 中 | ★★★★★ | 强烈建议 |
| 自动重规划 | 偏航、封路或事故后重新调用路由算法 | 中 | ★★★★★ | 强烈建议 |
| 路线统计面板 | 距离、预计时间、转弯次数、收费、风险、道路等级占比 | 低 | ★★★★☆ | 必做 |

这组功能能形成完整演示：

~~~text
选择起终点 → 生成三条路线 → 比较路线解释
        → 播放模拟轨迹 → 模拟偏航
        → 自动重规划 → 更新地图与统计
~~~

### 7.2 第二优先级：体现算法特色

**风险感知路线**

给道路增加事故频率、夜间风险、路口复杂度、道路施工等属性：

~~~text
cost = time_cost + λ × risk_score
~~~

用户拖动风险偏好滑块时，路线应从“快”逐渐变成“稳”。如果没有真实风险数据，必须标注为实验数据或模拟数据。

**绿色/低能耗路线**

结合道路坡度、速度变化、道路等级和拥堵假设，估计能耗或碳排：

~~~text
cost = time_cost + λ × energy_cost
~~~

这比单纯最短路更有研究味道，但要说明能耗模型只是近似模型。

**可达性路线**

为轮椅、婴儿车或行人设置无障碍偏好，避开楼梯、陡坡、没有人行道的路段。这个方向适合结合 GIS 属性做专题展示。

**等时圈和可达区域**

给定起点和 15、30、60 分钟，计算可以到达的路网范围并绘制边界。它能体现路径规划不仅能返回一条线，也能回答“我在规定时间内能到哪里”。

### 7.3 第三优先级：有研究价值，但需要更多数据

- 时间依赖路径规划：不同时间段使用不同速度或拥堵权重。
- 多模式出行：步行、公交、骑行、驾车的组合路线。
- 多目的地或旅行商问题：给定多个地点，优化访问顺序。
- 路线鲁棒性：分析拥堵波动下的准时概率。
- 隐私与离线模式：轨迹尽量本地处理，地图和路由可离线运行。
- 自然语言约束：把“避开收费、尽量少走小路、我怕堵车”转换成结构化约束，再交给确定性的路由算法。

### 7.4 应急场景与 DEM 地形约束

加入 DEM 后，项目可以增加一条“地形感知应急路径规划”分支。这里要先区分两类场景：

1. **应急车辆救援**：消防车、救护车、救援车辆从基地赶往事故点，核心目标是快速、可通行、可靠。
2. **灾害疏散**：人员从危险区域前往避难点，核心目标是避开淹没、滑坡、陡坡和危险道路，并尽量保证多条可用路线。

DEM 不是直接的“灾害地图”，而是基础地形数据。可以从 DEM 派生：

- 道路或栅格的高程；
- 坡度和坡向；
- 山谷、低洼地和汇流区域；
- 汇流累积量、河网和分水岭；
- 可能影响车辆通行和人员疏散的地形风险。

GDAL 的 gdaldem 可以从 DEM 生成坡度、坡向和阴影地形；GRASS GIS 的 r.watershed 等工具可以进一步计算流向、汇流累积、河网和流域等水文特征。相关结果可以采样到道路边上，转化为路网属性。[GDAL terrain analysis](https://gdal.org/en/stable/programs/gdaldem.html)、[GRASS r.watershed](https://grass.osgeo.org/grass85/manuals/r.watershed.html)

推荐的数据处理链：

~~~text
DEM 栅格
    → 投影、裁剪、填补 NoData
    → 生成坡度、坡向、汇流累积等栅格
    → 将栅格值采样到道路边
    → 形成道路坡度、低洼度、积水风险等属性
    → 应急车辆/疏散场景的路径规划
~~~

应急车辆的代价可以设计为：

~~~text
cost = response_time
      + λ1 × slope_penalty
      + λ2 × flood_risk
      + λ3 × road_failure_risk
      + λ4 × turn_penalty
~~~

应急车辆与普通车辆的区别是：

- 时间通常是第一目标；
- 不能经过车辆无法通行的道路；
- 陡坡、窄路、桥梁、低洼路段可以增加风险；
- 某些道路虽然距离短，但在灾害条件下不可靠；
- 必要时要保留第二条备用路线。

疏散场景不能只给每个人返回同一条最短路。可以进一步研究：

- 危险区域到避难点的安全路线；
- 避开低洼和高汇流区域；
- 计算 15、30、60 分钟疏散可达区域；
- 为多个避难点分配不同人群；
- 根据道路容量和拥堵风险生成多条疏散路线；
- 当道路封闭时自动重新规划。

要特别注意：DEM 能说明地形和水流汇聚趋势，但不能单独准确判断洪水淹没深度。若要做洪水应急路线，需要结合降雨、水位、河流、土地利用、历史灾害或已有淹没范围等数据。课程项目中可以先采用“DEM 派生地形风险 + 模拟封路事件”的可解释方案，不要把它表述成真实灾害预报。

这个方向的创新点是：

> 将二维道路图与三维地形风险结合，把普通最短路扩展为面向救援和疏散的风险约束路径规划。

自然语言模块应当只是约束解析器，不能让大模型直接胡乱生成路线。正确结构是：

~~~text
自然语言 → 约束 JSON → 路网权重/过滤器 → 确定性路径规划
~~~

### 7.5 现在不建议一开始就做

- 全国级实时交通系统；
- 自己实现完整 CH/MLD 并追求商业地图规模；
- 完整公交时刻表和换乘系统；
- 复杂的无人机三维避障；
- 端侧大模型导航；
- 没有数据支撑的“AI 智能路线评分”。

## 8. 推荐的最终功能组合

### 方案 A：最稳妥

路径规划 + 路线解释 + 多路线对比 + 轨迹回放 + 偏航重规划。

### 方案 B：最有特色

方案 A + 风险感知路线 + 绿色/低能耗路线 + 路线鲁棒性或等时圈。

### 方案 C：最适合课堂展示

地图交互 + 三条不同偏好的路线 + 解释面板 + 模拟车辆轨迹 + 偏航后自动重规划 + 自然语言约束演示。

推荐采用方案 C 的展示方式，但底层只实现方案 A 的稳定功能，风险、绿色和自然语言作为可控的增强模块。这样既能保证按时完成，又有明显区别于普通最短路作业的内容。

### 方案 D：应急 GIS 特色方向

普通车辆或救援车辆路线 + DEM 坡度分析 + 低洼/汇流风险 + 模拟道路封闭 + 备用路线或疏散可达区域。

如果组内有成员愿意负责栅格数据和 GIS 分析，方案 D 很适合作为项目的差异化方向。但建议先完成普通路径规划和多目标路线，再加入 DEM，不要一开始就把所有灾害模型都做进去。

## 12. 评估指标与验收标准

### 算法正确性

- 与 Dijkstra 基线比较，A* 的最优代价一致；
- 单行道不会逆行；
- 不可达时能返回明确错误；
- 禁止转向不会被路线绕过；
- 起点终点在同一连通分量时能够找到路线。

### 工程质量

- 输入输出格式固定；
- API 有错误处理；
- 关键模块有单元测试；
- 代码可从 README 复现；
- 数据、参数、实验结果有记录。

### 展示效果

- 地图上能看见起终点和路线；
- 能解释不同路线为什么不同；
- 能模拟偏航并展示重规划；
- 能展示至少一项传统最短路之外的增强功能。

### 性能指标

建议记录图规模、预处理耗时、单次查询耗时、Dijkstra 与 A* 的扩展节点数，以及多路线和增强权重对性能的影响。

不要在没有实验数据的情况下直接宣称“提升几十倍”或“适合百万级路网”。成熟引擎使用了复杂预处理和工程优化，我们的原型应当区分理论复杂度、实验结果和工程推测。

## 13. 我们现在的执行结论

第一阶段先完成：

~~~text
小区域 OSM 数据
→ 有向道路图
→ Dijkstra/A*
→ 时间与距离权重
→ FastAPI
→ GeoJSON
→ MapLibre/Leaflet 展示
→ 路线解释、轨迹回放、偏航重规划
~~~

第二阶段从下面选一个特色方向：

1. 风险感知路线；
2. 绿色/低能耗路线；
3. 等时圈；
4. 可达性路线；
5. 自然语言约束转结构化规划参数；
6. DEM 地形感知的应急救援或疏散路线。

最推荐的项目主线是：

> **可解释的多偏好路径规划与动态重规划导航系统**

它既保留路径规划模块的算法核心，又能把数据、服务、地图、轨迹和用户交互串成一个完整系统，适合作为五人小组的课程项目。
