# G4 路径规划引擎组：五角色任务分解与扩展优化方案

> **用途**：把四次作业的任务内容与产出物，拆成五个角色各司其职的任务，并为每次作业补上**扩展优化项**。
> **核心原则**：**每人纵向深入一条能力线，四次作业不换岗**——越做越深，而不是每次重新上手。
> **配套**：现有分工见 `docs/project/初步了解本组任务.md` 第 9 节；本方案在其基础上细化并补扩展。
>
> **关于文中提到的几个文档路径**：`docs/validation/report_week4.md`、`docs/validation/performance.md`、
> `docs/validation/multi_route_eval.md` 是**各作业阶段才产出的交付物**，现在**还不存在**——

## 0. 设计思路（先看这个，否则五角色的划分会显得奇怪）

### 0.1 为什么按"技术层"分角色，而不是按"作业任务"分

如果按作业的任务分（谁做 Dijkstra、谁做 A*、谁做双向 A*……），会出现三个问题：

1. **同一个人每次作业都在学新东西**，做不深；
2. **接口没人负责**，交接处容易出错；
3. 作业 2 一上 CH，图要重写、可视化要重做，**没人接得住**。

所以本方案改成**按技术层分**，让每个角色专精一条线：

```text
A1 数据线    路网怎么进来、怎么存、怎么压     ← 从 552 节点做到 100 万节点
A2 算法正确线 路线算得对不对、优不优          ← 从 Dijkstra 做到 能耗路线
A3 性能与测试线 怎么算得快、怎么证明跑得对    ← 从优先队列优化做到 CH + 全项目测试
A4 交互呈现线 怎么让老师一眼看懂              ← 从搜索动画做到答辩演示
A5 演示材料线 怎么把上面四条讲清楚            ← 从截图整理做到 PPT 与讲稿
```

### 0.2 五个角色的依赖关系

```text
        A1 数据线
            │（提供图与数据契约）
            ▼
        A2 算法线 ──────► A3 性能与测试线
            │（提供正确的基准算法）  （在正确算法上加预处理）
            │                    （并负责全项目测试）
            ▼
        A4 交互线 ◄────── A5 演示线
        （消费算法产出的数据）    （把四条的产出做成 PPT 与讲稿）
```

**关键**：A3 必须在 A2 之**后**工作（否则加速一个错的算法毫无意义）；A5 在最后汇总，素材全部来自其余四条的成果区。

### 0.2.1 五个人 → 五个角色（速查）

> **注意**：不是简单"一人一角色"。你们有 2 个算法人手、却只有 1 个算法角色，
> 所以要把算法拆成"**正确性**"和"**加速**"两条线，各给一个人。
> 完整说明见 §5.4。

| 人员 | 角色 | 一句话职责 |
|---|---|---|
| **P1** | **A2 算法正确线** | 路线算得**对不对、优不优** |
| **P2** | **A3 性能与测试线** | **CH 全链路** + 算得快 + **全项目测试** |
| **P3** | **A4 交互线** | 让老师**一眼看懂** |
| **P4** | **A1 数据线**（兼 A5 报告） | 路网怎么进来、怎么存、怎么压 |
| **P5** | **A5 演示材料线**（兼 A4 支援） | 把四条线的产出**讲清楚**（PPT + 讲稿） |

**三个必须避免的坑**（详见 §5.4）：

1. **两个算法人不要都做 A2** —— 一个做双向 A*，一个做 CH。两者技术栈完全不同，且作业 2 有 **45%** 的分押在这两项上。
2. **A1 工作量前松后紧** —— 作业 1 很轻、作业 2 骤重。让 P4 在作业 1 就**启动 10 万节点路网下载**。
3. **P5 会被"PPT + 支援前端"撕成两半** —— 按作业阶段倾斜：作业 1 主攻前端，作业 2/3 收集素材，作业 4 主攻 PPT 与讲稿。

> **2026-09-29 职责调整**：原方案把"测试与验证"放在 A5。实际执行中测试
> 一直是 A3 在做（SearchTrace 的 19 项测试、回归测试、56 项测试套件），
> 职责名与实际工作对不上。现改为：**A3 = 性能与测试线**（唯一测试责任人），
> **A5 = 演示材料线**（只出 PPT 与讲稿）。各作业表格中 A5 的验证条目、
> 以及作业 4 的"回归测试"条目已同步转给 A3。

**压力最大的是 P1 和 P2**，建议把文档类任务交给 P4/P5，让他们专注代码与验证。

### 0.3 三次"提前锁定"，让后面能并行

| 锁定时机 | 锁定什么 | 谁定 | 为什么必须早定 | 状态 |
|---|---|---|---|---|

> 谁想改接口，必须先通知其他四个角色。

## 1. 第 1 次作业（第 4 周后）：Dijkstra 与 A*

### 1.1 原始任务与产出物（不变）

**任务内容**

1. 实现 Dijkstra 最短路径算法（优先队列优化）
2. 实现 A* 算法，设计启发函数（欧氏距离/地标距离）
3. 实现路径重建和路径信息输出（总距离/总时间/路段序列）
4. 开发算法可视化界面：在路网上动画展示搜索过程（已访问节点/边界节点/最终路径）
5. 支持起点终点点击选择，实时计算路径

**产出物**：Dijkstra 与 A* 源代码 / 可运行程序 / 算法对比报告 / 可视化界面演示

**考核打分**：算法正确且路径最优 30% ｜ 启发函数设计合理、可采纳性验证 20% ｜ 搜索过程可视化动画流畅 25% ｜ 交互友好，点击选点实时计算 10% ｜ 文档和对比报告 15%

### 1.3 扩展优化项（加在每个角色任务后面）

| 角色 | 扩展优化项 | 为什么值得加 | 难度 |
|---|---|---|---|
| **A1** | **① 图完整性校验器**：检查重复边、孤立节点、几何缺失、连通分量 | 我实测过：552 节点里有 25 个节点不在最大强连通分量内，**不校验的话演示时点上去会"无路可达"** | 低 |
| | **② 提前下载城市级路网**（>10 万节点） | 作业 2 要求 10 万节点，你们现在只有 **552**——差 200 倍。**下载慢且不依赖算法进度，现在就该后台跑** | 中 |

## 2. 第 2 次作业（第 7 周后）：双向 A* 与 CH 收缩层次

### 2.1 原始任务与产出物（不变）

**任务内容**

### 2.3 扩展优化项

| 角色 | 扩展优化项 | 为什么值得加 | 难度 |
|---|---|---|---|
| **A1** | **① CSR 图结构**（数组化邻接表） | 现有 `dict` + 数据类对象在 10 万节点约需数百 MB，100 万节点要几个 GB。**CSR 是作业 4"百万级"的唯一出路** | **高（重点）** |
| | **② 节点 ID 稠密化重映射** | OSM 的节点 ID 是 `9626752368` 这种大数，**没法直接当数组下标**，必须先映射成 0..N-1 | 中 |
| | **③ 几何数据外置按需加载** | `Edge.geometry` 现在**饿汉式**全塞内存。10 万节点时几何是最大内存项，但搜索根本不用它 | 中 |
| **A2** | **① 双向搜索的正确终止条件** ⭐ | 必须满足"两方向队首之和 ≥ 当前最优"才能停。**极易写错且写错不报错，只给次优解** | **高（重点）** |
| | **② ALT 地标加速作为 CH 备用方案** | 如果 CH 没做出来，ALT 是"进阶算法"的兜底，**保住 20%** | 中 |
| | **③ 有向图/非对称代价下的双向搜索** | 单行道会让"反向图"和正向图不同，**不处理会算出逆行路线** | 中 |
| **A3** | **① 先做 CH-lite**：不做 witness search 的收缩 | 捷径边会变多但**结果仍正确**，能快速验证整条链路通不通 | 低 |
| | **② 用 RoutingKit 的两条弧表示法存捷径** | 参考实现：捷径用 `(前半段弧, 后半段弧)` 两个 ID 表示，**不存中间节点列表**，解压时递归 | 中 |
| | **③ 收缩顺序复用** ⭐ | RoutingKit 文档明确：拓扑不变时**顺序可复用**，换权重只需重建索引。**这是 CH 与交通模拟共存的唯一出路** | 中 |
| | **④ CH 与动态权重的回退策略** ⭐ | 交通一改权重，CH 的捷径边就**失效且会给出错误结果**。必须显式回退到 A* 并标注 | **高（必做）** |
| | **⑤ 公平对比四条铁律**（原 A5） | 同图、同查询集、同代价模型、预处理时间单列 | 低 |
| | **⑥ CH 正确性专项测试**（原 A5） | 解压后的完整路径 vs Dijkstra；CH 最容易"数字对但路径错" | 中 |
| | **⑦ 大规模内存峰值监控**（原 A5） | 对应 20% 的"测试数据可信" | 中 |
| **A4** | **① 四种算法同屏对比仪表盘** | 对应 20% 的"仪表盘直观" | 中 |

### 3.3 扩展优化项

| 角色 | 扩展优化项 | 为什么值得加 | 难度 |
|---|---|---|---|
| **A1** | **① 事件驱动而非随机拥堵** ⭐ | 随机改权重**不可复现、无法解释**。改成"事件文件 + 固定种子"，才能做对照实验 | 中 |
| | **② 时间依赖权重**（按时段变化） | 为作业 4 的真实导航场景铺路 | 中 |
| | **③ 所有模拟数据标注 `source="simulated"`** | 诚实标注，避免被质疑数据来源 | 低 |
| | **④ 红绿灯/风景/充电桩属性采集** | 用 Overpass 查校园周边信号灯和充电桩，**有真实数据支撑比编造强** | 中 |
| **A2** | **① Yen 算法而非"重复跑最短路"** ⭐ | 直接跑 4 次不同偏好，在真实路网上**经常得到同一条路**——会被质疑"多路径没差异" | **高（重点）** |
| | **② 重合率约束 + 惩罚法兜底** | 给 `overlap < 0.7` 的硬约束；Yen 不够多样时用路段惩罚法补 | 中 |
| | **③ 偏好冲突的分层处理** | **先硬约束过滤，再加权求和**——否则"最快"会把"避开高速"抵消掉 | 中 |

| **A3** | **① 多路径查询复用**（一次搜索出多条） | K 条路径各跑一次 Dijkstra 太慢，可共享部分搜索状态 | 高 |
| | **② 动态权重重算的性能边界** | 量化"改一个事件后重算要多久"，这是 **CH 回退策略的依据** | 中 |
| | **③ 多样性指标定义**（原 A5）：长度加权重合率 + 走廊 Jaccard 距离 | 25% 的"候选路径有明显差异"**必须用数字证明**，不能靠肉眼 | 中 |
| | **④ 事件重放一致性测试**（原 A5） | 同一事件文件跑两次，结果必须**完全一致** | 低 |
| | **⑤ 偏好有效性测试**（原 A5） | 切换偏好后路线**必须改变**，否则说明权重没生效 | 低 |
| **A4** | **① 差异路段高亮** | 对应 20% 的"标注差异路段" | 中 |
| | **② 每条路径独立指标卡**（距离/时间/偏好得分） | 让"用户满意度"可视化 | 低 |
| | **③ 车辆动画 + 剩余距离实时更新** | 对应原文第 5 条 | 中 |
| | **④ 拖动时间轴看事件影响** | 展示"拥堵发生前后路线怎么变"，演示效果极好 | 中 |
| **A5** | **① 多路径对比 PPT 与讲稿** | 把"K 条路到底哪里不一样"讲成一眼能看懂的画面 | 中 |
| | **② 用户满意度结论的写法** | 原文产出物要求"用户满意度模拟"；**模型由 A3 给数据，A5 负责表述** | 中 |

### 3.4 本作业的**最大陷阱**

| 陷阱 | 说明 | 应对 |
|---|---|---|
| **多路径高度重复** | 只跑多次不同偏好 → 真实路网上常得到同一条路 | A2 用 Yen + 重合率硬约束 |
| **偏好被"最快"抵消** | 所有偏好平等加权 → 最优时间压倒一切 | 分层：先硬约束，后加权 |
| **交通模拟不可复现** | 随机改权重 → 报告里的数字无法重现 | 事件文件 + 固定种子 |

| **P1** | Dijkstra + A* + **地标启发式(ALT)** | 双向 A* + ALT 加固 | **Yen 多路径** + 偏好映射 | **TSP 途经点** + 能耗模型 |
| **P2** | SearchTrace + 优先队列优化 + **测试套件** | **CH 全链路**（含与动态权重的回退） | 多路径性能 + 多样性指标 | **API 服务** + 百万级优化 + 回归测试 |
| **P3** | **地图 + 搜索动画 + 点击选点** | 性能仪表盘 + CH 预处理动画 | 多路径对比 + 车辆动画 | **导航演示** + 演示视频 |
| **P4** | 路网体检 + **启动 10 万节点下载** | 10 万节点接入 + **CSR 压缩图** | 交通事件建模 | DEM 坡度 + 导出数据 |
| **P5** | **主攻前端**（与 P3 一起做作业 1 的界面） | 性能对比 PPT 与讲稿 | 多路径对比 PPT | **三份文档 + AI 日志 + 答辩 PPT** |

#### 三个必须避免的坑

**坑 1：两个算法人不要都做 A2**

"两个人搞算法"听起来合理，但如果两人都做 Dijkstra/A*/双向 A*，会**重复劳动且没人做 CH**。

作业 2 的两项是"双向 A* 正确（**20%**）"和"CH 正确（**25%**）"——**45% 的分，且技术栈完全不同**：

| | 技术栈 | 主要难点 |
|---|---|---|
| 双向 A*（P1） | 图搜索 | 反向图的正确性、**相遇判定与终止条件** |
| CH（P2） | 图预处理 | 节点收缩、witness search、**捷径边解压** |

**让两人各背一项，比两人一起做同一项高效得多。**

而且 CH 一旦出错是**灾难级**的（捷径边把错误**固化**进预处理结果，查起来比普通 bug 难十倍），必须有一个**专职负责人**。

**坑 2：A1 的工作量"前松后紧"，作业 1 会闲、作业 2 会崩**

| 作业 | A1（P4）工作量 | 原因 |
|---|---|---|
| 作业 1 | **轻** | 加载器已写好，只有 552 节点 |
| 作业 2 | **突然变重** | 10 万节点 + CSR 压缩图 + 节点 ID 重映射 |
| 作业 3 | 中 | 交通事件 + 边属性 |
| 作业 4 | 中 | DEM 坡度采样 |

**对策**：让 P4 在作业 1 阶段就**启动 10 万节点路网下载**。
下载慢、可能失败、要换镜像重试，正好填满作业 1 的空档，**而且完全不依赖任何算法进度**。

**坑 3：P5 的"测试 + 支援前端"会被撕成两半**

"测试"是**横切**的（要验证所有人的产出），"支援前端"是**纵向**的（要深入界面细节）。两者都要，但精力会冲突。

**对策：按作业阶段倾斜，不要平均用力。**

| 作业 | P5 重点 | 理由 |
|---|---|---|
| 作业 1 | **主攻前端** | 前端占作业 1 的 **35%**（25% 动画 + 10% 交互），是最大缺口 |
| 作业 2 | **主攻测试** | CH 的 **25%** 靠正确性验证撑住 |
| 作业 3 | 测试 | "候选路径有明显差异（**25%**）"**必须用数字证明**，不能靠肉眼 |
| 作业 4 | **文档 + 答辩** | 文档 15% + 答辩演示与核心函数解释 15% |

#### 作业 1 当前状态（截至 2026-09-18）

| 项 | 状态 | 谁接着做 |
|---|---|---|
| 算法内核（Dijkstra / A*）正确性 | ✅ 已修复并验证（56 个测试） | — |

> 其余都已有可运行代码。

#### 工作量排序（哪几个角色最重）

| 排名 | 角色 | 人员 | 为什么重 |
|---|---|---|---|
| **并列 1** | A2 算法正确线 | P1 | 背作业1 的 **50%**（正确 30% + 可采纳性 20%）、作业2 的 20%、作业3 的 50% |
| **并列 1** | A3 性能与测试线 | P2 | 背作业2 的 **CH 25%** + 仪表盘数据 20%，外加作业4 的性能 15% 与**全项目测试**；且 CH 技术风险最高 |
| 3 | A4 交互线 | P3 | 作业1 **35%**、作业2 20%、作业3 20%；且**作业 1 是关键路径** |
| 4 | A5 演示材料线 | P5 | 不写代码，作业 4 独自背 30%（文档 15% + 答辩 15%），前三个作业收集素材 |
| 5 | A1 数据线 | P4 | 作业 1 轻、**作业 2 骤重**，需要提前布局 |

**结论**：**P1 和 P2 是压力最大的两个人**，建议给他们**减少文档类任务**（文档交给 P4/P5），
让他们专注代码与验证。**测试不再由 P5 分担**——归 P2 统一负责，
这样"谁改坏了谁跑测试"这一条不再需要跨人协调。

## 6. 三个必须现在就知道的风险

### 风险 1：作业 1 的 30%——**已消除**（2026-09-18 修复）

我实测过：552 节点真实路网上跑 300 组随机查询，**崩溃率 52.3% ~ 58.2%（四种偏好平均 55.5%）**，抛的是 `TypeError`。
而作业 1 有 30% 的分数是"Dijkstra 和 A* 算法正确"。

**已修复。** 修复内容与实测结果：

| 缺陷 | 修之前 | 修之后 |
|---|---|---|
| 优先队列等代价崩溃 | 崩溃率 55.5% | **0 崩溃** |
| A* 终止条件（几何不自洽图返回次优） | 800 m（最优 250 m） | 新增一致性校验器，真实路网违反数 **0** |

**细节见 `docs/learning/notes/学习笔记_03_修掉两个缺陷.md`。**

> ⚠️ **但这条风险要持续守着**：任何人改动 `router.py` 的搜索循环，都必须重跑对拍测试（当前 **56 个测试**）。
> 建议把 `python -m unittest discover -s tests` 作为**提交前的固定动作**。

### 风险 2：10 万节点数据还没开始准备（**次紧急**）

作业 2 要求 >10 万节点。你们现在有 **552**，差 **200 倍**。

下载 + 转换**不依赖任何算法进度**，而且网络下载可能失败、需要重试。**建议作业 1 阶段就让 A1 后台启动。**

### 风险 3："百万级 < 100ms"在纯 Python 下做不到（**要在报告里提前处理**）

我分析过你们的实现：`heapq` + `dict` + 数据类对象，纯 Python 在百万节点上单次查询预计**百毫秒到秒级**。

**不要硬套这个目标**，改成三档：

| 档位 | 目标 |
|---|---|
| 保底 | 552 节点，A* p95 < 50 ms |
| 合理 | 5 万节点，A* p95 < 200 ms |
| 挑战 | 10 万节点，CH p95 < 100 ms（仅静态权重，预处理时间单列） |

**成人话就是**："百万节点规模下算法不崩溃、内存可控，并如实报告实测耗时"。老师更认这个，而不是一个做不到的数字。

## 7. 一句话总结

> **按技术层分五个角色，每人四次作业不换岗、越做越深**：
> A1 数据线、A2 算法线、A3 性能与测试线、A4 交互线、A5 演示材料线。
>
> **每次作业的扩展优化都挂在角色任务后面**，并且**只在作业 1 锁定三个接口**（图契约、结果格式、事件流），后面三次作业就能并行推进。
>
> **最紧急的两件事**：修那个崩溃率 55.5% 的 bug（保作业 1 的 30%）、启动 10 万节点路网下载（保作业 2 的 20%）。
