# GIS 导航系统全链路系统学习手册

## 这份文档解决什么问题

很多人第一次接触导航系统时，会把它理解成一个最短路算法：

~~~text
输入起点和终点 → 调用 Dijkstra 或 A* → 输出路线
~~~

真实的导航系统远不止这一步。算法要使用道路数据，数据要被清洗和建模，用户输入的经纬度要吸附到道路，路线还要被转换成地图线、转弯提示和语音。车辆移动后，系统要判断是否偏航，遇到封路或交通变化后还要重新规划。

我们要学习的是一条完整链路：

~~~text
现实世界
    ↓
地图数据与传感器数据
    ↓
坐标、几何和空间数据库
    ↓
道路网络图
    ↓
权重、约束和路径算法
    ↓
路线后处理与导航指令
    ↓
地图、语音和用户交互
    ↓
轨迹反馈、偏航检测、动态重规划
~~~

本手册的目标是让你能回答五个问题：

1. 一条导航路线从什么数据产生？
2. 十二个模块分别做什么，输入和输出是什么？
3. 路径规划为什么是图搜索，而不是简单画一条直线？
4. 工具链为什么有这么多工具，它们各自负责哪一段？
5. 我们怎样把普通路径规划扩展成多主体、多目标、应急和智能体系统？

---

## 1. 先建立三个基本认识

### 1.1 GIS、地图和导航不是一回事

GIS 是处理地理空间信息的一整套方法和软件。它关注对象在哪里、对象之间有什么空间关系、如何分析和展示。

地图是空间数据的一种可视化结果。

导航是在地图和道路网络的基础上，结合出行主体、路线目标、当前位置和环境变化，持续给出行动建议。

~~~text
GIS 提供空间数据和空间分析能力
地图负责把空间信息显示出来
导航负责根据约束和状态做连续决策
~~~

### 1.2 路径规划不是直线距离问题

两点之间的直线距离通常不是可行路线：

- 中间可能有河流、建筑或封闭区域；
- 道路可能是单行道；
- 车辆不能走人行道；
- 道路可能有收费、高速或高度限制；
- 路口可能禁止左转；
- 灾害时道路可能已经被水淹或损毁。

路径规划寻找的是：

> 在允许通行的道路网络中，满足约束并使某种代价最小的道路序列。

### 1.3 导航系统同时处理矢量和栅格

道路、路口、兴趣点通常是矢量数据：

- 点：路口、公交站、事故点；
- 线：道路、河流、轨迹；
- 面：行政区、湖泊、危险区。

DEM、温度、降雨、污染等通常是栅格数据。栅格把空间划分成很多像元，每个像元保存一个数值。

应急场景正是矢量路网和栅格地形结合的典型例子：

~~~text
道路矢量：车辆可以沿哪些边移动
DEM 栅格：每个位置的高程和坡度
灾害栅格：哪些位置有淹水或滑坡风险
路径算法：在综合信息上选择路线
~~~

## 2. 一张图看懂完整系统

### 2.1 四层架构

| 层 | 主要问题 | 典型内容 |
|---|---|---|
| 数据层 | 我们有什么空间数据 | OSM 道路、DEM、GPS、交通事件、兴趣点 |
| 算法层 | 如何从数据得到路线 | 路网建模、权重、Dijkstra、A*、多目标、重规划 |
| 服务层 | 如何给其他程序调用 | 路线 API、地图匹配 API、轨迹 API、缓存、日志 |
| 交互层 | 用户如何看到和使用结果 | 网页地图、路线对比、导航指令、语音、轨迹回放 |

### 2.2 端到端数据流

~~~text
用户输入起点终点
    ↓
地理编码或坐标校验
    ↓
把起终点吸附到最近的可通行道路
    ↓
读取对应出行主体的道路规则
    ↓
生成边权和转向代价
    ↓
调用路径算法
    ↓
输出道路边序列
    ↓
合并道路几何并生成 GeoJSON
    ↓
生成距离、时间、转弯点和文字指令
    ↓
前端地图展示或语音播报
    ↓
接收 GPS 和交通事件
    ↓
判断偏航、封路和路线失效
    ↓
重新规划
~~~

### 2.3 三种对象要一直分清

**道路数据**

描述现实道路本身，例如道路名称、等级、方向、限速和几何形状。

**道路网络**

把道路数据转成图结构，节点和边可以被算法搜索。

**路线结果**

是一次具体查询产生的道路序列、几何线、距离、时间和导航步骤。

~~~text
道路数据 ≠ 道路网络 ≠ 某一次路线结果
~~~

## 3. 十二个模块逐个理解

下面按工程依赖关系说明十二个模块。课程 PPT 可能把相邻功能放在同一页或拆成不同页，这里把它们整理成一条便于学习和实现的链路。

### 模块一：数据获取

#### 它解决什么问题

系统首先要知道哪里有道路、道路怎样连接、哪些道路单行、限速多少、是否收费或允许某种交通主体通行。

#### 主要数据来源

| 数据 | 适合用途 |
|---|---|
| OpenStreetMap | 道路、路口、兴趣点、交通设施和道路标签 |
| Geofabrik 等区域下载 | 获取较大范围的 OSM PBF 文件 |
| Overpass API | 查询小范围的特定要素，例如交通信号灯 |
| GPS 轨迹 | 当前位置、历史行驶路径、地图匹配和偏航测试 |
| DEM | 高程、坡度、地形和应急风险分析 |
| 交通事件 | 拥堵、事故、施工、封路和临时限制 |

#### 输入和输出

~~~text
输入：区域、数据源、时间范围、出行方式
输出：PBF、GeoJSON、Shapefile、GeoTIFF、CSV 或 API JSON
~~~

#### 要掌握的概念

- OSM 是开放地理数据，不是已经完成的路由图；
- PBF 是适合传输和保存 OSM 数据的二进制格式；
- OSM 标签决定道路属性，例如 highway、oneway、maxspeed、access；
- 不同数据源的坐标系、精度、更新时间和许可条件可能不同。

#### 工具

- OpenStreetMap；
- Geofabrik；
- Overpass Turbo；
- osmium；
- QGIS；
- GDAL。

#### 常见错误

- 只下载地图截图，没有获得可计算的道路数据；
- 把所有道路都当成汽车可通行；
- 忽略数据时间，导致实时交通和静态道路混用；
- 没有记录数据来源和下载日期。

### 模块二：数据预处理与质量检查

#### 它解决什么问题

原始数据通常不能直接送进最短路算法。需要清洗、裁剪、转换，并检查几何和属性是否合理。

#### 主要工作

1. 裁剪研究区域；
2. 删除与项目无关的道路类型；
3. 统一字段名称；
4. 处理缺失限速和缺失道路等级；
5. 根据 one-way、access 等标签确定方向；
6. 修复无效几何；
7. 检查道路是否断裂、重复或孤立；
8. 检查道路图是否存在多个不连通分量。

#### 输入和输出

~~~text
输入：原始 PBF、矢量或栅格数据
输出：清洗后的道路图层、属性表、质量检查报告
~~~

#### 工具

- osmium：PBF 裁剪和过滤；
- GDAL/OGR：格式转换；
- Shapely/GEOS：几何修复和空间运算；
- QGIS：人工检查；
- Python：自动化清洗脚本。

#### 为什么这一步重要

如果路网中有断裂，算法会错误地返回无路可达。如果方向错误，系统会规划出逆行路线。如果道路标签处理错误，汽车可能被规划到步行道上。

### 模块三：坐标系、距离和几何处理

#### 它解决什么问题

经纬度不是普通的平面坐标。经度和纬度的一个单位对应的实际距离会随位置变化，不能简单使用欧氏距离。

#### 常见坐标系

| 坐标系 | 主要用途 |
|---|---|
| WGS84 经纬度 | GPS、OSM、GeoJSON 常用坐标 |
| Web Mercator | 网页地图显示常用 |
| UTM 或地方投影 | 距离、面积和工程测量 |

#### 典型操作

- 经纬度和投影坐标转换；
- 两个点之间的球面距离；
- 道路折线长度；
- 点到道路的最近距离；
- 轨迹和道路的空间匹配；
- DEM 重投影和重采样。

#### 工具

- PROJ；
- PyProj；
- Shapely；
- GDAL；
- QGIS。

#### 必须记住的规则

GeoJSON 通常使用：

~~~text
[经度, 纬度]
~~~

很多前端地图或数学代码可能写成：

~~~text
(纬度, 经度)
~~~

顺序写反会让路线跑到错误的位置。

### 模块四：空间数据存储与索引

#### 它解决什么问题

当数据量变大，不能每次查询都扫描全部道路。系统需要保存空间数据，并快速找到附近道路、道路相交关系和研究区域内对象。

#### 常用存储方式

| 存储方式 | 适合阶段 |
|---|---|
| CSV / JSON | 最小实验和调试 |
| GeoJSON | 小区域展示和接口交换 |
| GeoPackage | 单机 GIS 数据交换 |
| GraphML | 图结构保存和 NetworkX 实验 |
| PostgreSQL + PostGIS | 多用户、空间查询和正式服务 |
| 自定义二进制或图引擎格式 | 大规模高性能路由 |

#### 空间索引的作用

空间索引要快速回答：

- 离这个点最近的道路是哪条？
- 哪些道路与危险区相交？
- 哪些道路在研究区域内？
- 哪些道路距离河流小于某个阈值？

常见结构包括 R-tree、GiST 和网格索引。

#### PostGIS 的价值

PostGIS 让数据库能够理解几何对象和空间关系。数据组可以用 SQL 查询，服务组可以通过数据库读取道路，路径规划组可以拿到已经过滤好的网络。

### 模块五：道路网络建模

#### 它解决什么问题

算法不能直接理解一条复杂的道路折线，需要把道路转换成图：

~~~text
节点：路口、道路端点、必要的分割点
边：两个节点之间的一段可通行道路
属性：长度、方向、速度、道路等级、几何、限制
~~~

#### 为什么是有向图

单行道只能沿一个方向行驶。常见做法是：

~~~text
双向道路 → 两条方向相反的有向边
单行道路 → 只保留允许方向的一条边
~~~

#### 边的典型属性

~~~json
{
  "edge_id": "e102",
  "u": "n10",
  "v": "n11",
  "length_m": 420.0,
  "speed_kmh": 40,
  "road_class": "primary",
  "oneway": true,
  "toll": false,
  "slope_mean": 2.4,
  "risk_score": 0.1
}
~~~

#### 工具

- OSMnx：从 OSM 生成路网；
- NetworkX：图结构和基础算法；
- igraph：更高性能的图分析；
- PostGIS/pgRouting：空间数据库中的图；
- OSRM、GraphHopper、Valhalla：成熟路由引擎。

#### 质量检查

- 节点是否重复；
- 边的起点终点是否存在；
- 是否存在孤立节点；
- 道路方向是否正确；
- 道路几何方向是否和边方向一致；
- 最大连通分量是否覆盖研究区域。

### 模块六：路网权重和约束

#### 它解决什么问题

路径算法通常只知道边和边代价。时间最短、距离最短、少红绿灯和低风险的差别，主要来自权重和约束。

#### 基本代价

距离权重：

~~~text
cost(edge) = edge.length_m
~~~

时间权重：

~~~text
cost(edge) = edge.length_m / edge.speed_mps
~~~

红绿灯权重：

~~~text
cost = travel_time + signal_count × average_signal_delay
~~~

#### 硬约束和软约束

硬约束：违反后不能使用，例如不走高速、轮椅不能走楼梯。

软约束：违反后可以使用，但代价增加，例如尽量少红绿灯、尽量安全。

#### 多目标权重

~~~text
total_cost =
    a × normalized_time
  + b × normalized_distance
  + c × normalized_signal_count
  + d × normalized_risk
~~~

不同单位必须归一化。不能直接把秒、米、次数和风险分数相加。

#### 交通主体配置

建议把规则配置成 profile，而不是写死在算法里：

~~~json
{
  "mode": "pedestrian",
  "allowed_road_classes": ["footway", "path", "residential"],
  "forbidden_road_classes": ["motorway"],
  "max_slope_percent": 12,
  "signal_penalty": 20,
  "risk_weight": 0.8
}
~~~

### 模块七：路径规划算法

#### 它解决什么问题

在当前道路图、交通主体、代价和限制下，找到从起点到终点的可行路线。

#### Dijkstra

Dijkstra 在所有边权非负时保证最优。它从起点开始，不断确定当前代价最小的节点。

适合：

- 正确性基线；
- 算法教学；
- 检查权重是否合理；
- 和 A* 做结果对照。

缺点是没有使用终点信息，在大图上可能扩展很多无关节点。

#### A*

A* 使用：

~~~text
f(n) = g(n) + h(n)
~~~

- g(n)：起点到当前节点的真实代价；
- h(n)：当前节点到终点的估计代价；
- f(n)：搜索优先级。

距离最短时，可以使用球面距离作为启发式。时间最短时，启发式必须和时间目标一致，例如用直线距离除以允许的最大速度，得到一个不会高估的时间下界。

#### 算法演进

~~~text
Dijkstra
    → A*
    → 双向 A*
    → 多目标和多主体
    → 动态权重和重规划
    → Landmark / ALT
    → CH / MLD
~~~

课程项目应先把前五步做稳，再考虑大规模加速。

### 模块八：路线后处理与导航指令

#### 它解决什么问题

算法输出的通常是边或节点序列，用户需要的是一条平滑路线、距离、时间和“前方右转”等指令。

#### 主要工作

1. 合并边的几何；
2. 去除重复坐标；
3. 计算总距离和总时间；
4. 识别连续直行和转弯；
5. 生成转弯点；
6. 输出 GeoJSON；
7. 生成文字或语音指令。

#### 转弯识别

可以根据相邻道路的方向角计算转角：

~~~text
转角较小 → 直行
转角为正且较大 → 左转
转角为负且较大 → 右转
接近 180 度 → 掉头
~~~

真实商业导航还会考虑道路名称、车道、复杂路口和出口编号。课程项目先实现基础方向判断即可。

### 模块九：定位与地图匹配

#### 它解决什么问题

GPS 点通常有误差，车辆位置不一定正好落在道路中心线上。地图匹配要判断车辆实际上在哪条道路上。

#### 基础方法

- 最近点匹配；
- 最近道路匹配；
- 根据行驶方向筛选候选道路；
- 根据连续轨迹判断最合理道路序列。

#### HMM 地图匹配

更复杂的方法把道路作为隐藏状态，把 GPS 点作为观测：

~~~text
观测：GPS 点
隐藏状态：车辆所在道路
转移概率：从上一条道路驶向下一条道路的合理程度
发射概率：道路与 GPS 点距离的合理程度
~~~

地图匹配可用于轨迹回放、偏航检测、历史速度统计、交通状态估计和重新规划触发。

### 模块十：动态交通、事件和重新规划

#### 它解决什么问题

静态路线假设道路永远不变，但现实中会出现拥堵、事故、施工、临时封路、车辆偏航和灾害导致道路失效。

#### 重新规划流程

~~~text
当前位置
    ↓
地图匹配
    ↓
判断是否偏离原路线
    ↓
更新道路权重或禁用道路
    ↓
以当前位置为新起点
    ↓
重新调用路径规划
    ↓
更新路线和导航指令
~~~

如果 GPS 有小幅抖动，系统不能每次都改变路线。可以设置偏离距离阈值、连续若干次观测确认、最小重规划时间间隔，以及新路线必须明显优于旧路线。

### 模块十一：服务、地图展示和语音导航

#### 服务层

服务层把算法封装成其他模块可以调用的接口：

~~~text
GET /route
POST /route
POST /match
POST /reroute
GET /health
~~~

典型输入是起点、终点、出行方式、目标和约束，输出是 JSON 和 GeoJSON。

#### 地图展示

前端地图通常需要：

- 起点和终点标记；
- 路线线图层；
- 多路线颜色区分；
- 危险区域或 DEM 图层；
- 当前车辆位置；
- 转弯点和提示面板；
- 轨迹回放动画。

常用工具包括 MapLibre GL JS、Leaflet、OpenLayers 和 Cesium。

#### 语音导航

语音链路可以拆成：

~~~text
转弯识别 → 文字指令 → TTS → 音频播放
~~~

课程项目可以先完成文字指令，再考虑 Piper、eSpeak NG 或其他 TTS 工具。

### 模块十二：测试、评估、部署和运维

#### 算法测试

- A* 与 Dijkstra 的最优代价一致；
- 单行道不会逆行；
- 禁止转弯规则生效；
- 不可达时返回明确错误；
- 车辆不会进入禁止道路；
- 多目标路线的代价和约束满足预期。

#### 数据测试

- 节点和边是否完整；
- 道路是否断裂；
- 坐标是否越界；
- 几何是否为空；
- 属性缺失是否有默认策略。

#### 服务测试

- 正常请求；
- 参数缺失；
- 起点终点不在研究区域；
- 不可达路线；
- 大量并发；
- 数据版本变化。

#### 评估指标

~~~text
正确性：路线是否可行、是否满足约束
效率：预处理时间、单次查询时间、扩展节点数
质量：距离、时间、风险、信号灯数量
稳定性：偏航检测和重规划是否合理
可解释性：用户能否理解路线为何如此选择
~~~

## 4. 路径规划模块的深入理解

### 4.1 起点终点为什么要吸附到道路

用户输入的经纬度通常是一个地图点，但图搜索需要从道路节点或道路边开始。因此要先找到最近的可通行道路。

吸附过程要考虑：

- 距离是否足够近；
- 交通主体是否允许使用该道路；
- 道路方向是否匹配；
- 道路是否在禁行区域；
- 起点和终点是否位于同一连通区域。

不能只找几何上最近的道路。最近的道路可能是隔着河的另一侧，也可能是机动车不能进入的高速。

### 4.2 转向限制为什么需要扩展状态

如果状态只有当前节点，算法不知道车辆上一条边是哪条，就无法表达“从 A 道路禁止左转进入 B 道路”。

可以把状态扩展为：

~~~text
state = (previous_edge, current_node)
~~~

这样可以记录禁止左转、禁止右转、禁止掉头、转弯等待时间、转弯风险和不同交通主体的转向规则。

### 4.3 多目标规划的三种实现方式

**加权和**

把多个目标归一化后按权重相加，容易实现，适合第一阶段。

**分层优化**

先满足硬约束，再最小化时间，再在时间接近时比较风险和距离，结果更容易解释。

**Pareto 候选**

返回一组互不完全占优的路线，例如一条更快、一条更短、一条更安全。展示效果好，但实现复杂度更高。

建议顺序：

~~~text
加权和 → 分层约束 → 多路线候选 → Pareto 前沿
~~~

### 4.4 不同交通主体如何共用算法

推荐使用：

~~~text
共享道路图
    + mode profile
    + objective profile
    + event layer
    + risk layer
    = 不同场景的规划结果
~~~

算法不需要知道“这是自行车还是消防车”的全部业务含义，只需要接收允许道路、速度、代价和限制。

### 4.5 应急场景和 DEM

应急场景至少要维护三类信息：

1. 道路通行性；
2. 地形和水文风险；
3. 临时灾害事件。

DEM 可以派生坡度、坡向、低洼和汇流等属性，再采样到道路边上：

~~~text
DEM 栅格
    → 坡度/汇流分析
    → 道路采样
    → 边属性 slope、lowland、flow_accumulation
    → 应急代价和禁行判断
~~~

但 DEM 本身不是洪水预报。真实洪水风险还要结合降雨、水位、河流、土地利用和历史灾害数据。课程项目可以采用“DEM 派生地形风险 + 模拟封路事件”的可解释方案。

## 5. 工具链应该怎样理解

### 5.1 Python 原型链

适合第一阶段：

~~~text
OSM / OSMnx
    → NetworkX
    → 自己的 Dijkstra / A*
    → FastAPI
    → GeoJSON
    → Leaflet 或 MapLibre
~~~

优点是容易读懂、容易调试、适合教学和算法对比。

### 5.2 GIS 数据处理链

~~~text
PBF / GeoTIFF
    → osmium / GDAL
    → QGIS 检查
    → PyProj 统一坐标
    → Shapely 处理几何
    → PostGIS 或图文件
~~~

### 5.3 成熟路由引擎链

| 引擎 | 语言和特点 | 我们的用途 |
|---|---|---|
| OSRM | C++，高性能驾车路由 | 结果和性能对照 |
| GraphHopper | Java，可配置权重和多种加速 | 学习权重和工程架构 |
| Valhalla | C++，多模式和动态 costing | 学习复杂导航服务 |
| pgRouting | PostgreSQL/PostGIS 扩展 | 学习数据库内路由 |

### 5.4 DEM 和栅格分析链

~~~text
DEM GeoTIFF
    → GDAL 重投影和裁剪
    → gdaldem 生成坡度和坡向
    → GRASS GIS 生成流向和汇流
    → 栅格采样到道路
    → 应急路线权重
~~~

## 6. 路径规划智能体和可复用 Skill

### 6.1 四个概念的关系

| 概念 | 作用 |
|---|---|
| 算法 | 真正计算路线 |
| 工具 | 提供地理编码、匹配、路由、DEM 分析等具体能力 |
| Skill | 把一套稳定流程封装成可复用任务 |
| Agent | 理解需求并决定调用哪些 Skill 和工具 |

### 6.2 推荐的智能体流程

~~~text
用户自然语言
    ↓
需求解析
    ↓
结构化 RouteRequest
    ↓
选择交通主体和目标
    ↓
调用数据、匹配、路由和评估工具
    ↓
验证路线是否满足约束
    ↓
生成路线、解释、备选方案和警告
~~~

大模型不应该直接生成一条未经验证的道路序列。它应该负责理解和编排，确定性的算法负责计算，验证器负责检查。

### 6.3 推荐的 Skill

- route_planning：普通路线；
- multi_objective_routing：多目标候选；
- mode_profile：汽车、骑行、步行、轮椅、消防车；
- dem_terrain_analysis：坡度、低洼和汇流分析；
- emergency_routing：救援和疏散；
- route_explanation：解释路线原因；
- rerouting：偏航和封路重规划；
- route_evaluation：比较算法和路线质量。

### 6.4 智能体的创新点

项目创新不一定要求提出全新的最短路算法，也可以体现在：

- 多交通主体规则统一建模；
- 多目标路线和备选路线；
- DEM 地形风险参与应急规划；
- 自然语言约束转换为结构化参数；
- 智能体自动选择工具和路线策略；
- 把数据处理、路由、验证和解释沉淀成可复用流程。

## 7. 一个完整的应急示例

用户输入：

> 暴雨后，规划消防车从消防站到事故点的最快路线，避开高汇流和低洼道路，并提供备用路线。

系统处理：

1. 识别场景为 emergency_rescue；
2. 识别交通主体为 fire_truck；
3. 把消防站和事故点吸附到可通行道路；
4. 读取 DEM 派生的坡度和汇流图层；
5. 读取暴雨导致的临时封路事件；
6. 禁用风险极高或已关闭道路；
7. 以响应时间为主目标；
8. 以坡度、低洼和汇流风险作为附加代价；
9. 计算主路线和备用路线；
10. 检查两条路线是否经过同一处高风险瓶颈；
11. 返回路线、风险说明、距离、时间和警告；
12. 在地图上显示 DEM、风险区域、主路线和备用路线。

最终结果不应只返回一条线，还应该告诉用户：

- 为什么选择这条路线；
- 哪些道路被排除了；
- 预计多久到达；
- 备用路线和主路线有什么差别；
- 哪些路段风险较高；
- 数据更新时间和风险模型的局限。

## 8. 我们项目应该按什么顺序学习和实现

### 阶段一：理解和跑通基础

- 掌握经纬度、GeoJSON、道路图；

- 跑通 Dijkstra；
- 跑通 A*；
- 写单元测试；

### 阶段二：加入真实道路属性

- 处理单行道；
- 处理道路等级；
- 加入限速和时间权重；
- 加入不走高速和少收费；
- 加入转向惩罚；
- 生成导航步骤。

### 阶段三：多主体、多目标和动态

- 汽车、骑行、步行 profile；
- 最快、最短、少红绿灯路线；
- 多路线比较；
- 轨迹回放；
- 偏航检测；
- 封路后重规划。

### 阶段四：DEM 应急路线

- 获得小区域 DEM；
- 计算坡度；
- 采样道路坡度；
- 模拟低洼路段封闭；
- 规划消防车或疏散路线；
- 增加备用路线；
- 在地图上展示地形和风险。

### 阶段五：智能体和 Skill

- 定义 RouteRequest；
- 实现工具函数；
- 实现 Skill 流程；
- 让智能体解析自然语言；
- 调用路径规划和 DEM 工具；
- 验证结果并生成解释。

## 10. 最终的系统定位

我们要做的不是一个单纯的最短路程序，而是一套：

> **面向多交通主体、多目标偏好和应急地形风险的可解释智能路径规划系统。**

最小可行版本是：

~~~text
OSM 道路数据
    → 有向道路图
    → Dijkstra / A*
    → 时间、距离和道路约束
    → FastAPI
    → GeoJSON 和网页地图
~~~

完整特色版本是：

~~~text
多交通主体
    + 多目标路线
    + 轨迹与偏航重规划
    + DEM 地形风险
    + 应急救援或疏散
    + 智能体工具编排
    + 可复用 Skill
~~~

最推荐的项目名称：

> **面向多交通主体与灾害地形风险的可解释智能路径规划智能体**
